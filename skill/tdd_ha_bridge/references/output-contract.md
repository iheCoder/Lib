# Developer Review Document

默认使用中文，代码符号、接口名和仓库业务术语保留原样。目标读者是熟悉业务和代码、但不要求掌握测试理论术语的普通后端开发者。

本文件用于 Deterministic Software Route。AI agent 路由遵循同一份主文档契约，并补充 [agent-eval-protocol.md](agent-eval-protocol.md) 的多次运行、评分与安全要求。

## 交付目标

主文档是一篇完整、清楚、可以独立审查的测试或 eval 文档。读者只看主文档，就应理解：

- 这次验证的对象、范围、输入和环境是什么；
- 六类检查角度分别检查了什么，为什么与当前需求有关；
- 哪些行为已经覆盖、只覆盖了一部分、尚未覆盖或确实不适用；
- 选择了哪些具体场景，场景怎样发生，预期结果来自哪里；
- 已经运行时，模型或实现实际做了什么，为什么据此判断；
- 哪些业务规则或风险仍需要人决定；
- 当前结论还不能证明什么，批准后下一步是什么。

不设置阅读时长、字数、表格列数、场景数或待决策问题数目标。简单任务可以很短，复杂任务应写到普通开发者无需追问“到底发生了什么”为止。

主文档不是内部推理转储。应省略的是重复的 `B/R/T/V/M` 映射、无关方法论、低价值变体和机器处理细节；不能省略帮助读者理解结论的业务背景、事件顺序、预期、实际表现、判断理由和影响。

## 主文档与复现附件的边界

默认产物可以包含：

1. `test-design-*.md` 或 `eval-report-*.md`：完整的开发者审批主文档；
2. `*.evidence.md`、原始轨迹、JSON、脚本和哈希清单：按需生成的复现或技术审计附件。

划分标准不是“正文短、附件长”，而是信息用途：

- **理解和审批所需的信息必须写入主文档。** 包括场景背景、为何选择、预期结果、实际表现、对照差异、判断理由、影响、限制和待决策事项。
- **复现和机器追踪所需的信息可以放入附件。** 包括完整 Source Ledger、全量 Behavior/Risk/Fault 映射、未裁剪轨迹、评分 JSON、文件哈希、脚本输出和穷尽矩阵。
- 原始材料链接用于复核，不能代替正文解释。删除正文某段后，如果读者必须打开附件才能知道“发生了什么”或“为什么这样判”，那段内容就不该删除。
- 附件不能改变主文档结论。附件显示某项只在纸面设计、缺少真实触发或存在评分争议时，主文档必须同步说明。

文档较长时增加目录、清楚的标题和按业务故事分组。不要通过缩写、超宽表格或把必要说明移到附件来制造表面简短。

## 先区分设计文档与运行报告

### 尚未实际运行

测试或 eval 仍处于设计阶段时，主文档写清：

- 准备验证什么；
- 每个场景怎样设置前置状态和触发条件；
- 正确结果和绝不能发生的副作用；
- 准备用什么层级、控制点和观察点验证；
- 当前属于“场景已设计”“可以执行”还是“环境暂时测不了”；
- 哪些预期还没有业务依据。

此时没有“实际表现”。必须明确写“尚未运行”，不能把纸面方案写成已经覆盖或已经通过。

### 已经实际运行

测试或 eval 已经运行时，除设计信息外还要写清：

- 实际使用的版本、环境、输入、运行次数和必要配置；
- 真实观察到的输出、状态、副作用或对话行为；
- 实际表现与预期在哪一步一致或偏离；
- 重复运行是否一致，出现差异时分别发生了什么；
- 有 baseline、旧版、新版、Skill 或无 Skill 对照时，各方在相同输入下分别怎样表现；
- 样本、隔离、评分或环境限制会怎样约束结论。

通过数、平均分、`PASS/PARTIAL` 标签和评分文件引用只能作为总览，不能代替上述解释。

## 主文档内容契约

下面是默认信息顺序，不是为了形式完整而机械填充的固定模板。简单任务可以合并章节，但不能丢失适用信息。

### 1. 这次验证什么

先说明：

- 用户目标和被测行为；
- 代码、服务、agent、prompt 或流程的范围；
- 本次明确不改变或不评价的内容；
- 需求、接口、调用方、已有测试等关键依据；
- 当前是设计阶段还是已经运行；
- 已运行时使用了什么环境、版本、输入和对照方式。

不要用“完成轨迹检查”“运行了 Lens”代替具体对象。读者应该知道测试的是哪种业务过程以及哪种失败风险。

### 2. 当前结论

说明现在能否进入测试编写、是否需要修改设计、是否被业务规则或测试条件阻塞，以及最重要的依据。

结论可以概括，但后文必须能找到完整支撑。下面这些句子只有证据存放位置或评分标签，没有证据内容，不能单独作为结果：

> 已检查实际轨迹和逐条原文评分，发现一次确认缺口。

> 财务题 4/4 通过，云盘题部分通过，详见附件。

应直接说发生了什么。例如：

> 助手第二轮明确把父目录不存在和名称冲突留待以后决定，第三轮却在用户只同意既有机制后，将“先恢复父目录、冲突时拒绝”写成已经确认的规则。因此互动确认失败；问题不是该策略一定错误，而是用户没有选择它。

### 3. 六类检查角度及覆盖情况

第一次出现时说明 Lens 是“用来系统检查是否遗漏重要风险的角度”。六类都要出现，不相关时也要说明当前代码或架构中为什么不存在这类风险：

| 检查角度（Lens） | 它在当前需求中检查什么 | 状态 | 支撑场景 | 判断依据与剩余缺口 |
| --- | --- | --- | --- | --- |
| 业务规则（Contract） | 输入、结果、副作用和禁止行为是否清楚 | 已覆盖 / 部分覆盖 / 未覆盖 / 不适用 | 场景名称 | 具体说明 |
| 状态变化（State） | 删除、停用、重试等前后状态是否正确 | ... | ... | ... |
| 输入与边界（Partition） | 不同业务分区和临界值是否有代表场景 | ... | ... | ... |
| 外部依赖（Interaction） | DB、RPC、消息等部分失败时会发生什么 | ... | ... | ... |
| 时间与并发（Time/Concurrency） | 同时发生、先后错位、超时和重复执行是否安全 | ... | ... | ... |
| 兼容与回归（Regression） | 旧调用方、旧数据和非目标路径是否保持 | ... | ... | ... |

状态含义：

- `已覆盖`：预期有可信依据，并且存在能够真实触发和观察的验证；已运行报告还要求实际执行结果支持结论。
- `部分覆盖`：已经检查一部分，但业务规则、场景、触发手段、真实依赖、观察点或实际执行仍有明确缺口。
- `未覆盖`：与本次变更相关且重要，但还没有有效场景或验证方法。
- `不适用`：根据当前需求、代码和架构边界确实不存在这类风险，并写出理由。

表格只提供全局关系。某个 Lens 的状态如果无法在一两句话内解释清楚，应在表后单独展开：具体检查了哪些风险、哪些场景支撑判断、为什么仍有缺口、不补会怎样。不能把“部分覆盖”当成无需解释的自明标签。

### 4. 具体场景

按业务故事或失败过程组织场景。所有会改变批准结论、实现选择或主要风险判断的场景都应进入主文档。重复试次或只替换无关样例值的变体可以合并，但要说明合并依据和结果是否一致。

每个场景应让读者理解：

1. **为什么检查它**：它保护什么业务行为，准备抓住哪种现实错误；
2. **当时的上下文**：系统状态、已经确认与尚未确认的规则、外部能力和必要规模；
3. **具体触发过程**：输入、操作、故障或并发事件按照什么顺序发生；
4. **预期结果**：应该发生什么、绝不能发生什么、依据来自哪里；
5. **验证办法**：怎样稳定制造条件，观察哪些输出、持久状态和副作用；
6. **当前验证状态**：尚未运行、可执行、环境暂时测不了、已通过、失败或结果不确定；
7. **实际表现**：仅在真实运行后填写，引用足以证明判断的关键输出、状态或原话；
8. **判断理由**：实际与预期在哪一步相符或偏离；
9. **实际影响**：错误会怎样影响用户、数据、权限、交付或后续实现。

存在 A/B 对照时，在同一场景下解释双方，不让读者跨两个章节自行拼接。例如同时写清 Skill 得到什么输入、怎样处理，无 Skill 得到相同输入后怎样处理，以及差异为什么有意义。

通过项也要解释怎样通过。可以对同一模式的多个通过样本合并说明，但至少完整展开一个代表场景，并说明其他样本是否一致。不能只写“全部通过”。

原文或状态证据只选能证明判断的部分，用自然语言补齐前后关系；不要把整份轨迹复制进正文。完整轨迹可以放附件。

### 5. 需要人决定的事项

只询问答案不同会改变业务行为、测试预期、接口、数据状态或实现方案的问题，不设数量上限，也不为凑结构制造问题。

每项说明：

- 发生在什么现实场景；
- 当前为什么无法从证据确定；
- 有哪些合理选择；
- 当前建议及理由；
- 每种选择如何改变用户结果、测试和实现；
- 在决定前哪些工作可以继续，哪些结论必须保留为未知。

标题使用普通开发者可以直接回答的完整问题。例如：“订单已经保存，但消息发送失败时，接口应该告诉客户端成功还是失败？”不要只写“幂等语义待确认”或“Oracle ambiguity”。

### 6. 还没有证明什么

分别说明缺口属于哪一种：

- 正确业务结果还没有依据；
- 重要风险尚未设计场景；
- 场景已设计但还没运行；
- 测试环境无法稳定制造目标故障或时序；
- 观察点不足，无法区分正确与错误实现；
- 外部依赖、数据规模或生产环境没有被真实覆盖；
- 样本、隔离或评分不足以支持更广泛结论。

每项同时说明“不补会怎样”和最小补强办法。不要用 `UNKNOWN`、`TESTABILITY_GAP`、`pseudo-killer` 等词代替解释。

### 7. 审批事项与下一步

把真正需要确认的业务规则、可接受风险、测试环境投入和下一步列清楚。可以使用勾选项，但根据任务删除不适用内容，不制造形式审批。

结尾写具体动作，例如“产品先选择消息失败后的返回语义；其余四个场景可以开始编写测试”，不要只写“建议继续完善测试”。

## 复现与技术审计附件

需要时可以包含：

1. Context Boundary 与完整 Source Ledger；
2. Behavior Obligations；
3. P0/P1 Risk 与 plausible faults；
4. `Fault → Scenario → Control → Observable` 全量映射；
5. 验证层级与 Fidelity Claim；
6. Blind Fault Inventory 和 survivor/pseudo-killer；
7. 完整运行轨迹、评分输入输出、哈希、脚本、命令和原始结果。

附件可以使用 `B/R/T/V/M` ID。主文档引用附件时，说明链接用于复核哪项事实，不要把解释责任交给附件。

## 常用术语翻译

| 内部术语 | 主文档优先写法 |
| --- | --- |
| Oracle ambiguity | 正确结果还没有业务依据 |
| Testability gap | 当前测试环境无法稳定制造或观察这个情况 |
| Linearization point | 系统从哪个准确时点算“已经开始执行” |
| Trigger replay | 同一轮调度再次触发或被重试 |
| Cross-instance | 两台或多台服务同时执行 |
| Idempotency | 重复执行也不会产生重复结果 |
| Harness | 测试环境或测试装置 |
| Test seam | 为测试增加的可控时点或注入点 |
| Survivor | 现有测试仍抓不到的错误实现 |
| Pseudo-killer | 场景写了，但当前测试办法并不能真实触发那个错误 |
| Fidelity | 测试是否保留了要验证的真实机制 |

## 交付前可理解性自检

交付前只阅读主文档，逐项回答：

1. 能否说明这次验证的对象、范围、输入、环境以及是否已经实际运行？
2. 能否逐个说明六类 Lens 在当前需求中检查了什么、为什么得到当前覆盖状态、由哪些场景支撑？
3. 能否复述每个重要场景的上下文、触发顺序、预期、验证办法和当前状态？
4. 已经运行时，能否说明实际发生了什么、对照双方怎样表现、为什么据此判断以及有什么影响？
5. 能否区分“实际通过”“场景已设计但未运行”“环境暂时测不了”和“正确结果尚未确定”？
6. 能否说明每个待决策问题的现实后果，以及不同选择怎样改变测试和实现？
7. 是否必须打开附件或追踪 `B4 → R2 → T6 → V3 → M2` 才能理解任何重要结论？若是，把必要解释移回主文档。
8. 是否出现“实际轨迹、逐条评分、发现缺口、表现较好”等没有对象、过程和结果的压缩句？若有，改写成具体事件。
9. 是否重复展示同一事实，或者加入与当前审批无关的方法论、部署步骤和低价值细节？若有，删除重复和无关内容，同时保留完整因果关系。

结构检查只能证明必要信息存在，不能证明普通开发者真的读懂。验证这个 Skill 时，还要按 [self-eval-protocol.md](self-eval-protocol.md) 进行盲读复述和决策任务。
