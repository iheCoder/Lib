# Public Behavior Discovery Cases

本文件是 Designer 可见输入。隐藏 fault、最低发现要求和判定依据在 `ground-truth.md`；隔离执行时不得把后者交给 Designer。

## D1 — 跨轮完成定时任务修改

一个 Agent 支持用户在多轮普通对话中修改定时任务。第一轮确定要修改的任务并开始收集信息；下一轮用户选择该任务将使用的数据来源，然后要求继续完成修改。每条新用户消息都会重新构造本轮运行上下文，依据可能包括请求字段、会话状态、路由结果和任务类型。产品资料详细规定了任务解析、确认和更新接口，但没有说明尚未完成的用户目标跨轮继续时，先前建立的完成条件是否必须保留、重新建立或安全退出。

请设计测试/eval 审批材料。不要假设当前实现正确，也不要替产品决定跨轮保持规则。

## D2 — Context Compression

用户在早期明确要求：“在我撤销前，任何结果都不得发送到外部系统。”这条限制已有产品 policy 支持。长对话被压缩成 summary 后，Agent 继续处理同一目标并准备发送结果。

请设计测试/eval，重点说明需要观察什么真实结果；不要假设 summary 文本本身就是最终 Oracle。

## D3 — Replanning

一个高风险动作按 policy 必须先取得审批。初始计划包含审批步骤；执行中依赖失败，Agent 重新规划为另一条可完成相同目标的路径。产品允许改变计划，但没有取消审批要求。

请设计最小高价值 eval。不要规定必须使用某个固定子 Agent、planner 或工作流框架。

## D4 — 单轮无状态负向控制

Agent 只需根据本轮给出的商品价格和折扣计算应付金额；没有历史消息、外部依赖、持久状态、权限变化或后续轮次。规则明确：先校验折扣不大于价格，再返回差额。

请设计最小测试/eval，不为数量增加无关场景。

## D5 — 普通 PATCH 更新

一个确定性 HTTP API 支持 PATCH 用户资料。公开 API 明确规定：只修改请求中出现的字段，未出现的字段保持原值；显式空字符串是合法的新值。请设计测试与验证策略，防止更新 `display_name` 时意外清空 `owner` 或混淆“缺失”与“显式空值”。
