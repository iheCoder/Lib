建议采用 PostgreSQL 保存任务事实、队列触发执行、对象存储保存 CSV 的方案。允许同一任务被重复投递，甚至短时间内重复计算；但只有持有当前执行资格的进程才能发布结果。页面看到“完成”时，文件已经生成，任务与文件的绑定已在数据库中一次性提交，此后不再更换。

下面是一份可供后端评审的设计。有效期暂按“从任务创建时起算”说明；这一点需要产品确认，如果希望用户总能获得完整的下载时间，应改为从完成时起算，并重新核对数据版本和文件的保留期限。具体时长、重试预算和并发限制属于部署参数，本文不预设数值。

### 一、必须保持的业务约束

1. 创建任务时选定并持久化数据版本，接口返回这一版本。执行和重试均使用任务中的版本，不重新选择最新版本。
2. 一个任务最多发布一个结果。重复执行可以产生临时文件，但不能产生多个对外可见的下载结果。
3. 完成状态与结果引用同时提交。完成后，重试、旧执行进程和撤权操作都不能修改完成状态或替换文件。
4. 创建时鉴权；每次下载请求重新调用权限服务鉴权。撤权不停止计算，不使任务失败，也不删除已完成结果。
5. 有效期内保留结果文件。存储或网络暂时不可用时，下载返回可重试错误，不能把已完成任务改回运行中或触发重新导出。

任务状态查询暂按“同租户的任务创建者可以查看自己的任务”设计；任务号本身不是访问凭据。查询状态不重新要求报表导出权限，因此用户撤权后仍能看到任务完成，但无法下载。若平台已有任务共享规则，应沿用平台规则。

### 二、接口

| 接口 | 行为 |
| --- | --- |
| `POST /reports/{report_id}/exports` | 登录及租户检查，调用权限服务检查导出权限，选择已发布版本，创建任务，返回 `202`、任务号、数据版本、状态和到期时间 |
| `GET /exports/{task_id}` | 检查任务访问权限，返回状态、固定的数据版本、到期时间；失败时返回可展示的错误说明 |
| `GET /exports/{task_id}/download` | 检查任务访问权限、完成状态及有效期，重新鉴权，通过后由平台读取私有对象并流式返回 CSV |

状态使用 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`。重试等待可以表现为 `QUEUED`，但 `SUCCEEDED` 不允许回退。到期单独通过 `expires_at` 表达，不需要把已完成任务改成另一个状态；到期下载返回 `410`。

创建接口仅在数据库提交成功后返回任务号。一次请求创建一个任务；客户端重复提交可能创建不同任务，这不违反“每个已创建任务只有一个结果”。如产品另有重复点击合并要求，再增加创建请求幂等机制。

### 三、持久化数据

任务表至少包含以下信息：

| 字段组 | 内容与用途 |
| --- | --- |
| 身份 | `id`、`tenant_id`、`created_by`、`report_id` |
| 固定输入 | `data_version`；如果报表列定义、筛选条件或格式配置可变，还需保存本次采用的配置或不可变配置版本 |
| 生命周期 | `status`、`created_at`、`expires_at`、`completed_at` |
| 执行资格 | 单调递增的 `attempt_no`、`lease_until`，用于识别当前执行并拒绝旧执行提交 |
| 重试与调度 | `next_dispatch_at`、`last_error`；执行次数可直接使用 `attempt_no` |
| 完成结果 | `object_key`、`file_size`、内容校验值；这些字段在完成时一次性写入 |

对 `SUCCEEDED` 增加完整性约束，要求结果引用和完成时间非空。数据库更新入口必须禁止修改已完成任务的固定输入和结果。任务状态接口不返回内部对象地址。

### 四、创建任务与可靠投递

创建流程依次执行身份检查、强一致权限检查、选择已发布版本、插入任务。后台后续不再鉴权，也不因撤权修改任务。

这里将创建时的权限判断点定义为本次权限服务调用；若业务要求权限必须一直保持到数据库提交瞬间，跨服务的一次鉴权不能保证这一点，需要额外协议，不能靠在提交前再查一次彻底解决。

不要依赖“数据库写入成功后，尽力发一次队列消息”。进程在两者之间退出会留下永远不执行的任务。

本次可以直接让任务表充当持久化待执行清单，避免另外引入一张事务消息表：

- 创建事务写入 `QUEUED` 和立即可调度的时间。
- 一个周期性调度器扫描到期的排队任务，以及租约已过期的运行任务，发送只包含任务号的队列消息。
- 发送成功后推迟下一次投递检查；发送失败则保留待投递条件，继续重试。扫描不能只依赖进程启动时执行一次。
- 调度器多实例并发发送或“发成功但更新数据库前崩溃”都可能产生重复消息，由工作进程的执行资格检查处理。

调度更新需带上读到的状态、执行编号等条件，不能覆盖工作进程刚写入的新执行或新重试计划。成功、失败或到期的任务不继续投递。

### 五、执行、重试与结果发布

**取得执行资格。** 工作进程收到消息后，以一条条件更新领取任务：任务必须可执行且仍在有效期内，并且处于到期可运行的排队状态，或原执行租约已经过期。领取时设置 `RUNNING`、增加 `attempt_no` 并写入新租约，返回新的执行编号。

这条更新以 PostgreSQL 为准，时间判断也使用数据库时间。两个进程同时领取同一任务时，只能有一个成功。没有领到任务的进程直接结束本次消息处理。

**流式生成文件。** 当前执行定期续租，同时始终携带固定的 `data_version` 分页查询。每页编码为 CSV 后写入对象存储分片上传，只保留有限大小的页和上传缓冲，通过背压控制内存。重试从头生成，不在本次需求中引入分页断点恢复。

分页必须具备稳定排序和明确的游标或分页语义；版本不可变并不自动保证无排序查询的分页稳定。需要在联调中确认同版本遍历没有重复和遗漏。所有分页请求都必须显式传入版本，不能在某个续页或重试分支回落到“当前版本”。

每次执行使用独立的对象键，例如 `exports/{task_id}/{attempt_no}.csv`。不同执行禁止覆盖同一对象。空结果也生成包含表头的合法 CSV；CSV 按既定列顺序输出，统一处理引号、逗号、换行、编码及字段类型格式。

**完成上传后再发布。** 完成分片上传，确认对象存储已成功形成可读取的完整对象，并校验大小和可用的内容校验值，然后执行数据库条件更新：

```sql
UPDATE export_tasks
SET status = 'SUCCEEDED',
    object_key = :object_key,
    file_size = :file_size,
    checksum = :checksum,
    completed_at = clock_timestamp(),
    lease_until = NULL
WHERE id = :task_id
  AND status = 'RUNNING'
  AND attempt_no = :attempt_no
  AND lease_until > clock_timestamp()
  AND expires_at > clock_timestamp();
```

只有影响一行才表示本次执行成功发布。状态与结果引用由这一条更新同时变成可见，状态查询以数据库为准。对象存储与 PostgreSQL 不需要分布式事务：对象先形成、引用后提交，中间失败最多产生没有被引用的文件，不会先显示完成再等待文件生成。

**失去执行资格。** 续租也必须检查执行编号、运行状态及租约尚未过期。续租失败后停止继续查询和上传；即使进程因暂停或网络异常未能及时停止，它恢复后也不能提交结果，因为执行编号或租约条件已经失效。

**自动重试。** 数据服务、对象存储或网络的临时故障使用退避重试；工作进程主动失败时，凭当前执行编号将任务改回排队并设置下次执行时间。进程直接退出则通过租约过期重新调度。确定不可恢复的错误或重试预算耗尽进入 `FAILED`，同样必须带当前执行资格条件，不能由旧进程覆盖新的执行或完成结果。

队列消息的确认时机应遵循所用队列的续期协议，但队列可见性超时不是执行所有权：即使消息已确认后进程退出，任务表扫描仍能恢复；即使消息提前重复投递，数据库也能拒绝重复领取。

### 六、下载与撤权

下载入口执行以下顺序：

1. 校验登录身份、租户和任务访问范围。
2. 读取已完成任务的固定对象引用，检查有效期。
3. 调用权限服务，检查当前用户对任务对应报表的导出权限。服务超时或不可用时返回可重试错误，不使用历史通过结果放行。
4. 鉴权通过后，从私有对象存储读取固定文件，通过平台向用户流式传输。

下载不返回可绕开平台鉴权、供浏览器反复访问的对象存储签名地址。若平台内部使用签名地址，由后端消费；浏览器始终经过平台下载入口。响应禁止共享缓存，平台缓存命中也不能跳过鉴权。

每个新下载请求，包括断点续传的新 Range 请求，都重新鉴权。同一次请求鉴权通过后可以完成文件传输，不在传输中再次检查撤权。权限检查和撤权并发时，遵循本次权限服务返回的结果；撤权提交成功后才开始的权限调用必须拒绝。已经下载到用户设备上的文件不在撤权回收范围内。

### 七、保留与清理

成功发布的文件在任务有效期内不得被清理或覆盖，对象存储生命周期策略必须覆盖这段时间。平台与存储的读权限、对象版本或覆盖策略，应能保证结果字节不会在发布后被其他执行修改。

未发布的执行文件由清理任务回收。清理依据是数据库确认该执行已被更大的执行编号取代，或任务已终结且文件不是已发布结果；不能仅凭“租约看起来过期”删除当前执行的对象，也不能在提交结果返回网络错误时直接删除文件，因为事务可能已经提交成功。

到期清理需要与已授权的传输协调：到期后不再接受新的下载，但已通过鉴权的请求允许完成。应确认存储对已打开读取的删除语义；若不保证读取可继续，平台需维护下载使用期并在传输结束后清理，不能把一个任意固定宽限期当作保证。具体采用哪一种取决于现有平台下载入口的能力。

### 八、关键故障验收

| 场景 | 应验证的结果 |
| --- | --- |
| 导出过程中发布新数据版本 | 返回版本与所有分页请求版本一致，CSV 不混入新版本数据 |
| 数据库提交后、发队列消息前退出 | 扫描恢复投递，任务最终执行 |
| 多实例同时收到同一消息 | 同一时刻只有一个有效执行资格 |
| 旧进程暂停、租约失效，新进程接管后旧进程恢复 | 旧进程不能续租、发布结果或把新执行改为失败 |
| 上传完成后、提交结果前退出 | 页面不会显示完成；重试可以生成新对象，遗留对象可回收 |
| 提交完成后、确认消息前退出 | 再次投递不重新计算，状态和结果引用不变 |
| 结果提交实际成功，但进程收到超时 | 不误删已发布文件；重查数据库可确认完成结果 |
| 运行中或完成后撤权 | 计算和完成状态不变；撤权之后开始的下载鉴权拒绝 |
| 下载鉴权通过后撤权 | 当前传输完成，新请求重新鉴权并拒绝 |
| 大文件、空数据、特殊字符、多页边界 | 内存有界，CSV 格式正确，数据无重复或遗漏 |
| 临近到期开始下载，同时发生文件清理 | 已授权传输不中断，到期后的新请求拒绝 |

上线前重点观察任务排队时长、执行时长、租约失效与重试次数、最终失败率、无引用对象量，以及下载鉴权和传输错误。日志统一携带任务号、数据版本和执行编号，避免记录报表内容。

评审需要首先确认有效期的起算点，以及现有分页与下载入口是否满足上述依赖。核心正确性依赖三处边界：创建时固定版本，数据库条件更新唯一发布结果，平台在每次下载时重新鉴权。
