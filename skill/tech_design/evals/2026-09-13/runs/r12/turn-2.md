按原方案，第一段要先区分“C 收到重复消息”和“C 成功取得执行资格”。重复投递本身不会让 C 接管任务。第二段则有明确结果：这次下载被拒绝，页面上的完成状态保持不变。

### 第一段：重复执行与旧实例失败回写

假设 A 领取 T 时，数据库中的执行编号是 `n`。

**1. B 发布 V42，不改变 T 的输入。**

T 创建时已经持久化 `data_version = V41`。V42 的发布不会修改这个字段，V41 也仍然可查。

如果 C 成功取得执行资格，它会按原方案从第一页重新生成文件，第一份请求和后续所有分页都读取 **V41**。它不承接 A 的第一页，也不查询最新版本。

**2. C 收到消息后，首先尝试数据库领取。**

- 如果 A 的数据库租约尚未过期，C 的领取条件不成立，更新影响零行。C 在这里结束，不能继续生成或发布结果。
- 如果 A 的租约已经过期，T 仍为可执行状态且任务尚未到期，C 可以原子领取，把执行编号从 `n` 增加为 `n+1`，设置新的租约。
- 如果 T 已到期或已经终结，领取同样被阻止。

因此，“A 长时间停顿”和“队列再次投递”不能单独证明 C 一定能接管。决定权在 PostgreSQL 的状态、执行编号和租约条件。

**3. 在 C 已成功领取的分支中，C 仍需满足发布条件。**

C 可以用 `n+1` 续租，把 V41 的完整 CSV 上传到本次执行独立的对象键。上传完成后，只有数据库仍满足以下条件，发布才生效：

```text
status = RUNNING
attempt_no = n+1
租约尚未过期
任务尚未到期
```

条件成立时，C 在一次数据库更新中写入 `SUCCEEDED` 和文件引用。完整文件先存在，完成状态后可见。

如果 C 上传失败、租约过期或执行资格又被其他实例接管，这次发布不会成功；即使上传了对象，也只是未发布文件。不能仅凭“C 尝试发布”就推导 T 已完成。

**4. A 恢复后，旧执行不能回写失败。**

在 C 已领取的分支中，A 仍携带旧编号 `n`，数据库已经是 `n+1`。A 的续租、失败回写和结果发布都因执行编号不匹配而影响零行。如果 C 已经发布成功，`status = RUNNING` 的条件也不成立。

A 自己判断“本次执行超时”只是本地错误信息，不会赋予它修改任务的权力。即使 A 没有及时停止，仍然向自己的独立对象键写入数据，也不能替换 C 的文件或修改任务的结果引用；这些未发布对象之后清理。

**最终结果取决于前面实际成功的步骤：**

| 实际分支 | 最终可确定的结果 |
| --- | --- |
| C 取得资格并成功发布，随后 A 尝试回写失败 | T 保持 `SUCCEEDED`，唯一结果是 C 生成的完整 V41 CSV；A 的失败回写不生效 |
| C 的领取被拒绝 | C 没有结果可发布。T 后续由仍有效的执行或重新调度推进，不能从题述直接认定为完成 |
| C 领取成功，但发布条件不成立或生成失败 | 不能认定 T 已完成；按实际数据库状态恢复或重试。A 仍不能用旧编号覆盖任务 |

在 C 被拒绝、A 恢复的分支中，A 的失败处理也必须检查当前执行资格。资格仍有效时才可按重试策略回到排队或进入最终失败；资格已过期则交由恢复调度处理，不能无条件写失败。

这里“可下载文件”指任务绑定的结果文件；用户实际取得它，还需要通过每次下载时的鉴权。

### 第二段：旧页面上的下载入口与撤权

**这次请求不能取得文件，U 仍保持完成。**

原页面显示下载入口，并没有完成这次下载的授权，也没有获得可以绕过平台的对象存储地址。A 点击后，请求进入 C，C 检查任务访问范围、完成状态和有效期，然后重新调用权限服务。

题述中，撤权已经提交成功，C 随后才收到下载请求，因此这次权限调用发生在撤权提交之后。按已给定的强一致保证，它会读到撤权后的状态并拒绝导出权限。**原设计下载流程的第 3 步——本次请求重新调用权限服务——决定拒绝结果。** C 不进入第 4 步，不读取并传输 CSV。

如果权限服务不可用，原方案同样不会用旧页面或历史授权结果放行，而是返回可重试错误。“鉴权通过后的这一次传输可以完成”不适用于这里，因为 A 尚未发起下载，之前打开详情页不算本次下载鉴权。

这两段顺序不要求改变原方案的核心机制。实现时需要把原文中的“当前执行资格”落实到失败更新条件中：同时检查运行状态、执行编号和未过期租约，并检查受影响行数；绝不能只按任务号更新失败。这样代码才能兑现上述推演。
