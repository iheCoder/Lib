建议复用现有个人设置存储，新增一个“收藏报表 ID 集合”，由 Go 服务统一处理收藏变更和列表排序。这个规模不需要新增服务、缓存或专门的收藏表。

### 数据与接口

在每个用户的个人设置中增加 `favorite_report_ids`，保存报表的稳定 ID，缺省为空集合。具体使用现有设置表的扩展字段还是增加列，沿用当前存储方式；不必为收藏改变个人设置的整体结构。

复用现有保存个人设置的接口，增加针对单张报表的局部更新操作，输入只有报表 ID 和期望状态，例如：

```json
{"report_id":"report-123","favorite":true}
```

具体请求结构沿用现有接口规范。用户身份始终从登录态取得，不接受客户端指定设置所属用户。

服务端先使用现有权限判断确认当前用户能看到该报表，再保存变更。无权访问时沿用现有接口的错误约定，不产生修改。收藏已收藏的报表、取消未收藏的报表都成功返回，重复请求不会反转状态。保存成功后返回该次保存的收藏状态。

### 保存与并发

客户端提交“把这张报表设为收藏／未收藏”，不要提交整个收藏集合，也不要使用“切换状态”的指令。否则两个设备各自拿着旧数据保存时，可能覆盖其他报表的收藏操作，重试也可能把状态切回去。

更新必须基于数据库中的最新值。可以使用 PostgreSQL 的原子字段更新；如果现有存储方式需要先读取、再由 Go 修改，则在同一事务中锁定该用户的设置行，读取后只增删目标报表 ID，再提交。优先沿用项目已有的局部更新机制。

同一用户的更新由数据库串行处理，同一报表以最后成功提交的保存为准，事务提交后才返回成功。不使用客户端时间戳，也不以响应到达设备的顺序判断最终状态。不同报表的并发操作都应保留。

需要一并检查现有个人设置保存逻辑：修改其他设置时不能用旧的整份设置覆盖收藏字段；收藏更新也不能覆盖其他设置。这是复用现有表时最需要确认的地方。

### 列表与页面

现有列表接口继续负责权限过滤，并为每张可见报表增加 `is_favorite`。排序规则为：

1. 当前用户收藏的报表在前。
2. 收藏组和未收藏组各自沿用原有完整排序规则。

如果列表在数据库中排序、分页，就把收藏状态作为原排序之前的排序条件，并在分页前完成；如果现有接口一次返回全部报表，则可以在 Go 中对原有有序结果做稳定分组。不能只对某一页分组，否则后续页的收藏报表无法排到列表前面。

页面根据 `is_favorite` 显示收藏按钮。点击后发送目标状态，该按钮在请求期间暂时禁用；成功后重新获取列表，使图标和排序与服务端一致，失败则保留原状态并提示重试。重新登录、换设备和刷新列表都会读取同一份服务端设置。本次不增加设备间实时推送，其他设备在下次获取列表时看到最新结果。

报表失去权限后，仍由现有列表接口过滤，不因收藏获得访问权限。设计上保留其收藏记录，因此以后恢复权限时会恢复收藏显示；这不需要额外的清理流程。

### 验证与交付

实现前只需核对现有个人设置的存储及更新方式、列表是否分页，然后确定具体 SQL 和字段变更。重点验证：

- 用户之间互不影响，重新登录及换设备后收藏仍在。
- 两组内部排序保持原样；存在分页时，收藏排序作用于全部可见结果。
- 无权限报表不能通过直接调用接口收藏或取消，也不会出现在列表里。
- 两个设备对同一报表提交相反状态，最终结果符合数据库提交顺序；重复提交同一状态不产生额外变化。
- 并发修改不同报表以及其他个人设置时，各项修改不会互相覆盖。
- 保存失败时界面不显示成功，重新获取列表可以恢复服务端真实状态。

交付范围是个人设置的一处数据扩展、单张报表的收藏更新、列表状态与排序，以及页面按钮。旧用户没有收藏数据时按空集合处理，原列表顺序自然保持不变。
