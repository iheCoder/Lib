## 4. 用户关心的几个问题，具体测到了什么

### 语言是否更容易理解

判据没有使用术语数量、中文比例或字数，而是检查：读者能否沿一次操作说明谁接手、读写什么、何时生效、为什么需要某个概念，以及尚待决定什么。评分看完整对话；六份预先选定文本另由独立读者只凭原文复述，必须附逐字引用，不得用工程经验替作者补步骤。

在收藏题里，双方都解释了为什么请求应该表达“设为收藏”，而不是“反转状态”；也都解释了为什么保存时读取最新集合、为什么排序要发生在分页之前。两份对应盲读均没有指出关键过程缺口。这一题没有复现“无 Skill 只能给晦涩术语”的情况。

盲读也有不能忽略的局限。名称题的一份 Skill 回答停在尚未确认的 CRM 分页保证上，无 Skill 对照则交付了附带接口前提的文档；两者阶段不同。导出题抽取的是后续时序回答，读者发现的部分缺口实际已在首轮说明。不能将这些缺口直接算成语言问题，更不能宣称测得真人阅读速度或理解率。详见 [六份盲读观察](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/reading/observations.md)。

### 是否不再一上来给长稿、夹带无关内容

这是本轮最清楚的差异。以第一次导出对照为例：

- 有 Skill 先聚焦旧执行恢复、独立文件、数据库条件发布和中断后重算的取舍，解释“任务”与“一次执行”为什么不同，然后请求确认主要方向。[原文](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r06/turn-1.md)
- 无 Skill 也正确解释了这些机制，但随后另给了十行故障注入验证矩阵，以及等待时长、重试次数、下载错误、未回收对象等运行指标。[原文](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r03/turn-1.md:84)

名称题的另一份无 Skill 文档继续展开“验证与发布”、8 分钟告警和回退步骤。这些内容没有改善已经解释清楚的名称查询机制，是范围评分的具体扣分依据。[原文](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r08/turn-3.md:66)

这里不把所有验证相关内容都扣分。通常时延不是容量证明、完整分页需要外部保证、文件清理会不会破坏有效期内下载，都直接影响方案，属于必要设计。被扣分的是额外展开的测试和日常运行交付。

导出首轮字符数平均约为 Skill 1951、无 Skill 4981。但在同处最终文档阶段的第二次名称题中，Skill 有 3870 字符，无 Skill 有 2884 字符：较长的 Skill 文档仍保持设计范围，较短的无 Skill 文档则夹带验证和运行安排。字符数只描述实际篇幅，不能当作理解成本或效率分。导出题原本明确要求评审设计，因此无 Skill 提供完整建议本身也没有被判错；Skill 聚焦讨论与无 Skill 完整文档并非同等阶段。**本轮支持的是范围控制差异，不是“越短越好”，也不是已经证明不存在信息过载。**

### 是否避免防御性过度设计，同时保留必要防护

低风险收藏题用于检查这个问题。双方都复用现有服务、个人设置与权限查询，没有扩展为独立服务、缓存平台或异步系统。

双方也都发现了真实联动：手机刚收藏 A，电脑随后保存一份旧的整套个人设置，可能把收藏覆盖掉。因此仅让收藏接口自身并发安全还不够，其他设置保存也必须避免覆盖不属于它的字段。这是当前失败路径支持的必要处理，不因使用事务或锁就判为过度设计。[Skill 原文](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r07/turn-1.md)、[无 Skill 原文](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r10/turn-1.md)

本轮没有观察到该维度的条件差异。尤其没有运行“同一个导出题去掉重试与撤权后”的低风险变体，所以尚不能证明 Skill 会随着风险消失主动删除多余机制。

### 是否基于关键约束提出真正合理的方案

名称题先给出一次批查约 80ms、订单约 120ms、页面目标约 350ms、每秒 12 次请求、CRM 每秒 60 次共享额度，以及可容忍 10 分钟陈旧和已有后台任务。题目没有要求“请列三个方案”。

双方都识别了两条可行路径：每次翻页去重后批查；提前维护名称副本、翻页读取本地。理由涉及页面等待、调用量、后台维护和过期处理，未用逐条请求这种明显较差方案凑数。

第二轮批查变为约 500ms。原先推荐同步等待的回答都移出了请求链；不能用短超时使正常请求一直缺名称来伪装满足时延。另一份 Skill 首轮已推荐后台刷新，第二轮解释哪些判断变化、为何仍保留主流程，得到了同样认可。[该 Skill 的三轮记录](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r11/turn-1.md)

这验证了本题中合理候选和约束适应能力，但双方均通过，没有证据说 Skill 能想出更多或更好的方案。不同正确方案也没有被强行收敛为唯一架构。

### 是否能处理 A、B、C 的复杂联动

导出题由一个未读 Skill 和旧 eval 的独立作者编写，隐藏判据逐条引用原需求，主要检查：

1. A 按 V41 读第一页并停顿；B 发布 V42；C 收到重投任务。C 必须继续使用创建时返回的 V41。
2. C 发布成功后，A 恢复并尝试写失败。已完成状态和正式文件必须保持稳定；保护数据库却允许覆盖正式对象也不成立。
3. A 在有权限时打开完成页面，B 撤权，C 随后处理旧页面发来的下载。页面仍可显示完成，但本次下载必须重新鉴权并拒绝。

两条件的两个重复均在首轮主动联系了版本变化与重试，以及旧执行恢复与结果覆盖。权限项中，一组被评为已解释因果，另一组仅记为有有效防护。两位评分者对“主动串联”的严格程度有差别；各自组内两条件同判。绝对通过数受此影响，不能把 1/2 解释成可靠发现概率。

还有一项 Skill 的真实不足：第二次重复的首轮虽然说完成后不能改成失败，却未明确独立失败处理的原子写入条件。被追问后，它自己指出：不能先查“尚未完成”再无条件写失败，因为 C 可能在两步之间提交成功；必须把未完成和执行资格检查放入失败更新本身。该项首轮防护记为不完整，第二轮记为补充细节，没有回填首轮分数。[补充原文](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-13/runs/r09/turn-2.md:19)

四次尝试在给出具体时序后都推演正确。这说明本批双方都有处理能力，同时说明 Skill 仍可能停在原则层面，需要具体交错才能补全关键机制。它不能被包装成“装了 Skill 就更善于发现复杂问题”。

## 5. 尚未证明的部分

- 没有真实普通开发者参加盲读，也没有真人校准评分；模型读者可能比目标读者强，模型评分也有共同盲区。
- 三道题每条件仅两次，作者知道 Skill；只有导出题作者未读 Skill 和旧结果。不是全面独立 holdout 或统计显著性实验。
- 无 Skill 仍有共同系统指令的清晰表达与最小化要求，不是没有任何引导的裸模型。新题不再提示“先解释概念”等目标行为，但背景约束本身当然会提示设计问题。
- 本轮衡量的是把已给条件连接成具体因果，不是发现所有隐藏现实约束。没有同一导出任务的风险消融，没有用户说“没看懂”后的真实适应性解释修复。
- 部分回答自报使用 Skill，匿名包只删除了四段加载元说明，原文完整保留；处理清单可查。风格仍可能泄露条件，不能保证完全盲化。
- 精确底层模型版本、采样参数和完整工具轨迹未由接口提供。使用新上下文及指定文件边界，但共享文件系统不是操作系统隔离。
- 一份 Skill 名称对话停在合理接口澄清，未交付最终文档。其适应能力通过不代表完整交付完成；本轮不以不公平追加消息救分。
