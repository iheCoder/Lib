# 技术设计 Skill 实际评估结果

## 1. 先看结论

**当前 Skill 能完成详细技术设计，但本轮没有证明它比不加载 Skill 更好。最明确的问题发生在云盘回收站题：助手先说“原父目录不存在和名称冲突时怎么办”稍后再定，下一轮却把“必须先恢复父目录、名称冲突就拒绝”写成已经讨论确认的规则。** 它在另外一些试次中能解释实际过程、承认外部能力不足、随新事实修正方案，也能在简单需求已确认时直接交付。

运行了 3 类题目，每类在加载/不加载 Skill 两个条件下各重复 2 次，共 **12 个独立试次、32 轮主对话**；另有 4 轮云盘追加验证。所有试次使用当前会话的同一继承配置，无模型参数覆盖。主评分为 Skill **4/6** 全项通过、对照 **5/6**；这不是可靠性概率，更不能据此认定 Skill 更差：其中有输入缺口，复核者对一个对照试次也有评分分歧。

此前只有格式校验，没有可比较的旧版行为基线。当前 Skill 全程冻结，源码未改。阅读时优先看第 3 节的覆盖范围和第 4 节的实际问题。

### 这 12 个试次具体怎么运行

评估使用财务自动提交、云盘回收站和项目改名三道题。每道题分别运行两次加载 Skill 的对话和两次不加载 Skill 的对话。每次从新的对话上下文开始，两边收到相同的用户消息；多轮题按相同顺序逐轮补充信息，模型不能提前看到后续消息。

这里所谓“实际轨迹”，就是一份真实保存下来的完整对话：第一轮用户给了什么条件、助手怎么回答；第二轮用户增加了什么事实、助手是否改变方案；最后用户批准了哪些内容、助手最终写了什么。评分者看到的是匿名后的整段对话，不知道哪份加载了 Skill，并对每一项判断引用助手原话。报告下面直接解释这些对话发生了什么；原始文件链接只用于复核。

## 2. 需要决定的事

本次运行已获用户明确授权，没有等待审批的事项。后续最值得处理的是：**用户概括地说“同意”，只能覆盖此前已经解释的建议，不能把明确待定的关键业务规则也视为已批准。** 建议只针对这个边界做小改动，再用失败轨迹和新题复测，不增加固定问卷或逐字段审批。

### 财务系统超时：本地看见相同现象，却需要做相反决定

**当时的上下文。** 四个 Go 服务实例共用 MySQL，每分钟扫描已批准的报销申请并提交财务。申请有全局唯一编号，业务要求不能漏单，也不能重复入账。第一轮只知道财务调用可能超时。

**真正触发判断的新事实。** 第二轮用户说明：财务既不按申请编号防重，也不能查询结果，而且调用超时可能已经完成入账。此时本地只看到“超时”，背后却可能是两种情况：请求根本没送达，再试一次才能避免漏单；请求已经入账，再试一次会重复入账。

**预期表现。** 助手必须承认仅靠 MySQL 任务表、实例锁、等待更久或限制重试次数，无法同时保证不漏和不重。它应该暂停自动重试设计，说明需要财务提供原子防重、结果查询或权威人工核实能力。第三轮财务补齐按申请编号唯一约束与查询接口后，助手才可以恢复自动重试方案，并让每次重试使用同一个编号。

**Skill 实际怎样做。** 代表试次明确回答：“在目前这个财务接口能力下，我方无法保证每张申请最终都入账、并且只入账一次”，并解释“多等几分钟、限制重试次数，或换一个实例继续，都不会补上这条缺失的信息”。财务补齐能力后，它设计为审批与本地待办一起提交；实例领取任务；恢复时先按原编号查询，没查到仍用原编号提交；旧实例恢复后的写入不能覆盖新实例结果。[Skill 第二轮](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/finance-s1/turn-2.md:1) · [Skill 第三轮](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/finance-s1/turn-3.md:17)

**无 Skill 实际怎样做。** 代表试次同样先停止承诺：“在财务现有能力下，我们无法同时保证‘不漏入账’和‘不重复入账’”，还明确指出数据库锁、延长超时和限制次数都不能消除歧义。能力补齐后，它也采用固定编号、财务防重、本地持久任务与接手恢复。[无 Skill 第二轮](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/finance-b1/turn-2.md:1) · [无 Skill 第三轮](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/finance-b1/turn-3.md:37)

**为什么双方都通过。** 两个条件各两次都识别出：本地协调只能防本地重复处理，不能替财务回答“刚才是否已经入账”。它们都随着外部能力变化修正了结论，也都解释了财务已入账、本地未保存便宕机时如何恢复。这说明本题里 Skill 没有表现出可观测优势；不能只写“4/4 通过”而省略双方到底做对了什么。

### 项目改名：信息已经给齐时，应直接交付小方案

**当时的上下文。** 这是内部后台每天几十次使用的小功能。用户已经确认所有者权限、名称长度、同名允许、最后提交成功者生效、现有表和事务足够，并明确不需要审计历史、版本号或软删除。

**预期表现。** 助手不应重新问已经确认的问题，也不应因为出现并发就增加消息队列、异步任务、版本历史或新服务。设计只需讲清身份校验、名称整理、带所有者条件的更新、事务提交后返回，以及同名提交和并发覆盖的边界。

**双方实际怎样做。** Skill 两次和无 Skill 两次都直接交付，没有新增业务对象或基础设施。两边还都注意到一个具体数据库边界：提交与当前名称相同的值时，MySQL 可能报告影响 0 行，不能因此把合法请求误判成项目不存在或无权限。Skill 代表回答通过同一事务内的当前读取区分这两种情况；无 Skill 代表回答先锁定符合项目 ID 与所有者条件的记录，再更新名称。[Skill 代表回答](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/simple-s1/turn-1.md:15) · [无 Skill 代表回答](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/simple-b1/turn-1.md:12)

**为什么双方都通过。** 它们都尊重已经收敛的范围，方案复杂度与每天几十次、单服务单库的实际规模相称。这一题证明本轮没有观察到 Skill 把简单功能拖进长问卷，也同样没有观察到无 Skill 会过度设计；它不是 Skill 优势证据。

### 云盘回收站：技术机制基本成立，分歧出在“用户到底确认了什么”

**当时的上下文。** 用户要求删除最大 1 万节点的目录，相关分享可能涉及 10 万用户。分享权限必须保留；接收者可以有多个独立共享入口；先单独删除的子文件不能在恢复父目录时被顺带恢复。删除提交后停止签发新的下载链接，但已签发链接可继续使用十分钟。

**预期表现。** 助手需要解释删除究竟更新 1 万个文件节点还是 10 万条分享记录、删除何时生效、现有链接为何还能使用、恢复时为何重新看当前权限。更关键的是：如果它说原父目录不存在或名称冲突的恢复行为还没确定，下一轮用户概括同意已经解释过的机制时，它仍应把这两项留作待决定，不能偷偷选一种用户可见规则。

**双方共同做到的部分。** 两个条件都能把原文件、分享权限和共享入口区分开，说明 10 万分享用户不会让删除变成 10 万次权限更新；也都把签发新链接的停止时点和已经签发链接的十分钟有效期分开。技术机制不是这次失败的中心。

### Skill 的第二个云盘试次：明确说稍后确定，随后却直接定案

加载 Skill 的第二个云盘试次，在[第二轮第 47 行](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/cloud-s2/turn-2.md:47)明确写道：

> 先假设原父目录仍可用、没有名称冲突；这些恢复落点问题稍后单独确定。

下一条用户消息只同意“上面解释的机制和模型”，并授权助手决定常规字段与接口命名。这里预期它继续保留恢复落点问题，或者先把候选行为及影响讲给用户再确认。助手却在[第三轮第 64 行](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/cloud-s2/turn-3.md:64)直接规定“父目录也在回收站时，需要先恢复父目录”，名称冲突时拒绝恢复，并在[第 67 行](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/cloud-s2/turn-3.md:67)称这是“沿用前面讨论的原位恢复”。

原位拒绝策略本身可以合理，但它改变用户能否选择其他恢复位置，并不是字段命名。这里将此前明确待定的规则写成了已经讨论确定的结论。主评分与未见其结果的另一位评审都认定互动存在缺口；两者对是否同时扣文档收敛分有分歧，原始成绩均保留。另一个 Skill 试次没有重复这个错误，因此这是一条真实失败证据，尚不是稳定出现的失败率估计。

**同一输入下无 Skill 的第二个试次怎样做。** 它在第一轮已经明确提出建议：“父目录已删除时要求先恢复父目录，同名时拒绝覆盖并提示冲突”，同时说明也可以选择恢复到根目录、指定位置或自动改名。第三轮用户同意此前的恢复取舍后，它沿用这个建议，授权范围比 Skill 失败试次更有依据。[无 Skill 第一轮建议](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/cloud-b2/turn-1.md:50) · [无 Skill 第三轮定稿](/Users/ihewe/GolandProjects/Lib/skill/tech_design/evals/2026-09-12/runs/cloud-b2/turn-3.md:33)

不过无 Skill 也不是毫无疑问地通过：它没有明确讨论接收者移除的共享入口是否进入回收站，最终选择“不新增入口恢复能力”。独立复核认为这可能是保持最小范围，也可能遗漏了用户概括同意并未覆盖的行为，因此将互动和收敛都保留为“部分通过”。这就是报告中所说的评分分歧：不是两个评分者随意打了不同标签，而是“未要求新能力时保持现状”是否足以处理共享入口恢复语义，现有题目没有唯一答案。

**实际影响。** Skill 的确定性缺口会把一个未选择的恢复策略交给开发实现：父目录丢失时用户不能改到其他位置，名称冲突时只能失败。无 Skill 的不确定项则说明题目本身没有给足共享入口恢复规则，不能强行判成确定错误。这两种情况必须分开，不能合并成一句“发现确认缺口”。

### 没有误算为 Skill 故障的情况

第一个 Skill 云盘试次继续追问恢复位置与物理对象是否复用；原始固定输入确实没有回答。对此保留“输入不足”，没有强判模型不肯收敛。

统一补齐这些前提后，追加评分认为 **Skill 两次均完成独立文档；对照一次完成，另一次只补充前文、独立性不足**。追加输入是看到原始输出后补写的开发验证，不能回填主成绩或当作未见题证明。它也不能抹掉第二个 Skill 试次此前未经确认就定案的行为。
