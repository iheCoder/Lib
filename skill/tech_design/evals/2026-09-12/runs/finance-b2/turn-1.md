当前最关键的是：**用申请编号建立财务侧的幂等保证，并明确超时后的处理方式。** 四个实例如何分工，可以通过 MySQL 解决；能否安全重试，取决于财务 API 的能力。

先看最危险的一种情况：财务已经接收了申请，但返回受理编号时网络超时。我方看到的只有超时，无法判断是否成功。直接重试可能重复入账；永远不重试又可能漏单。因此，申请编号虽然全局唯一，还必须让财务系统实际用它防重。

建议先按下面的机制讨论：

1. **财务提交使用固定的业务幂等键。** 每次都传同一个申请编号，包括超时重试、实例重启和人工重试。财务需要保证同一编号的并发或重复请求只产生一笔业务，并返回已有受理结果。这项保证必须覆盖实际入账，且不能在我方仍可能重试时失效；仅仅允许传一个编号不算幂等支持。

2. **审批通过与生成待提交记录一起落库。** 在同一个 MySQL 事务中完成，避免审批已通过却没有待提交任务。提交记录对申请编号加唯一约束，防止重复创建。这里以审批通过后的内容不再变更为前提。

3. **四个实例通过数据库原子领取任务。** 每分钟扫描后，用短事务或条件更新抢占一批任务，记录领取者和有效期；只有领取成功的实例才能调用财务。网络请求放在事务外，结果更新时检查领取身份，防止旧执行者覆盖新结果。领取过期可以恢复处理，但不代表上一次财务调用没有成功。

4. **把超时当作结果未知。** 收到受理编号就持久化，停止重复提交；超时则保留为待确认。若财务支持按申请编号查询，就查询并补记结果；若有可靠幂等保证，也可以使用原编号重试。查询“未找到”本身不能证明可以安全重提，因为原请求可能还在处理中。受理成功也只表示提交已被接受，不直接等同于入账完成。

一天约 2000 单，每分钟扫描的方案可以先保留，当前无需增加队列。**如果财务既不保证幂等，也没有能排除原请求继续执行的确认机制，我方就无法同时保证“不漏提交”和“不重复入账”。** 在能力未确认前，结果未知的申请应暂停自动重提，进入查询或人工核对。

现在最需要向财务确认的是：**他们是否支持以申请编号保证重复、并发提交只受理并入账一次，以及按该编号查询处理结果？** 这个答案决定超时后能否自动恢复，也是下一步技术设计的前提。
