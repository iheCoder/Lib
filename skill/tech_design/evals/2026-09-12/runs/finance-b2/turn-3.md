现在可以完成自动恢复了。我推荐的模型是：**我方持久记录提交任务，允许反复尝试；财务用申请编号保证只入账一次；我方通过查询或重复提交补齐本地结果。** 两边不需要同时提交一个事务，允许短时间出现“财务已入账、本地尚未确认”，但必须能自动收敛。

申请编号始终代表同一笔报销。重试、实例切换、人工触发恢复，都不能换编号。

**一、审批通过时，可靠地留下提交任务。**

在同一个 MySQL 事务中更新审批结果，并插入提交记录。提交记录以申请编号作唯一约束。事务提交后，扫描器才能看到并处理它，因此不会提交未通过审批的申请，也不会出现审批已通过却漏建任务的情况。

记录中保留提交内容、受理编号、下次处理时间、领取凭据、领取有效期和最近一次错误即可。提交内容在审批通过时固定下来，后续恢复使用相同编号和相同内容，避免重试时读到已经变化的数据。

受理编号为空表示“本地尚未确认完成”，其中可能包含财务已经入账的申请；有受理编号才表示提交任务完成。处理中可以由领取有效期表达，当前不必另加一套复杂状态。

**二、四个实例通过 MySQL 领取，调用财务时不占用数据库事务。**

每分钟扫描受理编号为空、已到处理时间、且没有有效领取的记录。实例通过条件更新原子领取：再次检查这些条件，写入本次唯一领取凭据和有效期，只有更新成功者才能处理。每次领取少量任务，避免领到的任务长时间排队。

领取有效期应覆盖正常的查询、提交和本地保存耗时，网络调用设置明确超时；有效期统一使用数据库时间判断。实例宕机后，其他实例可在领取过期后接手。

领取只能减少并发调用，不能彻底避免重叠：旧实例可能仍在等待财务响应，新实例已经接手。这种重叠由财务唯一约束保证不会重复入账。

**三、所有领取都执行同一条恢复流程。**

考虑到每天约 2000 单，我建议先统一采用“先查、再决定是否提交”，让首次处理和宕机恢复共用一套流程：

1. 按申请编号查询财务。查到已入账及受理编号，就进入本地完成步骤。
2. 明确查不到时，使用原申请编号和固定内容提交。即使此前的请求正在处理中，财务的事务内唯一约束也必须保证最终只有一笔入账，重复请求返回同一受理编号。
3. 查询失败、提交超时或暂时不可用时，不标记完成，记录错误并安排下次处理。如果接口返回“处理中”，同样稍后再查。
4. 获得受理编号后，在本地短事务中保存，并清除领取信息。更新必须匹配本次领取凭据，防止已失去领取权的旧实例覆盖新执行者的记录。

如果本地另有“已同步财务”等业务字段，与受理编号在同一个本地事务中更新。只有这个事务提交后，我方才对外展示同步完成。

先查会增加接口调用量；可以待运行后根据财务限流情况调整。正确性的关键仍然是固定编号和财务幂等，查询负责方便地取回已有结果。

**四、宕机不需要猜测上一轮执行到了哪里。**

| 中断位置 | 恢复方式 |
|---|---|
| 审批事务提交前 | 审批结果和提交记录一起回滚，不会留下半完成记录 |
| 任务已落库，尚未调用财务 | 后续扫描领取，查询无结果后提交 |
| 财务已入账，本地未保存受理编号 | 领取过期后重新查询，取回同一受理编号并保存 |
| 提交超时，不知道是否入账 | 后续查询；明确未查到时按原编号重提，由财务防重 |
| 本地保存结果时连接中断，不知道事务是否提交 | 若已提交，扫描不再选中；若未提交，后续再从财务补齐 |
| 旧实例恢复，和新实例同时处理 | 财务防止重复入账，本地领取凭据防止过期执行者覆盖结果 |

临时故障持续重试，并逐步延长间隔；超过运维关注的时长就告警，不能因为达到重试次数而删除任务或假装完成。明确的业务拒绝需要记录原因并交给业务处理，不能靠无限重试解决。

这个模型的两项保证分别来自不同地方：**“不重复入账”来自财务事务内的唯一约束；“不漏掉需要处理的申请”来自审批与任务一起落库，以及未完成任务持续可恢复。** 最终完成还依赖财务恢复可用、请求符合其业务规则。

联调时最需要实际验证的是：同编号并发提交、财务入账后响应丢失，以及我方收到成功后在本地保存前宕机。三种情况下都应只有一笔财务入账，且恢复后本地拿到同一受理编号。财务的防重约束必须持续有效，并与入账结果一起提交，不能只是一个会过期的接口缓存。
