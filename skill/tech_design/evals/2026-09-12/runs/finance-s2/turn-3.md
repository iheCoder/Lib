现在可以把方案闭合起来了。我推荐：**MySQL 持续保存每份申请的提交进度，实例领取后先向财务查结果，必要时使用原申请编号提交；本地只有保存了受理编号才算完成。** 实例宕机后，其他实例沿同一流程恢复。财务负责同一申请只入账一次，我们负责让尚未确认完成的申请一直有机会被继续处理。

之前不能安全解决的是“财务可能成功、本地却不知道”。现在财务能按申请编号返回原结果，重复请求又不会重复入账，这个不确定状态就有了恢复路径。

下面按这个选择整理设计。没有项目源码可核对，文中是推荐实现；尤其需要在实施时找到现有审批落库入口，将提交登记接入同一次事务。

**先用一份申请走完整个过程。**

1. 申请 A 审批通过时，Go 服务在同一个 MySQL 事务里保存审批结果，并把财务提交进度登记为“待处理”。事务提交后，页面可以显示“审批通过，等待财务提交”。如果事务未成功，两项修改都不生效，避免出现审批已经通过、却没有登记提交责任的申请。
2. 每分钟，四个实例分别查找到了处理时间的申请。发现 A 后，通过带条件的数据库更新竞争领取：A 必须仍然符合提交条件，并处于待处理状态；更新成功的实例将它改成“执行中”，记录本次执行标识和领取到期时间。只有领取成功的实例才能继续，事务结束后再调用财务。
3. 领取者先按 A 的全局唯一编号查询财务。查到已有单据及受理编号，就直接保存这个结果，不再新建单据。如果财务明确返回未找到，就读取这份申请固定的提交内容，携带原申请编号调用提交接口。
4. 提交返回受理编号后，实例在一次本地数据库更新中同时保存受理编号、将进度改为“已受理”，并清除领取信息。更新必须匹配本次执行标识，防止旧执行覆盖新的处理结果。事务提交后，本地才向用户展示“财务已受理”，后续扫描不再领取它。
5. 查询或提交遇到超时、连接中断等无法确定结果的情况，保留申请编号、提交内容和错误信息，将申请安排到后续时间继续处理。下一次仍然先查询，再决定是否提交，不需要猜测上一轮到底执行到了哪里。

“已受理”表示我们已经拿到并保存了财务受理编号。是否已经完成会计入账，应以财务接口对该结果的定义为准，不应仅凭受理编号在页面上宣称入账完成。这个功能的本地完成点是确认提交已被财务受理；同一申请最终只入账一次，由财务承诺的入账事务约束保证。

**核心模型可以保持很小。**

业务上仍然只有原来的报销申请。我们需要补充的是“这份已批准的申请向财务交付到哪里了”，可以先直接作为申请记录的一组提交信息，不必另建通用任务系统。

| 需要保存的信息 | 含义与存在理由 |
| --- | --- |
| 申请编号 | 原有的全局唯一编号，始终表示同一笔报销。财务查询和所有重试都使用它，不能每次尝试生成新编号。 |
| 固定的提交内容 | 本次审批通过后要交付财务的金额、报销项目等内容。重试必须重发同一份内容，不能因为员工资料或其他关联数据后来变化而悄悄改变报销单。 |
| 财务提交进度 | 区分待处理、执行中、已受理，以及确定需要业务处理的错误，避免把财务提交进度混进审批状态。 |
| 财务受理编号 | 财务确认的结果凭据。必须和“已受理”一起保存，不能只改状态、遗漏编号。 |
| 本次执行标识、领取到期时间 | 前者区分前后两次执行，后者让宕机实例领取的申请能够被接手。它们表示临时处理权，不表示财务是否已经成功。 |
| 下次处理时间、最近一次错误 | 控制后续处理节奏，并解释申请为什么还没有完成。它们不能代替财务结果。 |

固定提交内容不一定要求再复制一份完整申请：如果现有系统已经保存了不可变的已审批内容，就直接引用它；否则，在审批通过、登记待处理时保存向财务提交所需的内容。两种实现都要达到同一个效果：同一申请编号的提交内容固定，不从不断变化的关联资料重新拼装。

进度的含义尤其需要明确：

- **待处理**：本地还没有保存确定的受理结果，后续需要处理。它既可以是尚未发起第一次调用，也可以是上次超时后等待确认，不能解释成“财务肯定没有入账”。
- **执行中**：某个实例暂时领取了处理权。接口可能尚未调用，也可能已经在财务成功，单凭这个状态无法判断。
- **已受理**：本地已保存财务受理编号，自动提交流程完成。
- **需处理**：财务明确拒绝了这份报销，例如确定的业务校验错误。同样的无效内容不应无限自动重发，但这份申请仍然没有交付完成，不能当作成功或直接丢弃。后续修正应遵循现有报销与审批规则。

不需要另建一套持久化的“曾经发送”“可能成功”“等待查询”状态。因为每次领取后都先查询，恢复流程能够统一处理这些情况。代价是首次提交也多一次财务查询；在目前一天约 2000 单的数量级下，我倾向于用这点调用成本换取更简单的恢复机制，实际仍需核对财务接口限流和高峰流量。

**你提到的宕机场景，具体这样恢复。**

假设实例 1 领取 A，执行标识是第 7 次；财务已经入账并生成受理编号 F，但实例 1 在保存 F 前宕机。

MySQL 中的 A 会停留在“执行中”，仍保留第 7 次执行标识和领取到期时间。本地页面应显示提交处理中，不能显示失败，也不能让用户通过创建另一份申请来代替这次重试。

领取到期后，实例 2 在扫描中发现 A，通过条件更新接手：必须确认 A 仍在执行中且确实已到期，并将执行标识改为第 8 次、设置新的到期时间。接着按 A 查询财务，取得 F，再以“当前仍是第 8 次执行”为条件保存 F 和“已受理”。至此恢复完成，无须重新入账。

还要考虑实例 1 只是暂停、后来又恢复运行：

- 如果它晚到的成功结果尝试写回，由于第 7 次执行已经失效，本地更新不会成功，它应结束本次执行，不覆盖第 8 次执行的结果。
- 如果它的财务请求仍在途中，而实例 2 的查询暂时返回未找到，实例 2 可能再次提交 A。此时两个请求可以同时到达财务；财务必须利用已承诺的唯一约束，让它们对应同一份单据和同一次入账，最终返回同一个受理编号。

第二种情况说明：领取到期时间不能确保外部请求已经停止。因此，不论期限设置多长，财务的去重保证都仍然必要。期限应结合客户端请求超时和本地处理耗时设置，避免正常执行频繁被接手，但正确性不依赖两个执行绝不重叠。

**其他失败也沿相同机制处理。**

查询超时时，本轮不必再追加一次提交，等待后续扫描即可；查询明确未找到时，即使查询存在短暂延迟，使用同一编号再次提交也是安全的，因为财务会去重。若查询只返回正在处理、尚无受理编号，则保留待处理责任，稍后继续查询。

提交已成功、本地保存受理编号失败时，也不能把财务结果改写成“提交失败”。如果实例仍能更新数据库，可以安排后续确认；如果数据库完全不可用，就让领取自然到期，由恢复后的扫描继续。即使保存结果的数据库提交本身返回超时，恢复后也先读取本地状态：已经是“已受理”就结束，否则继续向财务查询。

暂时性错误可以逐步延长重试间隔，恢复后继续处理；不应因为达到某个重试次数就把申请标记完成或永久移出待办。明确的业务拒绝则保留为需处理事项。重试能够应对暂时故障，但如果财务长期不可用或始终拒绝一份申请，技术机制无法保证它最终入账；这里的“不漏单”首先保证提交责任始终保留，后续仍有可执行的恢复或业务处理路径。

**扫描与财务接口的实现边界。**

MySQL 分别按“待处理且已到下次处理时间”和“执行中且领取已到期”定位申请，配相应索引，分批领取。每份申请的领取和结果写回都用短事务，不把网络调用放进数据库事务里。扫描成本随当前待办和过期领取数量增长，不应随全部历史申请增长。批量大小和请求并发需要依据财务限流、响应耗时及审批高峰决定，目前没有实测容量或确定耗时结论。

财务接口需明确返回：已找到及受理编号、未找到、处理中，以及能够确定的业务拒绝；超时等技术错误单独处理。重复请求返回同一编号的保证应覆盖申请的完整有效期，而不是只在短时间缓存内成立；同一编号携带不同内容时应明确报冲突。我们始终使用同一申请编号恢复原操作，执行标识只服务本地领取，不作为新的财务业务编号。

按这个设计，无论实例在调用前、调用中，还是财务成功后宕机，本地都不会丢掉未完成的提交责任；恢复可以重复查询和提交同一申请，财务用唯一约束保证这些尝试只对应一次入账。
