已确认，下面整理为可独立阅读的技术设计定稿。财务承诺的接口能力上线后，按此方案实施；本轮不编写业务代码。

**员工报销审批后自动提交财务：技术设计**

**目标与前提**

报销申请审批通过后，系统自动向财务提交。提交遇到超时、实例宕机等情况时能够恢复，同一申请在财务只入账一次。

现有 Go 服务有 4 个实例，共用一个 MySQL；每天约 2000 单，每分钟扫描一次，不新增消息队列。申请已有全局唯一编号。

上线依赖财务提供以下能力：

- 按我方申请编号，在入账事务中保证唯一性；包括并发提交在内，同一申请只能入账一次。
- 重复提交同一申请，返回同一个受理编号。
- 支持按申请编号查询已有结果。

这些保证需要覆盖申请的完整处理和恢复周期，不能只依赖短期去重缓存。重复编号对应不同报销内容时，财务应返回明确冲突，不能生成第二份单据。

目前没有源码验证，下面定义需要实现的行为，不代表现有审批入口已经具备相应事务处理。

**整体机制**

MySQL 持续保存尚未完成的财务提交责任。实例竞争领取申请，领取后先查询财务；已有结果则保存结果，未找到则用原申请编号和固定内容提交。

本地完成点是：**受理编号和“财务已受理”状态已经一起提交到 MySQL。** 在此之前，申请始终保留为未完成事项，不能因为发生过调用或超过重试次数就丢弃。

本地领取用于减少实例之间的重复执行，并防止旧执行覆盖新结果。领取到期不代表外部请求已经停止；跨实例、跨重试的重复入账风险，由财务的唯一约束解决。

**模型与数据归属**

沿用原报销申请，在申请记录上补充财务提交信息，不引入独立任务平台。审批状态继续表达是否获准报销；财务提交进度表达这份申请是否已经交付财务，两者分开维护。

| 信息 | 业务含义与维护方式 |
| --- | --- |
| 申请编号 | 原有全局唯一编号。所有查询、首次提交和重试均使用它，重试不生成新的财务业务编号。 |
| 固定提交内容 | 审批通过时保存财务接口需要的内容。仅保存提交所需数据，后续重试直接复用，避免关联资料变化导致同一编号提交不同内容。 |
| 财务提交进度 | 待处理、执行中、已受理、需处理。审批通过时登记，领取和结果处理时更新。 |
| 财务受理编号 | 财务返回的结果凭据，与“已受理”在同一次本地更新中保存。 |
| 执行标识 | 每次成功领取生成的新标识，区分前后两次执行。后续状态写回必须匹配它。 |
| 领取到期时间 | 表示本次处理权何时允许被接手，解决实例领取后宕机的问题。 |
| 下次处理时间 | 决定待处理申请何时再次参加扫描，避免持续故障时过于频繁地调用财务。 |
| 最近一次错误 | 记录最近的技术错误或业务拒绝，便于解释未完成原因。 |

各进度的准确含义如下：

- **待处理**：本地尚无确定的受理结果，包括首次等待提交、超时后等待确认。不能据此断言财务尚未入账。
- **执行中**：某个实例暂时拥有处理权。接口可能尚未调用，也可能已经成功。
- **已受理**：本地已保存受理编号，自动提交流程完成。
- **需处理**：财务明确拒绝了这份申请，需要处理业务问题。它仍是未完成事项，但不自动重复发送相同的无效内容。

用户界面分别展示审批状态和财务提交进度。拿到受理编号只展示“财务已受理”；是否可以展示“已入账”，取决于财务结果的明确语义，不能自行等同。

**审批与提交登记**

审批通过时，服务在同一个 MySQL 事务中完成三件事：保存审批通过、保存固定提交内容、登记财务待处理及首次处理时间。

事务成功后，这份申请同时成为已审批申请和财务待办；事务失败则全部回滚。重复处理审批通过事件时，不覆盖已有提交内容和财务进度，尤其不能把已受理申请重新改回待处理。数据库更新应检查原审批和提交状态，确保登记只发生一次。

扫描不提交尚未审批通过的申请。向财务重试时，也不直接修改已审批内容；明确的业务拒绝交由已有业务处理流程接续，自动提交功能不提供绕过审批修改报销内容的能力。

**领取和调用过程**

每个实例每分钟扫描两类记录：到了下次处理时间的待处理申请，以及领取已经到期的执行中申请。按处理时间和申请编号稳定排序，分批处理。

扫描结果只是候选项。实例必须通过带条件的数据库更新领取：待处理申请仍符合处理条件，或者执行中的申请仍然到期，才能写入新的执行标识、领取到期时间和“执行中”。只有更新成功的实例继续执行；竞争失败的实例跳过该申请。

领取事务结束后才调用财务，不在等待网络响应时持有数据库事务或行锁。一次领取后的执行顺序为：

1. 按申请编号查询财务。
2. 若取得受理编号，直接进入本地完成写回。
3. 若财务明确返回未找到，则用原申请编号和固定内容提交。
4. 若查询表示仍在处理，或查询出现技术错误，则安排后续查询，本轮结束。
5. 提交取得受理编号后，进入本地完成写回；技术错误安排后续处理；明确业务拒绝记录为需处理。

任何结果写回都必须满足“申请仍处于执行中，执行标识仍是本次领取”。成功完成时，将受理编号和已受理状态一起保存；需要后续处理时，改回待处理并设置下次处理时间；两种情况都清除本次领取信息。

写回影响零条记录，表示本次执行已经失去处理权或记录已经完成。旧执行停止，不覆盖当前记录。即使旧执行拿到了真实受理编号，新的领取者也能通过财务查询重新取得，不需要允许旧执行越过条件写入。

**超时与宕机恢复**

以申请 A 为例：实例 1 领取后提交，财务已经入账并生成受理编号 F，实例 1 在保存 F 前宕机。

MySQL 中的 A 仍然是执行中。领取到期后，实例 2 通过条件更新接手，写入新的执行标识，再按 A 查询财务，取回 F，最后保存 F 和已受理。整个恢复过程不要求人工判断原调用是否成功，也不会新建第二份报销单。

如果实例 1 没有宕机，只是暂停后恢复，它的旧执行标识已经失效，不能覆盖实例 2 的结果。如果两个实例的外部请求发生重叠，财务仍须让相同申请编号只产生一次入账。

查询暂时未找到，也不意味着原请求绝对没有成功。但现在再次提交仍然安全：无论是查询延迟，还是原请求尚在执行，财务的唯一约束都应把同一申请的请求归到同一笔业务上。

其他中断位置按同一规则恢复：

| 中断位置 | 留下的情况 | 后续处理 |
| --- | --- | --- |
| 审批与待办登记事务未提交 | 两项修改均未生效 | 由正常审批处理继续，不产生半份待办 |
| 已领取，尚未调用财务 | 本地执行中，财务可能没有记录 | 领取到期后接手，查询未找到则提交 |
| 提交超时 | 财务可能成功，也可能未收到 | 安排后续查询，必要时按原编号提交 |
| 财务成功，本地结果未保存 | 财务有结果，本地未完成 | 查询取回受理编号并保存 |
| 本地完成更新返回超时 | 本地事务可能已经提交 | 后续先依据数据库实际状态；已受理则结束，否则继续确认财务结果 |

如果实例在错误发生后还能写 MySQL，就安排后续处理；如果连 MySQL 也无法写入，就让已有领取信息保留，数据库恢复后由到期扫描接手。

领取期限应大于一次正常查询、可能的提交和本地写回所需时间，并为客户端超时设置留出余量。实际数值按财务接口约定确定，不依赖期限设置来防止重复入账，也不需要为了本流程先增加持续续租机制。

**重试和业务拒绝**

技术错误使用延后重试，并在连续失败时逐步延长间隔、设置上限，避免财务故障时持续高频调用。无论重试多少次，都使用原申请编号和固定内容；不因次数耗尽而将未完成申请删除、标记成功或永久停止处理。

明确的业务校验错误进入需处理，保留错误原因和提交责任，不继续重复发送相同无效内容。业务问题解决后，恢复处理仍须从查询原申请结果开始，不能仅凭本地错误记录推断财务不存在原单。

“不漏单”在本系统中的可实现含义是：已审批申请的提交责任不会因进程中断或暂时错误丢失，且可以继续恢复。最终完成仍依赖财务恢复服务、接受合法申请，以及业务错误得到处理；系统不能保证一份始终被财务拒绝的申请最终入账。

**接口与规模考虑**

财务查询接口需要区分已取得结果、未找到、仍在处理和确定的业务拒绝；技术错误单独处理，不能把查询超时翻译成未找到。提交接口携带申请编号和固定内容，成功返回受理编号，重复请求返回原结果。

每次处理先查询，使首次提交多一次查询，但无需持久化区分“从未发送”和“曾经发送但结果未知”，所有恢复走同一条流程。一天约 2000 单时先采用这个选择；接口限流和集中审批高峰仍需在实施前核对。

MySQL 为待处理时间和领取到期时间对应的扫描条件建立索引，分批读取和条件领取，避免反复扫描全部历史申请。运行成本主要随当前待办量、到期领取量和重试量增长。网络请求并发受财务限流约束，单次批量不超过实例近期可处理的数量，避免领取大量记录后在本地排队至到期。

每分钟扫描决定正常情况下发现新待办的节奏，不构成一分钟内必定完成的承诺。确切批量、并发和耗时需要依据接口能力与实际负载确定，目前尚无性能实测结论。
