# 项目显示名称修改技术设计

本功能允许项目所有者修改项目的显示名称。修改只影响 `projects.display_name`，项目 ID 和所有者保持原样，不增加新表、字段或外部依赖。

## 已确认的规则与运行条件

- 内部后台每天使用几十次，由单个 Go 服务访问 MySQL。
- 只有项目所有者可以修改名称；项目不存在和当前用户不是所有者，统一返回“项目不可操作”。
- 名称去除首尾空白后，长度必须为 1–50 个 Unicode 字符。空名称和超长名称直接拒绝，不截断；不同项目允许重名。
- 请求提供项目 ID 和新名称，成功时返回本次修改后的名称。
- 同一项目允许并发修改，最后一次成功提交的修改生效，不引入版本号或冲突提示。
- 沿用现有数据库事务，不需要审计历史或软删除。

以下设计基于这些已确认条件，未核查项目源码。登录态读取、事务封装和错误响应格式在实施时沿用现有代码约定。

## 一次修改如何执行

1. 服务端从现有登录态取得当前用户 ID。未登录请求按现有认证规则拒绝；不从请求正文接收或信任所有者 ID。
2. 服务端去除新名称的首尾空白，然后校验长度。Go 中可使用 `strings.TrimSpace` 处理空白，按 `rune` 数量计数，避免将中文或其他多字节字符按字节计算。名称内部的空格保持原样。处理后不足 1 个或超过 50 个字符，返回名称校验错误，不执行更新。
3. 在现有数据库事务内更新项目，将项目 ID 和当前用户 ID 同时作为条件，即只修改 `id` 与请求项目 ID 相同、且 `owner_id` 与登录用户 ID 相同的记录。写入经过上述处理的名称。
4. 确认项目可操作、更新没有出错后，提交事务。只有事务提交成功，服务端才返回成功及本次写入的名称。若事务由外层管理，成功响应也必须等外层提交完成后再发送。
5. 前端收到成功响应后，用返回的名称更新显示。校验失败、项目不可操作、数据库更新或提交失败时，展示对应错误，不显示修改成功。

权限条件直接参与更新，使“检查是否属于当前用户”和“修改这条记录”由同一条更新语句约束，避免先在事务外查权限、再只按项目 ID 更新。

## 数据模型与接口职责

继续使用现有的项目记录：`id` 标识要修改的项目，`owner_id` 决定谁有权修改，`display_name` 保存当前展示给用户的名称。这三个字段已经覆盖本次操作需要的信息，没有需要单独维护的新对象或状态。

名称不承担项目身份标识的职责，因此改名不改变项目 ID，也不检查其他项目的名称。不为名称增加唯一性约束。

接口接收项目 ID 和新名称，认证信息由现有登录机制提供。成功结果返回去除首尾空白后、本次提交的名称；错误区分名称不合法、项目不可操作和数据库操作失败，其中“不存在”和“非所有者”使用同一种错误响应。

成功返回值表示本次请求成功提交的值。并发情况下，其他请求可能随后再次修改名称，因此不承诺响应到达客户端时，该值仍是数据库中的最新值。

## 相同名称的处理

用户可能将名称提交为原值，也可能输入了首尾空白，但处理后仍与原名称相同。这是合法操作，应返回成功和处理后的名称。

MySQL 更新结果中的“影响行数”可能表示实际发生变化的行数，因此不能直接把影响行数为 0 判断为“项目不可操作”。实现采用以下处理，避免依赖连接是否配置为返回匹配行数：

- 更新影响行数为 1 时，继续提交事务。
- 更新影响行数为 0 时，在同一事务内，仍以项目 ID 和当前用户 ID 为条件，使用 `SELECT … FOR UPDATE` 查询是否存在可操作记录。若存在，说明这次更新没有造成实际变化，按合法操作继续提交；若不存在，统一返回“项目不可操作”。
- 更新或查询发生数据库错误时，回滚并返回失败。

这里使用锁定读取，是为了读取当前记录并维持本次事务内的判断，避免依赖可能较早建立的普通查询快照。查询只确认是否存在，不需要增加版本号或保存旧名称。

## 并发与失败过程

假设原名称为“甲”，两个所有者请求分别要改成“乙”和“丙”。两次更新都修改同一条项目记录，MySQL 的事务行锁会使它们依次完成：先获得锁的请求完成更新并提交，另一个请求再继续写入。如果后提交成功的是“丙”，最终名称就是“丙”。

这里以数据库成功提交的先后为准，不按请求到达服务端或响应到达前端的顺序判断。事务期间的改名不会作为成功结果提前暴露；现有普通读取应使用不会读取未提交数据的事务隔离设置。

如果后一个请求更新失败并回滚，前一个请求已提交的名称仍然有效。如果单次请求执行更新后、提交前失败，该请求不返回成功，由现有事务机制回滚未提交修改。

如果数据库已经提交，但响应在返回途中丢失，客户端可能不知道修改已成功。此时客户端不显示成功，可以重新读取项目确认当前名称，不增加请求记录或补偿流程。

重复提交同一名称通常只会得到相同结果。不过，如果第一次请求已经成功，另一个请求随后改了名称，此时再次提交旧请求的名称会构成一次新的修改，并可能覆盖后来的值。这符合已接受的“最后一次成功提交生效”规则；客户端不在结果不明时自动反复提交旧名称。

## 访问成本与实施边界

每次有效请求只更新一个项目，通常执行一次更新；影响行数为 0 时，多一次针对同一项目的存在性查询。不扫描其他项目、不检查名称重复，也不处理任何关联记录。

按项目 ID 已具备主键或唯一索引这一常规前提，查找成本由单个项目定位承担；不同项目的修改不会因本功能主动争用同一把应用锁。同一项目的并发修改由数据库行锁串行处理，事务内只保留必要的数据库操作，及时提交。

每天几十次的使用规模没有引入缓存、队列或额外并发控制的必要。这是基于操作范围的设计判断，尚未进行性能实测，不承诺具体耗时。

实施时确认现有项目 ID 索引、事务表引擎、隔离设置，以及名称列和连接的字符集能够完整保存所允许的 Unicode 字符，通常应使用 `utf8mb4`，并确保列容量至少覆盖 50 个字符。这些属于现有数据库配置核对；若不满足，应修正对应配置或列定义，防止服务端校验通过后发生存储失败或截断。

关键机制、模型和业务取舍均已确认，可以据此进入实现，无需继续增加设计决策。
