按已确认的范围，这个功能可以直接整理为下面的技术设计，无需再引入业务模型或新增表字段。本轮只确定设计，不写代码。

接口采用 `PATCH /projects/{id}/display-name`，请求体为 `{"display_name":"新名称"}`，成功返回 `200` 和 `{"display_name":"去除首尾空白后的名称"}`。登录用户 ID 从服务端已有登录上下文取得，请求不能指定项目所有者。

服务端按以下顺序处理：

1. 解析项目 ID 和请求体。对名称使用 Go 的 `strings.TrimSpace` 去除首尾空白，再用 `utf8.RuneCountInString` 按 Unicode 码点计数，允许 1–50 个字符。缺少名称、空值、非字符串、处理后为空或超过上限，都返回参数错误；不截断名称，不修改中间空白，也不检查名称唯一性。
2. 在现有数据库事务中，按项目 ID 和登录用户 ID 查询项目，并使用 `FOR UPDATE` 锁定该行。查不到时统一返回“项目不存在或不可操作”，不区分不存在与非所有者。
3. 使用参数化 SQL 更新 `display_name`，更新条件仍同时包含 `id` 和 `owner_id`。事务成功提交后，返回校验后的名称；查询、更新或提交失败，都走错误响应。

对应 SQL 如下，参数由数据库驱动绑定：

```sql
SELECT id
FROM projects
WHERE id = ? AND owner_id = ?
FOR UPDATE;

UPDATE projects
SET display_name = ?
WHERE id = ? AND owner_id = ?;
```

这里先查询并锁定项目，是为了可靠区分“没有可操作的项目”和“提交的名称与原名称相同”。MySQL 的更新受影响行数可能在名称未变化时为 0，因此不能直接把 0 当作权限或存在性失败。项目已在当前事务中确认并锁定后，同名提交正常返回成功，不依赖修改数据库连接配置。

同一项目的并发修改由数据库行锁串行完成，后一次成功提交的更新覆盖前一次，符合已接受的并发规则。整个过程沿用现有事务，不增加嵌套事务或应用层锁。如果事务由外层统一提交，成功响应也必须在外层确认提交成功之后发送。

错误响应沿用项目已有格式，状态语义确定为：未登录返回 `401`；请求格式或名称不合法返回 `400`；项目不存在或非所有者统一返回 `404` 和相同错误信息；数据库操作或提交失败返回 `500`，不向客户端暴露数据库细节。界面只在接口成功后显示返回的名称和成功提示，失败时保留原显示名称。

实现完成后的验证围绕实际边界展开：所有者修改成功且数据库持久化正确；首尾空白被去除，中间空白保留；中文、英文和 emoji 按码点计数，1 与 50 个字符通过、51 个拒绝；缺失、空值和纯空白名称拒绝；其他项目重名允许；不存在与非所有者响应一致且不改数据；同名提交成功；并发提交符合后提交覆盖规则；更新或事务提交失败时没有成功响应。

改动范围就是现有接口处理、名称校验和项目数据访问逻辑，以及对应验证。不需要数据库迁移、审计记录、版本字段或额外组件。现有信息已足够进入实现。
