技术设计按这个方案收敛，暂不写代码。下面整理已确认的实现约定；字段和接口名称由我确定。

**数据模型**

自有文件继续使用现有文件树，删除期间保留所有者、父目录和类型。现有文件状态增加回收站状态，并增加 `trash_batch_id`，指向本次删除所属的批次。

新增 `trash_batches`，表示一次可整体恢复的删除：

| 字段 | 含义 |
|---|---|
| `id` | 删除批次 ID，也是恢复操作的目标 |
| `owner_id` | 文件所有者 |
| `root_file_id` | 本次删除的根文件或根文件夹 |
| `deleted_at` | 本次删除时间，使用数据库时间 |
| `restored_at` | 恢复成功时间，未恢复时为空 |

文件表按 `owner_id, parent_id` 查询子树，按 `trash_batch_id` 查询恢复成员；批次表支持按所有者查询回收站、按删除时间筛选清理候选。

共享入口继续独立存储，以入口自身的 `entry_id` 标识，增加 `removed_at` 表示该入口被接收者移除。原分享关系和权限仍由现有权限模型管理，不写入删除批次，也不保存恢复用的权限副本。

批次不会因为恢复而立即删除：保留 `restored_at` 可以识别重复恢复请求。如果文件恢复后再次删除，会创建新批次；旧批次的重试请求不能影响新批次。

**接口及操作单位**

| 接口 | 操作含义 |
|---|---|
| `POST /files/{file_id}/trash` | 删除自有文件或文件夹，成功返回 `trash_batch_id` |
| `GET /trash` | 查询所有者的删除批次，每个批次展示一项 |
| `POST /trash/{batch_id}/restore` | 整体恢复该批次 |
| `DELETE /shared-entries/{entry_id}` | 仅移除接收者指定的共享入口 |
| `POST /files/{file_id}/download-link` | 检查状态和当前权限后签发链接 |

通过共享入口签发链接时，请求携带 `entry_id`，服务端核实它确实指向目标文件，并检查该入口及对应访问权限。入口 ID 只是定位信息，不能代替鉴权。

随文件夹一起删除的子文件不能单独调用恢复；此前单独删除的子文件保留自己的批次，可以按自己的期限处理。接收者对共享文件夹子文件的删除请求、把共享入口移入普通文件夹的请求，都在服务端拒绝。

**事务和锁的统一规则**

每个文件所有者预先有一条固定的锁记录。事务统一使用主库和 `READ COMMITTED`，并先取得所有者锁，再读取和修改受保护的数据。

| 操作 | 所有者锁 | 锁内完成的工作 |
|---|---|---|
| 创建、移动、删除、恢复自有文件 | 排他锁 | 检查当前树和节点状态，完成树或删除状态修改并提交 |
| 签发下载链接 | 共享锁 | 检查目标状态、入口和当前权限，完成链接生成 |

已有所有者必须先补齐锁记录，避免对不存在的记录加锁却误以为已建立互斥。所有相关操作入口都必须接入；普通文件列表读取无需取得这把写锁。

删除事务在锁内重新确定子树，只把本次仍正常的节点加入新批次。1 万个节点可以分块更新，但只能整体提交；失败则全部回滚。分享用户数量不参与这次更新。

恢复事务在锁内检查所有权、批次是否已恢复、是否仍在恢复期限内，以及恢复位置是否有效，然后整体恢复该批次的节点并写入 `restored_at`。不修改此前其他批次，也不修改分享权限或共享入口。

重复删除已在回收站的对象，不创建新批次、不刷新删除时间；重复恢复已完成的批次返回已恢复结果。涉及过期、位置冲突等失败时，事务不应部分恢复。

**链接生效边界**

删除提交成功后才返回成功。签发必须在共享锁内完成实际链接生成，因此删除与签发有确定的先后关系：先完成签发的链接按原有效期继续使用；删除先提交的，后续签发检查到删除状态后拒绝。

“已经签发”以服务端完成生成的时间为准，最长有效期为 10 分钟。网络延迟导致客户端稍后收到，不改变这一归属。生成失败、事务结束失败时不向客户端返回链接，重试必须重新取得锁并检查状态。

所有签发入口都执行这套检查，包括重新获取链接的请求。不能把缓存中的旧状态作为签发依据，也不能在锁外重新生成或延长链接。

恢复后，文件服务仍检查当前权限：删除期间撤销的分享继续失效，仍有效的分享可以使用；接收者自行移除的入口保持移除状态。同一用户通过另一份有效分享访问的能力不受误伤。

**期限和后台清理**

恢复资格按 `deleted_at + 30 天` 判断，到达边界即不可恢复；物理清理只能在 `deleted_at + 90 天` 后开始。时间判断使用数据库时间，避免多个实例时钟差异。是否过期直接由时间计算，不依赖定时任务是否已经运行。

清理任务运行在现有 Go 服务中，用 MySQL 协调任务领取，并保留失败后可重试的清理进度。清理前重新核实批次未恢复且已满 90 天。物理删除在数据库事务外执行，成功后再完成相关元数据清理；重复删除已经不存在的内容应能安全重试。

涉及大量分享关系的失效元数据可以后台分批整理，不进入用户删除请求的事务。如果现有存储存在物理内容复用，物理删除还必须遵守其引用规则；目前没有这部分存储事实，不能直接按逻辑文件 ID 推断内容可删。

**实现验收重点**

- 两个 Go 实例之间，删除与创建、移入、移出、恢复竞争时，删除范围没有漏标或误标。
- 签发先于删除时允许旧链接继续使用；删除先提交时，等待中的签发和新请求都被拒绝。
- 先删子文件、再删父文件夹，恢复父文件夹后，先前删除的子文件仍在原批次。
- 删除期间撤销一份分享，恢复后该分享仍无效，其他有效分享正常工作。
- 同一用户的多个共享入口可以独立移除，不误删其他入口或原分享关系。
- 30 天和 90 天边界、事务回滚、提交后响应丢失，以及物理清理中断后的重试符合上述约定。
- 用 1 万节点验证事务耗时、锁等待和失败情况；同时施加共享用户签发压力，确认同一所有者的等待时间可接受。目前还没有实测结果，不能承诺具体延迟。
