已有信息足够形成技术设计，无需再补充业务决策。实现范围限定在现有 Go 服务的项目名称修改接口，复用 `projects` 表和现有事务。

接口采用 `PATCH /projects/{project_id}/display-name`，请求体为 `{"display_name":"新名称"}`，成功返回 `200` 和 `{"display_name":"处理后的名称"}`。登录用户 ID 从服务端认证上下文获取，不接受客户端指定所有者。

处理流程如下：

1. 读取项目 ID 和请求体，检查参数格式。名称字段缺失、为 `null` 或不是字符串，均按参数错误处理。
2. 使用 `strings.TrimSpace` 去除名称首尾空白，再按 Go `rune` 计数，接受 1–50 个 Unicode 字符。长度不按 UTF-8 字节数计算；名称内部空白保留，不做额外格式转换。
3. 在现有事务内，按 `id = 项目 ID AND owner_id = 登录用户 ID` 查询项目并锁定该记录。未找到时，统一返回“项目不可操作”。随后仍以这两个条件更新 `display_name`，写入处理后的名称。
4. 由现有事务统一提交，提交成功后返回写入的名称。查询、更新或提交失败时返回失败，不能提前返回成功。

事务内的资格查询使用 `SELECT … FOR UPDATE`。它既让资格检查与后续更新保持一致，也避免直接依赖 MySQL 的影响行数判断项目是否可操作：提交与当前名称相同的名称时，MySQL 可能报告修改了 0 行，但这仍是成功请求。已找到并锁定合法记录后，更新无错误即可继续提交，不把 0 行变更当作权限错误。不新增嵌套事务。

并发更新由数据库行锁串行处理。后续成功提交的修改覆盖前面的修改，不增加版本检查、冲突提示或自动重试流程。成功响应表示本次事务已经提交；其他请求随后仍可能再次修改该名称。

错误响应沿用服务现有格式，语义与 HTTP 状态约定如下：

| 情况 | 状态 | 对外结果 |
|---|---|---|
| 未登录或登录态无效 | `401` | 请先登录 |
| 项目 ID、请求体或名称不合法 | `400` | 参数错误；名称错误说明长度要求 |
| 项目不存在或当前用户不是所有者 | `404` | 项目不可操作，两者使用相同错误码和文案 |
| 数据库查询、更新或事务提交失败 | `500` | 修改失败 |

前端仅在成功响应后更新页面上的名称，并使用响应中的值，以反映服务端去除首尾空白后的结果。请求失败时保留原显示名称，提示失败；草稿可保留供用户继续编辑。

代码职责保持在现有分层中：接口层负责认证信息、参数解析和响应；业务层负责名称规则与流程；数据访问层负责条件查询和更新。表结构、索引和依赖不新增，也不为这个接口单独建立通用框架。

实现后的验证围绕以下行为展开：

- 名称去空白后为 1 或 50 个字符时成功，为 0 或 51 个字符时拒绝；覆盖中文和 emoji，确认按字符数判断。
- 所有者修改成功，并返回处理后的名称；同名重复提交也成功。
- 非所有者和不存在的项目返回相同结果，且不改动其他项目。
- 不同项目可以使用相同名称。
- 更新失败或事务回滚时名称不变；提交失败时不返回成功。
- 使用真实 MySQL 事务验证两个并发修改，确认后续成功提交的名称成为最终值。

这份设计基于已确认的项目条件整理；本轮未查阅源码、实现代码或运行验证。
