这个补充改变了我们要保证的边界：**已经签发的链接可以继续用到到期；删除成功后，文件服务不能再为这些文件签发新链接。** 因此，我们需要把“检查文件是否可用”和“生成下载链接”作为一个受保护的过程。只在签发前查一次状态，然后任由删除与签发同时进行，会留下空隙。

下面按整棵子树事务的方案展开。为把多实例之间的配合说具体，我先提出一个简单的协调方式：**同一所有者的目录树修改依次进行；下载链接可以同时签发，但不能与该所有者的目录树修改交叉执行。** 这个方式会让同一所有者下互不相关的目录操作也相互等待，属于需要你确认的取舍。

先解释两个需要保存的东西。

一个是“这一次删除”。例如今天删除 A 文件夹，A 和里面本次被删除的文件属于同一次操作。我们要记住这次操作的所有者、根节点 A、删除时间，以及哪些节点属于它。以后点击恢复 A，就能找到这次删除的整组节点。昨天已经单独删除的 B 属于昨天的操作，不会被归进今天这一组。这份记录可以叫“删除记录”，节点上保存对应的删除记录编号。

另一个是让多个服务实例排队的一条数据库记录。每个所有者对应一条，内容本身不代表文件状态；它只是让各实例对同一个所有者使用同一把 MySQL 行锁。可以叫“所有者协调记录”。删除、恢复、移动、创建节点以及修改分享权限时，对它取得排他锁；签发链接时取得共享锁。共享锁之间可以并存，排他锁则必须等其他持锁者结束。同一协议必须由所有相关入口遵守，否则这条记录没有保护作用。

删除 A 的过程如下。

1. **收到请求，确认操作的是原文件夹。** 请求提供 A 的标识和操作者身份。服务先找到它的所有者；如果用户点的是接收者界面里的共享入口，就走移除那个入口的逻辑，不能转成删除原文件夹。对原文件夹的归属还要在下面的事务里重新核实。

2. **开始 MySQL 事务，锁住所有者协调记录。** 这个实例取得排他锁后，同一所有者的其他目录树修改、权限修改和新链接签发会等待。如果其他实例已经开始签发链接，本次删除要等它完成签发并释放共享锁后，才能继续。

   这也解释了为什么不能只在 Go 代码里加一把锁：另一个实例不会受它约束，而 MySQL 的这条记录是所有实例共同使用的。

3. **重新检查 A，再沿父子关系找出整棵子树。** 持锁后检查 A 属于当前操作者，并且仍然可用。随后先读取 A 的直接子节点，再读取这些节点的子节点，直到没有下一层。查询使用所有者与父目录的索引；一层很多时可以拆成几条 SQL。所有查询都在同一个事务里，期间没有其他遵守协议的操作能往 A 里放文件、把文件移出去或恢复其中的节点，因此这次找到的范围不会中途改变。

   查询需要看见已删除的节点，不能因为 B 已经删除就直接跳过整个分支；但“找到它”和“把它归入本次删除”是两件事。

4. **保存这次删除，并修改本次仍然可用的节点。** 建立一条删除记录，使用数据库时间记录本次删除时间。A 和本次仍可用的后代都关联到它，文件状态变为已删除。B 以及属于 B 原有删除操作的节点保留原来的删除归属和时间。

   这些更新可以拆成多条 SQL，但中间不提交。例如写完一部分时，事务还没有完成，服务不能把这部分当成已经对用户生效的结果。分几条 SQL 是控制单条语句大小，不是分几次完成删除。

   文件之间的父子关系、对象存储里的内容、分享权限和接收者的共享入口均不需要在此时修改。对 10 万个共享用户逐一撤销分享，既违背保留分享的规则，也不是实现禁用访问的必要步骤。

5. **提交事务，然后返回删除成功。** 提交使这组删除状态一起生效，同时释放所有者协调锁。此前等待的新链接请求随后取得共享锁，读到目标文件已删除，返回文件不可用，不生成链接。

   事务执行到一半出错就回滚，本次删除记录和节点改动一起撤销，不留下只删除一半的目录。如果提交成功但返回结果前连接断了，客户端会暂时不知道结果；删除请求应携带可复用的请求编号，并与删除记录一起提交，重试时查回这次操作的结果，避免把重试误当作一次新删除。

链接签发也需要作相应的小范围调整，否则上面的保证不成立。具体顺序是：

1. 确定目标文件的所有者，开始一个使用 `READ COMMITTED` 的短事务，对该所有者协调记录取得共享锁。
2. **取得锁以后**，读取文件状态和当前访问权限；不能拿等待锁之前查到的结果继续判断。文件已删除或没有有效权限就拒绝。
3. 检查通过后，在仍然持锁期间完成预签名链接的生成，再结束事务、释放锁，并把链接返回给调用方。不能先释放锁，再生成链接。

这样，删除和签发的先后就能说清楚：若签发先取得共享锁，它先完成链接生成，删除等它结束后才能提交；这个链接属于删除成功前已签发的链接，可以继续使用。若删除先取得排他锁，签发等待删除提交后检查状态，就会被拒绝。这里以链接生成完成为签发时点，网络传输可能使一个此前已生成的链接稍晚才到达客户端。

预签名通常可以在服务内生成；这里需要核实现有实现是否还要等待外部调用。如果需要，外部等待也会延长持锁时间，不能把它忽略成一次无成本的本地操作。

再推演恢复和撤销分享。假设删除之前，A 内的文件 C 有一份给张三的分享、一份给李四的分享，B 则在昨天就已经单独删除。以下先按 A 的原父目录仍可用、恢复位置没有重名冲突来说明。

1. 删除 A 后，C 的两份分享关系都还在，但 C 已删除，因此两人都不能再获取它的新下载链接。
2. 原主人撤销给李四的那份分享。这个请求也取得所有者协调记录的排他锁，修改对应的权限记录并提交。它不改变 C 的删除记录，也不删除张三的分享或把多个共享入口混为一条记录。
3. 原主人在 30 天内请求恢复 A。服务取得同一把排他锁，找到 A 对应的删除记录，检查所有者、恢复期限及原父目录是否可用。恢复单位是这条删除记录代表的整组节点，不能从中挑一个子文件单独恢复。
4. 服务只把**当前仍归属于这次删除**的节点恢复为可用，并在同一个事务中提交。B 仍归属于昨天的删除记录，保持已删除，原删除时间也保留。恢复不读取旧权限快照，更不会把旧分享权限写回去。
5. 恢复提交后，张三请求 C 的新链接：文件可用，张三当前的权限有效，可以签发。李四通过被撤销的那份分享请求：文件虽然可用，但对应权限已经无效，因此拒绝。如果李四另有一份独立有效授权，则可以依据那份授权访问；这不代表被撤销的分享复活了。

撤销与恢复即使同时发生，也会在这条协调记录上排出先后顺序。恢复只改变文件可用性，撤销只改变当前权限，后执行的恢复不会覆盖前面已经提交的撤销。一个用户拥有多个共享入口，也不能被直接解释为拥有多份独立授权；入口与实际授权仍按现有关系分别处理。

这套机制的主要成本在于：删除 1 万个节点时，要读取子树、修改本次有效节点，并把这些写入保留到一次提交。它不随共享用户数直接扩大写入量，但同一所有者的其他修改和新链接签发会在此期间等待。目录深度影响查询轮数，节点数影响读写量，实际事务耗时需要测量；不能据此承诺具体响应时间。

**你是否接受先采用这种按所有者协调的方式，允许删除大目录时短暂阻塞该所有者其他目录的修改和新链接签发？** 这是当前方案最主要的代价。接受后，我们再把原父目录不可用、恢复位置重名，以及 30 天恢复期限与 90 天物理清理之间的配合补齐；这些场景不能靠悄悄换位置或覆盖现有文件来处理。
