方案已确认，下面整理为可以独立阅读的技术设计。实现基于现有 Go 单体、多实例和共享 MySQL 8，不增加中间件。

**回收站保留文件树，用删除记录控制访问；原分享权限始终独立维护。** 删除文件夹时只记录这次直接删除的文件夹，访问时检查目标及其祖先。删除和恢复不遍历修改整棵子树，也不向共享用户逐个传播状态。

恢复期为 30 天，物理内容保留至少 90 天。删除成功、撤销分享成功以后，不能再凭已经失效的状态或权限签发新下载链接；此前已经签发的预签名链接允许继续使用到原到期时间，最长 10 分钟。

**核心信息及其含义**

现有文件节点仍然表示原文件或文件夹，保留所有者、父目录和类型。进入回收站不会把它移到另一棵目录树，否则通过文件 ID 访问时就难以判断它原本处于哪个已删除文件夹内。

在节点上增加 `deleted_at`，表示用户直接删除这个节点的时间。空值表示节点自身没有被直接删除，但它仍可能因祖先被删除而不可访问。例如删除 A 后，其下 C 的 `deleted_at` 可以为空；访问 C 时沿父目录遇到 A，就知道 C 当前不能访问。

这一区别也是整体恢复的依据：B 昨天单独删除，今天再删除它的父文件夹 A，两者各有自己的删除时间。恢复 A 只清除 A 的记录，不清除 B 的记录。因此不需要给本次删除覆盖的每一个子文件增加一份状态，也不需要保存整棵树的恢复快照。

原有分享授权继续回答“谁当前可以访问原文件”。接收者的共享入口回答“这个用户从哪个入口找到原文件”。入口必须有独立 ID；同一个用户指向同一个原文件的多个入口是不同记录。删除一个入口按入口 ID 和接收者身份定位，只移除这一条记录，不修改原文件、授权或其他入口。

接收者不能把共享入口移进自己的普通文件夹，也不能通过共享文件夹执行子文件删除。这些限制在服务端判断，不能仅依赖界面隐藏按钮。原文件删除必须校验原主人身份。

为协调多个实例，为每个所有者维护一条稳定的 `owner_tree_guard` 记录，唯一键为所有者 ID。它没有业务状态，只提供共同的 MySQL 行锁位置；由账号或文件空间初始化流程保证存在。这条记录的存在理由是：防止下载已经检查通过，但目录状态或分享权限在签名之前发生变化。

**所有实例遵守同一套操作顺序**

签发链接取得所有者协调记录的共享锁。多个签发请求可以并行；删除、恢复、移动、新建以及原文件授权修改取得该记录的排他锁。这些修改在同一所有者范围内依次执行，并与签发过程互相等待。

取得协调锁以后，才读取和判断当前目录、删除状态及权限。涉及这些判断的查询使用当前读取，例如 `SELECT ... FOR SHARE` 等锁定读取，不沿用旧事务快照；状态缓存不能代替这次读取。统一先取协调锁，再读写节点和权限，避免不同接口采用相反顺序。

所有会改变这些判断依据的路径都必须接入，包括后台任务和管理接口。若现有授权还依赖其他可变数据，授权变更路径也必须提供同样的顺序保证；不能只协调某一张直接分享表，却允许其他授权来源在检查与签发之间失效。

这一选择的明确代价是：同一所有者在不同目录的修改也会互相等待。先使用这个简单范围，不引入子树锁、锁升级等额外机制。若单个所有者的并发成为瓶颈，再依据实际等待情况重评。

**删除目录的完整过程**

以删除 A 为例，A 下有 1 万个节点，分享涉及 10 万个用户：

1. 服务解析目标，确认操作针对原文件节点而非接收者的共享入口，并取得所有者身份。这里的读取用于定位，最终判断仍在锁内完成。
2. 开启事务，取得该所有者的排他锁。已经持有共享锁的签发请求先完成；删除请求等待期间不能返回成功。
3. 在锁内重新检查所有者身份、目标状态及祖先状态。目标已被直接删除时，可以返回其原有删除结果，不能重写删除时间；若目标只是被已删除祖先覆盖，则拒绝把这次请求转成一次新的独立删除。
4. 用数据库时间给 A 写入 `deleted_at`。父子关系、所有子节点自身的删除记录、分享授权和共享入口都保持原样。不调用对象存储删除内容。
5. 提交事务，随后返回删除成功。事务失败则没有成功结果；响应丢失后的重试通过原删除记录确认结果。

从提交开始，后续请求读取 A 的当前记录就会发现它被删除。没有后台逐个封禁子文件的阶段，也没有部分共享用户已经失效、另一部分尚未失效的传播窗口。

移动和新建同样先取得所有者的排他锁，再检查源节点及目标父目录是否可用。已删除目录内不能继续新建、移动或改写文件，也不能通过把子文件移出目录来绕过整体恢复。若这些操作先完成，删除看到的是完成后的树；若删除先完成，随后操作会因目录不可用而被拒绝。

**访问与签发下载链接的完整过程**

共享入口先解析到原文件。无论请求来自共享入口、所有者目录还是直接使用文件 ID，都走同一条原文件访问链：

1. 开启事务，取得原文件所有者的共享锁。
2. 读取目标文件，沿父目录检查到所属文件树的根。目标或任一祖先存在 `deleted_at`，就拒绝访问。若父链断裂、所有者不符或出现循环，也不能按“未发现删除标记”放行，应作为数据异常处理。
3. 路径可用后，检查请求人的当前权限。不能把共享入口存在当成有效授权，也不能使用删除时保存的权限快照。
4. 检查通过后，在共享锁仍然持有期间完成预签名链接生成。签名失败则不返回可用链接；成功后结束事务，再把链接返回调用方。

因此签发和删除有明确顺序：签发先持锁，就在删除能够提交之前完成签名；删除先持锁，后续签发就会读到已删除状态。签名完成与网络响应送达是不同时间，删除成功后才收到一个先前已签出的链接，仍属于已接受的旧链接边界。

下载开始后由对象存储验证预签名链接。此时不会再查 MySQL，数据库状态变化不能让旧链接提前失效。目录列表、预览和其他由文件服务提供的内容访问，也必须执行目标及祖先状态检查；任何能生成内容访问凭据的入口都必须接入签发协调。

**恢复目录与分享撤销的完整过程**

恢复针对节点自身的删除记录执行。只有被已删除祖先覆盖、自己没有删除记录的子节点，不能单独恢复；应恢复覆盖它的文件夹。

1. 校验原主人身份，开启事务并取得所有者排他锁。
2. 读取当前删除记录，按数据库时间判断是否仍在 30 天内。达到 30 天就拒绝恢复，即使物理内容尚未清理。
3. 检查原父目录及其祖先可用，并满足正常目录操作的名称约束。父目录也在回收站时，需要先恢复父目录；不能通过本次操作把目标悄悄移到其他目录。存在名称冲突时不提交恢复，返回明确冲突，让调用方处理后重试。
4. 只清除目标节点的 `deleted_at`，提交后返回成功。已恢复目标的重复请求可以返回当前结果，但不能顺手恢复它的祖先或子节点。

这个流程沿用前面讨论的原位恢复，不额外引入自动改名或自动迁移目录的策略。名称是否可复用以及具体比较规则，应沿用现有正常文件操作规则；本次方案不修改它们。

假设 A 下的 B 先被单独删除，C 原本通过授权 G 分享给用户甲。A 删除以后，原主人撤销 G，再恢复 A：

- A 的删除标记被清除，正常子文件重新通过目录状态检查。
- B 自己的删除标记仍在，仍然不可访问，也不会重新计算 B 的恢复期限。
- G 的撤销结果不变。用户甲通过任一入口访问 C 时，若没有其他独立有效授权，仍被拒绝签发链接。
- 其他用户依据各自当前有效的权限访问 C。

恢复和撤权都取得同一所有者的排他锁，所以并发时会按实际先后提交。撤权先提交，恢复不带回权限；恢复先提交，撤权之前可能签出的链接属于旧链接，撤权提交后不能再凭 G 签新链接。已经签出的链接继续遵守最长 10 分钟的到期边界。

恢复和删除都不读取或回写权限快照，因此不会覆盖恢复期间发生的合法授权修改。

**30 天与 90 天分别控制什么**

每个节点自己的 `deleted_at` 只记录它当前这一次独立删除。未满 30 天允许恢复；从第 30 天开始不再允许恢复；满 90 天才允许清理这次删除所覆盖的物理内容。

成功恢复会清除这次删除记录，取消它对应的清理资格。以后再次删除，使用新的删除时间。后台不能仅凭以前扫描到的“曾经删除过”就执行清理，必须重新核对当前记录。

父子节点的删除时间不互相覆盖。例如 B 比 A 早删除 20 天，B 达到 90 天时可以清理 B 自己覆盖的内容，即使 A 还没有达到 90 天，因为恢复 A 从来不会恢复 B。A 达到 90 天后，其余被 A 覆盖的内容才取得相应清理资格。

物理清理作为现有 Go 服务中的后台任务运行，MySQL 保存进度，不需要增加消息队列。它与用户删除请求分开，具体过程是：

1. 查找达到 90 天的当前删除记录。为选中目标取得所有者排他锁，重新核对删除时间及当前状态，排除扫描后已经恢复或重新删除的旧候选。
2. 沿保留的父子关系分批找到尚未清理的文件，读取其物理内容标识。超过恢复期限的已删除目录不能再恢复或修改，因此核验通过后，这批内容不会重新变成合法可访问内容。
3. 释放数据库事务，再调用存储层清理物理内容，避免把对象存储调用放在所有者排他锁内。一次只处理有界批次，不在一个长事务里处理 1 万个文件。
4. 存储层确认成功或内容已经不存在后，重新取得协调锁，在对应文件上记录 `content_purged_at`。它表示物理内容清理已完成，供重试和后续扫描跳过该文件；调用失败时不记录完成。

本次只要求清理物理内容，节点元数据、删除记录及分享记录保留，所以分批清理不会拆断祖先检查路径。以后是否压缩这些元数据，是另一个需求，不混入这次实现。

进程在对象删除之前中断，下一轮继续处理；对象已删除但数据库还没记录完成时中断，下一轮再次请求清理，存储层把“已经不存在”作为成功，再补记完成。多个实例偶尔选中同一文件，也按同一重复调用规则处理，无需为此新增任务租约系统。

这里对存储层有一个明确要求：清理某原文件的内容不能破坏其他仍有效文件的内容。如果现有系统为每个原文件保存独立对象，可以直接删除该对象；若有去重、版本共享或其他物理复用，必须通过相应的内容释放能力确认没有仍需保留的引用，不能直接按对象键删除。现有存储模型没有提供，这部分需要在接入物理清理前查证；本设计不假设物理对象一定独占，也不提前新增引用计数表。

物理内容标识也必须避免被后续无关文件复用，否则一次延迟重试可能误删新内容。这应作为存储清理接口的约束核实。

**接口职责与规模边界**

原文件删除和恢复接口按原文件 ID 定位，负责所有者校验、状态变化和事务提交。共享入口移除接口按入口 ID 定位，负责接收者校验并只移除该入口。分享修改接口负责当前授权，下载接口负责原文件路径与当前权限检查后签发链接。找不到目标、身份不符、处于已删除祖先内、恢复过期和名称冲突应返回可区分的业务结果，调用方不能根据一个笼统失败猜测是否已经成功。

查询方面，父目录关系需要索引以支持列出子节点和分批清理；所有者与删除时间需要索引以支持回收站查询及到期扫描。回收站以节点自身的删除记录为依据，不为一个文件夹的 1 万个普通子节点生成 1 万份独立回收条目。独立删除的 B 保留自己的记录，但在 A 仍被删除时不能单独恢复 B。

同步删除和恢复的工作量主要随祖先深度增加，不随整棵目录节点数或共享用户数增加。每次链接签发增加祖先路径检查；90 天后的物理清理才随文件数量及存储调用量增长。最需要验证的是目录深度、同一所有者的并发访问和修改量，以及签名是否包含较慢的远程调用。

这些是根据执行过程得到的成本判断，目前没有源码或性能实测依据，不能承诺 1 万节点删除的具体耗时。若要调整锁定范围或访问缓存，必须重新证明“状态检查到签名完成之间不会被删除或撤权穿过”这一点。
