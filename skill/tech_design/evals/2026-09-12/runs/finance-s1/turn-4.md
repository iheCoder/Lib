以下是收敛后的技术设计，以财务承诺的防重和查询能力正式上线为实施前提。

本次改造让审批通过的报销申请自动提交给财务。已有 Go 服务的四个实例共用 MySQL，每分钟扫描可处理的任务，不新增消息队列。一天约 2000 单作为当前已知业务量，不视为经过验证的峰值容量。

**整体机制是：本地可靠记录待办，多个实例协调处理，同一申请始终使用同一编号向财务确认，直到本地保存明确结果。** 网络调用可以发生多次；财务按申请编号约束实际入账，保证每张申请只入账一次。

财务接口需要兑现以下约定：

- 提交请求携带我方全局唯一申请编号。编号与财务单据及受理编号稳定对应，重复或并发提交不会产生第二次入账，并能返回同一受理编号。
- 防重约束与实际入账在同一个财务事务中保持一致，不能出现编号已占用却永久丢失业务结果，或者已经入账却丢失编号对应关系的情况。
- 支持按申请编号查询已有结果，并明确区分“尚未查到”“仍在处理”“已有受理结果”和终止性的业务拒绝，具体以财务实际提供的结果类型为准。
- 在申请仍可能被重试期间，保留防重记录和结果对应关系。同一编号提交不同财务内容时应明确拒绝，不能覆盖原单据或重新入账。

“尚未查到”不作为原请求已经失败的证据。即使查询有可见性延迟，或者原提交仍在执行，相同编号的再次提交也必须受到财务防重保护。

**核心数据由报销申请和一份对应的提交任务组成。** 报销申请负责员工报销内容与审批结论；提交任务负责把这份已批准的内容送达财务，并记录确认结果。申请编号直接作为任务的唯一业务标识，不为一次重试创建新任务或新申请编号。

任务需要保存的信息如下：

| 信息 | 含义与存在理由 |
| --- | --- |
| 申请编号 | 关联原申请，也是财务防重和查询使用的稳定编号；本地任务按此编号唯一 |
| 已批准的提交内容 | 在审批通过时固定金额、收款方等财务所需内容，使宕机后的重试仍提交同一份批准内容 |
| 处理状态 | 区分待处理、处理中、已提交、需处理，决定扫描和业务展示行为 |
| 下次尝试时间、领取次数 | 控制重试节奏，并判断本次属于首次处理还是恢复处理；领取次数不代表实际入账或实际网络请求次数 |
| 领取标识、领取期限 | 标识当前负责处理的这一次执行；允许过期接手，并阻止旧执行覆盖新执行结果 |
| 财务受理编号 | 保存财务明确返回的结果，是本地确认提交完成的依据 |
| 最近处理原因 | 记录超时、业务拒绝等原因，使未完成任务能解释清楚、继续处理 |

领取信息直接放在任务中，无需单独的调度服务或锁表。领取标识每次重新生成，不能只使用实例名称：同一个实例重启或再次领取，也必须被视为不同的执行。

任务状态的含义保持清晰：

- **待处理**：尚未确认提交结果，到了下次尝试时间即可领取。包括首次提交和需要继续确认的超时任务。
- **处理中**：已经被某次执行领取。领取过期后可以被其他实例接手。
- **已提交**：本地已保存财务明确返回的受理编号，不再进入提交扫描。“已提交”不自行扩大为“已支付”等其他财务业务状态；页面按接口明确的业务含义展示结果。
- **需处理**：财务明确拒绝相同内容继续提交，需要业务介入，保留原因并停止无意义的自动重试。它仍是未完成任务，不能计入提交成功。

超时只说明结果未知，不进入终止性拒绝分支。任务内容在重试过程中保持固定；修改已提交申请属于另行定义的更正业务，不覆盖原任务内容。

从审批到完成，按以下流程执行。

1. **审批通过时创建任务。** 将审批通过状态和任务写入已有 MySQL 的同一个事务。事务提交后，申请与任务一起生效；失败时一起回滚，审批操作也不能对外报告成功。重复处理同一次审批时，利用任务申请编号的唯一约束确认任务已经存在，保留原任务及其进度，不重新初始化。这里将审批状态与任务同库保存作为本方案的落地要求。

2. **每分钟扫描少量到期任务。** 每个实例分别查找到了尝试时间的待处理任务，以及领取期限已过的处理中任务。只读取候选任务不代表取得执行权。实例需要按任务编号执行带条件的原子更新，再次检查任务仍可领取，写入新领取标识和期限，并增加领取次数。只有更新成功的实例才能调用财务；竞争失败就跳过。领取操作结束后立即释放数据库锁，不在持锁期间等待财务响应。

3. **领取后确认或提交。** 首次处理直接提交固定内容与申请编号。恢复处理先按申请编号查询：有受理结果就准备落库；明确仍在处理中就安排稍后再查；尚未查到就用相同编号提交。查询自身超时则稍后继续确认。任何情况下都不通过更换编号来绕开财务防重。

4. **保存明确结果。** 收到受理编号后，在一次数据库更新中同时保存受理编号、改为已提交，并清除领取信息。更新必须要求任务仍为处理中、领取标识仍属于当前执行。数据库提交成功后，本地才确认任务完成。如果更新影响零条记录，说明任务已经被接手或完成，旧执行停止修改它。

5. **处理暂时性失败。** 提交超时或可重试的暂时错误，也必须检查领取标识，再将任务交回待处理、记录原因和下次尝试时间。连续失败逐步拉长间隔，并设置等待上限，避免持续密集调用；不因达到固定次数而丢弃未确认任务。若本地数据库也不可用，无法交回任务，保留的处理中状态会通过领取到期机制恢复。

6. **保留明确拒绝的任务。** 只有财务明确返回终止性业务拒绝，才转入需处理，并保留具体原因。业务介入后不能直接改写一份可能已经入账的任务再发送；应依据财务明确结果及相应业务规则处理。未知结果与明确拒绝必须在接口适配处区分。

**“财务已入账，本地保存前宕机”沿同一流程自然恢复。** 假设实例甲领取申请 A，财务已经入账并生成受理编号 F，甲随即宕机。本地仍保留 A 的处理中状态。领取期限到期后，实例乙在后续扫描中领取 A，写入新标识，按 A 查询取得 F，再将 F 与已提交状态一起保存。

如果乙尚未查到结果而重新提交 A，财务仍返回同一个 F，不重复入账。如果乙也在保存前宕机，后续实例重复这一过程。如果本地结果实际上已经保存成功，只是数据库响应丢失，后续扫描会看到已提交状态并跳过它。因此不需要猜测某个实例究竟执行到了哪一步，也不需要因为一次网络故障撤销财务入账。

还需覆盖两个实例短暂重叠处理的情况。甲可能只是很慢，领取过期后乙接手，但甲的财务调用仍然继续。这时财务按 A 防止重复入账，本地按领取标识防止旧执行覆盖新结果。甲晚到的成功结果不能抢回任务，晚到的失败结果也不能把乙的成功改回待处理；乙自行查询或重试即可取得同一财务结果。

领取期限应覆盖一次查询、可能的一次提交和本地保存的有界等待时间，并留出余量。所有外部调用设置超时；实例只领取能够马上开始执行的少量任务，避免任务在本地队列里等待到领取过期。本方案不要求额外的领取续期机制：异常暂停导致过期时允许接手，通过财务防重和本地领取标识维持正确性。

性能上，审批路径只增加一份本地任务写入，不等待财务。扫描分别使用“状态与下次尝试时间”“状态与领取期限”相应索引获取少量候选任务，不扫描全部历史申请或全部已提交记录。外部调用使用有限并发，数据库更新保持短小。恢复中的申请可能多一次查询，其负担主要取决于财务响应时间、当前积压量及失败比例，而不是累计申请总量。

每分钟扫描意味着任务通常在后续一次扫描中开始处理；宕机恢复还需要等待领取到期，暂时失败需要等待下次尝试时间。每天 2000 单支持优先采用这个简单架构，但峰值吞吐、财务限流和故障后的积压恢复时间尚无实测依据，不能承诺固定完成时长。

本方案的保证边界是：每张已批准申请都有持久化任务；任务在本地保存明确结果前不会被当作成功或遗忘；相同编号可以重复确认，由财务保证只入账一次。在服务和财务最终恢复可用、申请内容有效的条件下，任务能够继续推进到本地结果确认完成。持续故障或业务拒绝期间，申请明确保持未完成并保留处理依据。

实施时需要核对财务接口的具体返回码、查询结果含义、超时及限流要求，以及当前审批落库入口；这些用于落实接口适配和运行参数。财务防重与查询能力正式可用，仍是启动自动提交的必要前提。
