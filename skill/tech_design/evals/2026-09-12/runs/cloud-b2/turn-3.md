好，按已确认的机制定稿，当前仍只做技术设计，不写业务代码。字段和接口采用下面的命名；实现时沿用现有文件状态、权限判定逻辑，不另建一套权限体系。

**删除的单位是一次操作形成的文件集合，恢复的单位也是这个集合。** 删除自有目录时，把当时有效的整棵子树放入同一删除批次；此前已删除的节点保留原批次。共享入口始终独立于原文件，不参与文件删除批次。

| 对象 | 含义与必要字段 |
|---|---|
| 文件记录 `files` | 保留现有所有者、父目录、类型及有效状态；增加 `delete_batch_id`，表示当前属于哪次删除 |
| 删除批次 `file_delete_batches` | `id`、`owner_id`、`root_file_id`、`deleted_at`；记录这次删除的根节点和统一时间 |
| 所有者协调记录 `owner_file_locks` | 每个所有者一行，以 `owner_id` 为主键；供多个实例通过 MySQL 行锁协调操作 |
| 共享入口 `shared_entries` | 使用独立的入口 ID，保留接收者和目标文件引用；移除只作用于这个入口 |
| 分享权限 | 沿用现有权限记录，删除和恢复文件都不复制、不重建权限 |

协调记录在所有者初始化时建立，已有所有者在上线迁移时补齐。它只提供一个稳定的加锁对象，不保存“谁正在操作”等应用状态。

文件有效时，`delete_batch_id` 为空；被删除时，文件状态和批次关联在同一事务中更新。恢复时一起恢复有效状态、清空当前批次关联。批次记录可以保留，但回收站只展示仍有对应删除根节点的批次，不把已恢复的历史批次继续展示为待恢复项。

删除流程固定为：

1. 开启事务，获取所有者协调记录的排他锁。
2. 当前读检查目标归属和状态；接收者不能通过这个接口删除共享内容。
3. 根据父目录关系遍历有效子树，排除此前已经删除的节点。
4. 创建删除批次，把本次全部节点标记为已删除并关联批次；多条 SQL 可以分批执行，但必须一次提交。
5. 提交成功后返回批次 ID 和删除时间。此时既不清理物理内容，也不更新共享用户的入口。

创建文件、上传完成落目录、移动、删除、恢复，以及分享权限变更，都遵循“先获取所有者排他锁，再检查和修改”的顺序。这样能防止删除遍历期间漏进一个新文件，也能让权限变更与链接签发有确定的先后。普通元数据读取不需要这把锁。

目录遍历需要父目录查询索引，批次恢复需要 `delete_batch_id` 索引，到期扫描需要删除时间索引。共享用户数量不进入删除事务的更新规模。

恢复流程固定为：

1. 开启事务，获取所有者排他锁，确认请求人拥有这个删除批次。
2. 检查根节点仍属于该批次，且距离批次删除时间未满 30 天。
3. 检查原父目录仍有效、原位置不存在命名冲突。父目录已删除时要求先恢复父目录；同名时拒绝覆盖并返回冲突。
4. 恢复该批次全部成员，一次提交；不允许只恢复其中一个子节点。

恢复不会修改分享权限。原主人在删除期间撤销的一份分享继续保持撤销；其他有效授权继续按现有权限规则生效。接收者曾移除的某个共享入口也不会因此重建。这里不新增共享入口恢复能力，入口移除继续按独立入口操作处理。

**链接的生效边界以完成签名为准。** 每次签发都经过下面的路径：

> 开启事务 → 获取原文件所有者的共享锁 → 当前读检查目标状态和有效权限 → 持锁完成链接签名 → 结束事务 → 返回链接。

多个签发请求可以并行持有共享锁。删除必须等此前的签发完成，才能取得排他锁；删除提交后才取得共享锁的请求，会读到已删除状态并拒绝签发。签名不能放到释放锁以后，也不能采用缓存、读副本或旧快照替代这次检查。

已经完成签名的链接继续使用到原到期时间，最长还有 10 分钟；不尝试中止已开始的下载。预览和其他签发存储地址的入口也适用同一规则。权限撤销同样阻止撤销后的新签发，不撤回此前已签发的链接。

时间规则统一使用数据库时间，保存为 UTC：

| 距本次删除的时间 | 行为 |
|---|---|
| 未满 30 天 | 允许恢复 |
| 满 30 天、未满 90 天 | 拒绝恢复，保留物理内容 |
| 满 90 天 | 允许后台清理物理内容；这是最早清理时间，不承诺这一刻立即清完 |

恢复后再次删除，创建新批次并重新计时。此前单独删除的子文件仍按自己的批次计时，不被父目录的删除或恢复刷新期限。

后台清理只挑选“仍处于删除状态、所属批次已满 90 天、物理内容尚未清理”的文件。逐个删除对应物理内容，成功或确认内容已不存在后记录 `content_purged_at`；失败保留待处理状态，后续重试。多实例可能重复处理同一候选，因此物理删除必须幂等，物理对象标识不能复用于其他新文件。

不按目录递归清空存储路径，也不在本次设计中硬删除目录关系和分享元数据。如果现有存储存在去重或共享物理对象，清理时还要确认没有其他需要保留的引用；90 天到期本身不代表可以删除仍被引用的对象。

接口按原文件与共享入口分别表达：

| 接口 | 行为 |
|---|---|
| `DELETE /files/{file_id}` | 删除自己的文件或整棵有效子树，返回删除批次 |
| `GET /trash` | 查询自己的当前删除批次；返回根节点、删除时间和是否仍可恢复 |
| `POST /trash/{batch_id}/restore` | 整体恢复该批次 |
| `DELETE /shared-entries/{entry_id}` | 只移除当前接收者拥有的指定入口 |
| `POST /files/{file_id}/download-url` | 按共享锁、当前状态和当前权限签发链接 |

分享授权和撤销沿用现有接口，只补上上述协调规则。所有归属、期限和状态限制都由服务端检查，不能依靠页面是否显示按钮。

事务失败时整体回滚；提交后响应丢失时，客户端应查询当前结果，不能把超时解释为删除失败。目标已经删除时不创建新批次、不刷新删除时间。恢复过期、原位置冲突或批次已不处于待恢复状态，返回明确的业务错误。

后续实现验证重点为：先删子文件再删父目录的恢复范围、多个共享入口互不影响、恢复与权限撤销并发、树修改与删除并发、签发和删除的两种先后顺序，以及 30 天和 90 天边界。性能验证使用 1 万节点目录，测量事务耗时、同一所有者的锁等待和签发延迟；10 万共享用户场景需确认没有权限或入口的批量更新。同步事务的响应时间目前尚未实测。
