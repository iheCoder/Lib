这次应当沿用原申请，直接把已查到的工单作为最终结果。**工单创建已经成功，剩下的问题只是把成功结果正确交给前端；JSON 修复不能重新开启创建流程。**

按前面的设计，接下来这样走：

1. **先把查询到的成功结果保存好，再交给模型组织回复。** 恢复程序通过原业务请求号查到工单后，把该申请与工单编号、链接的对应关系持久化，记为创建成功。模型生成 JSON 是否成功，不影响这个事实。如果当前只是把查询结果放进模型上下文、尚未保存，应先补上这一步。

2. **拦住修复输出过程中再次出现的创建动作。** 输出修复只需要修复表达，建议这个步骤不开放创建工具。即使模型仍输出了工具调用，执行程序也不能把它直接转发到工单平台，而应把它视为不符合本步骤要求的输出。

   同时，创建工具本身仍要能应对重复调用：即使这次调用实际进入了工具，工具也先读取当前申请记录，看到已有成功结果，就直接返回原工单编号和链接，不再调用平台创建接口。这里应先处理“申请已经成功”，再考虑模型本次提交的内容，避免新标题的校验问题把一个已成功的申请误报为失败。

3. **重新措辞的标题不生效。** 这段文字只是模型在修复输出时给出的新参数，既不是用户另提新申请，也不是已授权的修改操作。工具不生成新业务请求号，不修改原提交内容，也不修改平台工单。它可以明确返回“本申请已创建，本次传入的标题未应用”，并携带原成功结果；前端若展示工单标题，应使用已确认的实际标题。

4. **由程序组装前端需要的成功 JSON，保证这次能结束。** 工单编号和链接已经是确定的数据，不必再让模型决定最终结果是什么。后端读取已保存的成功结果，按前端约定的结构，用标准 JSON 序列化生成响应；回复文字也可以直接用固定句式，例如“工单已创建：〈实际链接〉”。如果希望保留模型润色，润色失败时就使用这份程序生成的响应，不能无限修复，更不能返回创建阶段。

用户最后拿到的是**第一次创建的那张工单的真实链接**。这次新拟的标题不会出现在工单里，也不能向用户宣称已经改了标题。

如果把最终 JSON 发给前端时连接又断了，前端重试或重新查询这份申请，后端仍从已保存的结果返回同一张工单。需要区分“创建成功”和“这次回复是否送达”：回复失败不会撤销创建成功，更不会成为另建一张的理由。

这也补明确了前面方案的执行边界：稳定业务请求号负责让重复外部调用不会多建单；持久化的成功结果负责让业务完成后不再执行创建；程序生成最终响应负责让模型格式错误不阻断已确定结果的交付。这三个环节都由执行程序落实，不能只靠提示词要求模型记住。
