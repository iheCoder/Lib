**这次执行继续归属原申请，最终应回复已经查到的那张工单。** 模型修复 JSON 时再次调用工具、重新措辞标题，都不能成为新建工单的依据。这里需要把上一轮的执行顺序说得更明确：**先判断这份申请是否已经完成，再处理模型本次传入的内容。**

按这串实际事件，接下来这样走：

1. **查到工单后，先保存确定结果，再交给模型组织回复。** 恢复流程用原业务请求号查询到了工单，就把平台返回的工单编号和链接保存到原申请记录，并标记创建已完成。这个事实来自平台，不能取决于模型后面是否输出了合法 JSON。

2. **JSON 不合法，只代表回复还没交付成功。** 此时工单创建已经完成，不应把整个申请重置为“尚未创建”，也不重新执行完整业务流程。需要修复的是前端响应。

3. **模型再次调用创建工具时，工具首先读取原申请记录。** 它看到已保存的成功结果，直接返回同一个工单编号和链接，不再调用平台创建接口，也不覆盖此前保存的标题或提交内容。此次重新措辞的标题不生效，更不能触发换号。

这里要修正上一轮容易产生误解的地方：“内容不同就返回冲突”适用于还没有确认创建结果、却试图改写已保存提交内容的情况。**本例已经确认创建成功，应优先返回原结果，不能因为标题变了就阻断用户取回链接。** 工具可以同时明确告诉模型：“本申请已创建，本次标题未应用。”这并不授权更新已有工单；更新是另一种业务操作，本次没有提出。

如果查询虽然成功了，但进程恰好在保存结果前崩溃，恢复后本地仍可能没有成功记录。此时也不接受新标题覆盖原提交内容，而是继续用原业务请求号查询，找回同一张工单并保存。结果不确定时，允许的创建重试仍只能使用原号码和原来保存的内容。

最后给前端的确定结果，我建议由业务代码从已保存的平台结果直接构造：成功状态、工单编号、工单链接，以及一句“工单已创建”。JSON 使用程序正常序列化，链接直接取平台结果。这些必要信息没有让模型生成的必要。模型可以补充自然语言说明，但它的输出失败不应卡住工单结果的返回。

因此，回复修复这一步也应收窄边界：只处理回复文本或格式，不提供创建工具。即使旧流程仍让模型发出了创建调用，上面的工具检查也会直接返回已有结果；正确性不能只依靠提示词要求模型“不要再创建”。如果可选的模型说明一直修复失败，就省略它，使用程序生成的成功回复结束本次处理。

如果前端响应本身也丢失，前端再次获取这份申请的结果时，服务端仍读取原申请记录，返回同一个链接。需要稳定传递的是申请标识，不是让模型再描述一遍故障来重跑流程。

这条执行链最后会停在：**原申请对应一张已确认的工单，平台结果已保存，前端收到合法 JSON 和该工单链接。** 模型输出错误影响回复生成，不会撤销创建成功的事实，也不会产生另一份申请。
