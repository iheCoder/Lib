我会按技术设计 Skill，先把最影响正确性的机制和工具边界讲清楚，再与你确认这个职责划分。

这里的关键是：**业务请求号必须属于用户的这一次故障申请，不能属于某一次模型推理、Agent 运行或工具调用。** 工单平台已经能按号码原子去重，我们需要保证模型重试、重新规划和进程恢复时，始终拿到同一个号码。

例如，用户申请“设备 A 无法启动”，平台已经创建成功，但响应在途中丢失。Agent 重启后再次调用创建工具，只要仍使用原号码，就能找回原工单；如果模型重新生成号码，就会产生第二张。反过来，用户明确说“再提交一份新申请”，即使描述完全相同，也必须分配新号码。因此，不能用标题、正文或设备编号的内容摘要判断是不是同一申请，也不能把整个会话当成一份申请。

我建议由接收申请的业务代码维护这份身份，模型负责整理内容，执行工具负责可靠地完成这一份申请。

1. **先保存本次申请，再启动 Agent。** 接收入口为这次申请生成业务请求号，并持久化它与原始申请的关联。保存成功后才允许进入创建流程。入口自身重收同一请求，也必须找到原记录；否则 Agent 内部再可靠，入口重试仍可能生成两个号码。如果入口已有稳定的提交标识，可以利用它建立唯一关联。用户明确发起另一份申请时，建立另一条记录、分配新号码。
2. **模型整理标题、正文和设备编号。** 模型可以补齐必要信息，但不生成或更换业务请求号。用户发起流程已经授权创建，整理完成后可以直接执行，不加审批。
3. **创建工具绑定本次申请。** 工具从可信的运行上下文取得申请身份，模型只提交整理后的工单内容。上下文在恢复后仍指向原申请；不能暴露一个让模型任意换号、或每调用一次就创建一份新申请的接口。同一会话存在多份申请时，每次执行都明确绑定自己的申请，避免使用一个会被后来申请覆盖的“当前请求号”。
4. **首次发送前，保存实际要发送的内容。** 工具原子地保存本次申请的标题、正文和设备编号，再用已保存的业务请求号调用平台。此后恢复和重试使用同一份内容。这样模型重新规划后即使换了措辞，也不会让同一个号码代表两份不同的提交内容。两个工具调用同时到来时，只允许其中一份内容首先保存成功；另一份若内容不同，应返回“本申请已有提交内容”，不能覆盖它或另换号码创建。
5. **确认平台结果后保存并回复链接。** 平台返回工单编号和链接，工具将其保存到原申请中，再返回给 Agent。之后对这份申请重复调用，直接返回已保存的结果。只有拿到已确认的工单链接，助手才告诉用户创建成功。

异常处理仍围绕这份申请，不需要另造一套补偿流程：

- **调用超时、连接断开：** 此时只知道结果未确认，不能判断创建失败。按原号码查询；查到就保存结果，暂时查不到可以用原号码再次创建。即使第一次调用仍在执行，平台的原子去重也能保证只产生一张。
- **平台已创建，本地还没保存就崩溃：** 恢复后从已保存的申请取得原号码，再查平台或重复创建，收敛到原工单。
- **两个执行同时恢复：** 两者读取同一个号码和已保存的提交内容，平台仍只创建一张。本地保存结果也应落到同一条申请记录，不能因另一个执行稍后超时而清掉已确认的成功结果。
- **平台持续不可用：** 保留未确认的申请，告诉用户暂时无法确认结果，后续仍按原号码恢复。不能为了“重新试一次”新建申请。

面向模型，我倾向于只提供一个“完成本次申请的工单创建”工具：输入整理后的内容，返回已创建的工单链接、结果尚未确认，或明确的输入错误。按业务请求号查询、重复发送和读取本地结果，都由工具内部执行。平台原始的创建与查询接口留在工具实现层，避免把是否换号、是否重试这些一致性责任交给模型判断。这个工具可以被重复调用，其业务含义始终是完成当前这一份申请。

目前最值得先确认的是这个职责边界：**你是否认可由接收入口持久化“一次申请”的身份、执行工具管理查询和重试，模型只整理内容并请求完成当前申请？** 这会决定申请记录放在哪里，以及 Agent 恢复时需要传递什么上下文。确认后，再把必要的数据、接口和恢复流程整理成可以实施的完整设计。
