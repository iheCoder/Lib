这次应直接返回已经查到的那张工单。原用户没有发起新申请，所以修复 JSON、再次调用工具、重新措辞标题，都不能产生新的业务请求号，也不能改动已经创建的工单。

接下来按这个顺序走：

1. **先把查到的结果可靠保存。** 恢复执行按原业务请求号查询到工单后，执行代码立即把工单编号和链接写入原申请记录，确认本次建单已经完成，再把结果交给模型或前端。不能等模型输出合法 JSON 后才保存，否则展示环节的错误会影响业务结果的恢复。若查询后、保存前又崩溃，下次仍沿原号查询并补存。
2. **拦住修复过程中多出来的创建动作。** 输出修复只需要处理展示内容，这一步应关闭创建工具；模型即使输出看起来像工具调用的内容，也不执行它。同时，创建工具自身仍保留独立保障：若调度器真的把这次调用送了进来，运行时注入的仍是原申请身份，工具读取到已完成记录，就直接返回原工单编号和链接，不再调用外部创建接口。
3. **新标题不进入业务数据。** 它只是模型在输出修复中生成的另一种措辞，不能覆盖首次保存的提交内容，也不能被解释成新申请或修改工单的指令。工具返回原来的实际提交标题和已有工单结果；需要展示平台最终标题时，使用平台返回的数据。
4. **由代码组装确定的成功响应。** 工单编号和链接已经是结构化事实，没有必要再让模型生成整个 JSON。后端使用正常的 JSON 序列化，把已保存结果填入前端响应，例如：

```json
{
  "status": "created",
  "ticket_id": "平台返回的原工单编号",
  "ticket_url": "平台返回的原工单链接",
  "message": "工单已创建，点击链接查看。"
}
```

这里的字段值来自已确认的结果，不从模型重新生成的文字中提取。模型如果需要补充自然语言说明，可以只提供一个可选文本字段；修复尝试有上限，仍然失败就使用上述固定文案，让代码照常返回合法 JSON 和原链接。

这次故障也补出了上一轮工具边界中需要明确的一点：**建单是否完成由平台结果确认，向前端交付是否合法由响应代码保证，两者分别保存和处理。** 模型输出不合法只能触发展示修复，不能把已经完成的申请退回待创建。任何较晚到达的超时或模型错误，也不能覆盖已确认的成功结果。

如果最后连前端响应也因网络问题丢失，前端重取这次申请的结果时，后端仍从原申请记录返回同一编号和链接。最终给用户的是“工单已创建”以及已查证的原工单链接；本次过程中没有任何依据创建第二张工单。
