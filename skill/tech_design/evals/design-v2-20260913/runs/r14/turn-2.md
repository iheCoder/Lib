这次申请已经创建成功，接下来应把已有工单的确定结果交给前端。模型输出 JSON 失败只是回复生成失败；它随后提出的创建调用，也仍然属于原申请，不能换号或改写已提交内容。

具体这样走：

1. **先保存查询确认的结果。** 恢复代码查到原业务请求号对应的工单后，将平台返回的工单编号、链接保存到原申请记录，确认这份申请已完成创建，再把结果提供给模型。如果查询成功后、保存之前又中断，下次继续用原号查询即可。

2. **把 JSON 修复限制在回复生成。** 此时模型只需要把已有结果组织成回复，修复调用不再提供创建工具。如果模型仍输出了创建调用，执行代码也不能因为它出现在输出里就直接执行。

3. **工具执行入口再次检查原申请。** 这道检查必须放在实际执行工具的位置，不能只依赖恢复时已经检查过一次。执行代码从当前申请上下文取得原申请，发现已有确认结果，便直接返回原工单编号和链接，不再调用平台创建接口。此时应先检查是否已完成，再处理新的创建参数；模型重新措辞的标题不会写入本地提交内容，也不会更新外部工单，更不会触发新申请。

4. **由代码生成最终 JSON。** 前端需要的确定信息已经来自平台，无需继续依赖模型拼出合法 JSON。代码从保存的结果构造响应对象，用 JSON 序列化器输出“创建成功”、原工单编号和链接；用户可见文字可以直接是“工单已创建：查看工单”。模型生成的其他说明是可选内容，修复仍失败时使用这份固定回复即可。

因此，前端最后拿到的创建状态和链接来自已确认的工单结果。模型把标题改成什么、能否修好输出，都不能改变这一事实。如果页面需要展示工单标题，应使用平台返回的实际标题，不能展示模型重写后却没有提交的标题。

这里需要把上一轮的工具边界再明确一点：**“已完成则返回已有结果”必须是每次进入创建工具时都执行的规则，而且优先于处理模型这次提供的参数。** 对尚未确认结果的申请，才继续用原号、原提交内容查询或重试；对已经确认成功的申请，后续超时、格式错误和工具调用都不能把它重新变成待创建。

即使存在另一个调用早已通过检查、还在路上，它携带的也必须是原业务请求号和固定内容，平台的原子去重仍能保证只有一张工单。本地这道检查负责避免多余操作，外部原子去重负责守住并发和中断下的唯一性。

如果最终响应再次因连接问题未送达，前端重取原申请结果时仍拿到同一张工单的链接。只有用户明确发起新申请，接收申请的代码才会建立新记录、分配新号；修复模型输出不具备这个含义。
