这个流程的关键，是让“一次故障申请”的身份独立于模型运行。外部平台已经能按业务请求号原子去重，因此可以允许重复调用，同时保证同一申请只建一张；我们要守住的是：模型重新规划、工具重试、进程恢复，都不能替这份申请换号。

我按提供的技术设计 Skill，先把这一关键边界的建议和执行过程讲清楚，再与你确认。

用户第一次提交故障申请时，接收申请的执行代码先保存一条记录，表示“用户授权创建的这一张工单”，同时分配业务请求号。保存成功以后才允许调用模型和外部平台。这条记录属于业务申请，不属于某次模型运行或某次工具调用；后两者可以重来，前者保持不变。

这里还有一个入口约束：同一次提交因网络问题重复到达时，也必须找回同一申请。可以沿用已有的、重传时保持不变的消息或提交标识，在保存时约束它只能对应一份申请，不能在每次收到请求时重新生成业务号。用户明确提出另一份新申请，则创建另一条记录、分配新号，即使文字完全一样。不能用正文摘要、设备编号或对话编号代替申请身份：同一设备、同一对话中都可能存在多份合法申请。

建议模型与工具这样分工：

1. **模型整理内容。** 从用户描述中提取标题、正文、设备编号；缺少必要信息或存在无法判断的设备歧义时，再向用户补充询问。已有创建授权继续有效，不另加审批。
2. **执行代码掌管申请身份和外部创建。** 给模型一个绑定当前申请的“提交工单”工具。模型只提供整理后的内容，不能传入或生成外部业务请求号，也不能通过重试参数要求换号。工具从可信运行上下文中找到已保存的申请。
3. **工具先固定本次提交内容，再调用平台。** 检查必填信息和当前用户可操作的设备范围，然后把标题、正文和设备编号一次性保存为这份申请实际提交的内容。必须先持久化成功，再向外发请求。这样即使模型稍后改写标题，重试也仍然提交同一份内容，不会因为两个并发调用的参数不同而由网络先后顺序决定工单内容。
4. **平台确认结果后才回复成功。** 工具用已保存的业务请求号和内容创建工单，将平台返回的工单编号、链接保存到申请记录，再把链接交给模型回复。仅保存了申请，或者发出了 HTTP 请求，都不代表工单已创建。

提交后的内容修改不能悄悄塞进创建重试。如果模型再次调用时传了不同内容，工具应说明本申请已经固定了哪些内容，以及当前创建结果；修改既有工单属于另一种操作，这轮先不扩展进去。内容尚未提交时的整理和修正，则可以继续进行。

几个容易出错的过程，可以沿着这条边界直接处理：

- **平台已创建，但响应丢失。** 本地只能记为“结果尚未确认”。恢复后按原业务请求号查询；查到就保存原工单链接，查不到也只能用原号、原内容再次创建。查询未找到不能成为换号的理由，即使旧请求还在平台处理中，原子去重也能守住一张工单。
- **进程在发请求前或收到结果后崩溃。** 恢复代码从保存的申请和提交内容继续执行；如果本地尚未保存确认结果，就查询或重复调用原号。两种中断都不需要让模型重新决定是否另建一张。
- **模型同时发出两个工具调用。** 本地用原子写入保证只有一份提交内容被固定；两个调用都读取这份内容、使用同一业务号。外部平台负责最终的创建去重，不必靠一个跨网络持有的锁保证唯一性。
- **成功结果之后才收到旧调用的超时。** 更新本地记录时，不能让超时或旧失败覆盖已经确认的工单结果。对“是否创建成功”，平台按业务号返回的结果是依据；本地记录保存的是已确认结果和继续处理所需的信息。

工具返回给模型的结果也要明确区分：已确认创建时附工单链接；网络超时等情况说明结果待确认、仍属于原申请；只有平台明确证明未创建且无法继续时，才报告明确失败。待确认的申请由恢复执行代码继续查明，有限次数的自动重试用尽后可以停止本轮等待并告知用户，不能把它说成“创建失败，请重新申请”。重试次数限制控制等待和调用成本，不改变申请身份。

目前真正需要一起确定的是工具控制权：**我建议由申请入口及恢复代码维护申请身份、固定提交内容并处理结果未知；模型只整理内容、调用绑定当前申请的工具，以及解释结果。是否按这个边界继续细化？** 这个决定会直接影响工具接口和持久化内容。采用后，下一步再明确聊天入口如何把“补充原申请”和“明确发起新申请”传给执行代码，避免把这件事隐藏在模型随时可调用的“生成新业务号”工具里。
