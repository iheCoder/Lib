这次仍然是原申请。**查到已有工单后，创建这件事就已经完成；后面的 JSON 修复失败只能影响结果展示，不能让申请重新进入创建流程。** 模型重新措辞标题也不构成新申请。

接下来这样处理：

1. **先保存查询到的结果。** 恢复执行器把平台返回的工单编号、链接和可取得的实际标题保存到原申请，再交给模型组织回复。不能等模型输出合法 JSON 后才保存业务成功结果。
2. **重复工具调用仍绑定原申请。** 模型在修复输出时再次调用创建工具，执行器继续注入原业务请求号，不允许这次调用生成新号。
3. **工具优先返回已完成结果。** 工具发现原申请已有工单，直接返回该工单编号、链接和实际标题，不再请求创建接口，也不更新平台上的标题。模型新传入的标题不覆盖原提交内容。
4. **应用把确定的结果交给前端。** 工单编号和链接已由平台确认，应用可以直接用固定结构和 JSON 序列化器生成前端响应，例如包含“创建成功”、实际标题和工单链接。模型可负责额外说明，但不再承担成功结果的必要输出环节。

这里需要把上一轮的工具处理顺序说得更明确：**先检查是否已经完成，再处理提交参数是否变化。** 已完成时，返回原结果即可，可以附带“本次传入的新标题未应用”的说明；不要只返回标题冲突错误，让模型以为工单还没建成。如果尚未取得结果但已有提交记录，则沿用原请求号和原内容查询、恢复，仍不能接受新标题替换。

输出修复也应收窄边界：只提供已确认的工单结果和输出格式要求，不提供创建工具。如果现有执行循环仍收到创建调用，上述工具检查也会把它变成一次读取原结果，不产生新的工单。

如果再次修复仍输出非法 JSON，直接使用应用生成的固定响应结束本次处理，不需要继续让模型尝试。用户最终收到的是：“工单已创建：[原工单实际标题](平台确认的原工单链接)。”实际渲染时填入已保存的平台结果。

因此，这串故障最终应落在同一个确定结果上：平台只有原来那一张工单，标题保持实际创建时的内容，用户拿到它的真实链接。创建结果与回复格式分别处理，回复失败不会撤销已经确认的业务成功。
