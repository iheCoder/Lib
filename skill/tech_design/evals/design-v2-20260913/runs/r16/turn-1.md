核心是：**由应用为每份故障申请分配并保存一个业务请求号，后续所有创建、查询和恢复都使用这个号码。模型负责整理内容，不负责决定请求号，也不能在重试时换号。** 平台已有原子去重能力，可以直接利用，无需再加审批或自行实现一套分布式去重机制。

这里的“一份申请”是用户这次要求创建的那张工单。它可以跨多轮补充信息，也可以经历多次 Agent 运行。请求号不能按故障文字计算，不能使用会话号，也不能在每次工具调用时生成：相同文字的新申请需要新号，同一申请的重新规划和恢复则必须沿用旧号。

流程可以这样安排：

1. **先登记申请，再启动 Agent。** 应用在接受用户的创建请求时生成业务请求号，并持久保存申请与该号码的关联。消息重投、运行重试和进程恢复应找到已有申请；用户明确提出另一份新申请时，建立另一条申请记录并分配新号。入口若支持消息重投，应通过稳定的消息或提交标识识别重复送达，不能靠文字相同来判断。
2. **模型整理标题、正文和设备编号。** 信息不足时向用户补充询问，仍归属原申请。信息齐全后直接调用创建工具，不增加确认或审批步骤。
3. **工具先保存本次实际提交内容，再请求平台。** 首次创建前，以原子方式保存标题、正文和设备编号，作为这份申请的提交内容。并发调用只能确定一份内容；后续执行都使用已保存的版本，避免模型重新规划后用同一个号码提交不同内容。平台收到业务请求号和这份内容，执行原子去重创建。
4. **保存平台结果，再回复链接。** 将工单编号和链接关联到原申请。后续同一申请再次调用工具，直接返回已有工单。链接应来自平台结果或查询结果，不由模型猜测。

模型可见的工具可以保持为一个 `create_fault_ticket(title, body, device_id)`。业务请求号由工具执行环境从当前申请中注入，不放在模型可自由填写的参数中。工具必须绑定明确的申请上下文；如果一个会话里有多份申请，应用应分别绑定，不能简单取“会话里最新的申请”。没有申请上下文时，工具返回错误，不能顺手生成新号。

工具内部负责校验必填项、保存提交内容、调用平台、查询恢复和保存结果。这些属于确定性的执行职责，不应依赖模型是否记得先查询、是否正确判断超时、是否愿意沿用旧号码。模型也不需要一个能绕过这些约束的底层“任意请求号创建工单”工具。

需要特别处理的是“调用没有返回”的情况：

| 情况 | 处理方式 |
| --- | --- |
| 提交前进程退出 | 恢复原申请，使用原请求号和已保存的提交内容继续执行 |
| 平台已创建，但响应丢失或本地结果尚未保存 | 按原请求号查询，找到后保存并返回原工单 |
| 查询未找到，或者暂时无法确认是否创建 | 继续查询，或使用原请求号和原内容重试创建；不得换号 |
| 模型或多个运行重复调用 | 有本地结果就返回；没有结果就按同一号码执行，由平台原子去重兜底 |
| 平台暂时不可用 | 保存待恢复的信息，向用户说明结果尚未确认，恢复后继续处理 |

“查询未找到”不能成为换号的依据，因为原来的创建请求可能仍在执行。查询有助于恢复结果，真正防止重复创建的是平台对同一请求号的原子去重。

如果模型在首次提交之后又传入不同内容，工具应明确返回“该申请已开始提交，内容已固定”，并提供已知的工单结果或当前处理情况；不能静默覆盖内容，更不能另建一张。用户要修改已提交工单时，应进入单独的修改流程。提交前的信息补充则正常更新申请草稿。

本地只需持久保存申请标识、业务请求号、首次提交内容以及取得的平台结果，并保留必要的执行错误供恢复使用。保存申请和固定提交内容时需要本地原子写入，但不必为了防重复而在整个外部网络请求期间持有锁。

这样可以保证同一申请的重复执行最多产生一张工单；平台恢复可用且请求有效时，应用可以持续使用原号完成创建并取回链接。验收重点应放在：相同文字的新申请能够另建、同一申请的并发调用只建一张、平台成功但响应丢失后能取回原工单，以及进程重启后不会生成新请求号。
