建议把“一次故障申请”作为创建工单的边界：**申请有一个持久化的业务请求号，模型无论重新规划、重调工具，还是进程重启，都只能沿用这个号码。** 外部平台负责按号码原子去重，我们负责保证同一申请不会换号码。

这里要区分三件事：故障申请是用户要求创建的那一张工单；Agent 运行是处理申请的执行过程；工具调用是执行过程中的一次尝试。后两者都可能重复，因此不能用 Agent 运行 ID 或工具调用 ID 作为业务请求号。

**申请的建立与识别**

应用在接受新申请时生成业务请求号，并先持久化，再启动 Agent。后续补充设备编号、恢复运行和重试，都关联这条申请。用户明确另提一份新申请时，建立新记录、生成新号码，即使文字完全相同也一样。

不要按文本相似度或内容哈希去重。入口的同一次提交如果因网络重发，也必须能找到原申请，例如让提交携带一个稳定的提交标识，并在本地保证它只对应一个业务请求号。用户主动新建申请则使用新的提交标识。

对话里的补充消息应关联正在处理的申请。如果确实无法判断用户是在补充旧申请还是提出新申请，就只澄清这个业务含义；这不是创建审批。用户发起申请已经授权，流程不再增加确认创建的步骤。

**创建流程**

1. Agent 从用户描述中整理标题、正文和设备编号。缺少创建所必需的信息时向用户补充询问，期间仍保留同一申请。
2. Agent 调用创建工具。工具从受信任的执行上下文取得当前申请的业务请求号，校验字段，并将本次准备提交的完整内容持久化。内容保存成功之前，不调用外部平台。
3. 工具使用该业务请求号和已保存的内容创建外部工单。平台返回工单编号和链接后，工具把结果保存到申请记录，再返回给 Agent。
4. Agent 将已确认的工单链接回复给用户。以后同一申请再调用创建工具，直接返回已保存的结果。

本地最少保存业务请求号、与入口提交的关联、首次准备提交的内容，以及确认成功后的工单编号和链接。无需另设审批流，也不必为每次工具尝试建立一套业务状态。

首次准备提交的内容要通过数据库事务或其他原子写入机制确定。两个并发调用处理同一申请时，只能有一份内容被确定下来；后续调用使用这份内容。这样即使模型重新整理了标题，也不会让两个不同版本争着成为平台最终创建的工单。

**工具边界**

模型侧的创建工具可以只接受 `title`、`body`、`device_number`。业务请求号由工具服务从当前申请上下文绑定，不能让模型自行填写、生成或更换；模型也不能通过“重新开始”创建新的申请记录。

工具服务承担持久化、并发控制、平台调用、结果查询和恢复。模型承担信息整理、必要的业务澄清及结果表达。平台访问能力只放在工具服务中，避免模型绕过这条路径直接创建。

如果已经确定过提交内容，后续调用又传入不同内容，工具应明确返回“本申请已按此前内容提交或正在确认结果”，并提供当前可确认的信息，不能静默声称新内容已生效。用户要修改已有工单，属于另外的修改操作；不能借此换号再创建一张。

**超时和恢复**

最关键的情况是：平台已经建单，但我们的进程在收到或保存结果前退出。此时本地没有成功结果，不代表外部没有工单。

恢复时按原业务请求号查询：查到就保存并返回原工单；暂时查不到，可以用原号码和原内容再次创建。即使第一次请求仍在执行，平台的原子去重也会保证只建一张。查询失败或持续超时，则保留申请并继续恢复，向用户说明结果尚在确认，不能换号重试，也不能断言创建失败。

如果工单结果已保存，只是回复用户失败，恢复后重发链接即可。这里保证的是“一份申请只创建一张工单”，并不要求创建接口只能调用一次。

实现前需要核实平台去重记录和按号查询的保留期限，确保覆盖我们允许的恢复周期。如果平台会在一段时间后忘记旧号码，超过期限的未决申请就不能直接自动重建，必须先核实旧工单是否存在。

验证应重点覆盖：同一申请并发调用、平台成功后本地保存前崩溃、超时后模型重新调用，以及用户用相同文字明确发起新申请。前三种应始终落到同一张工单，最后一种应得到另一张工单。
