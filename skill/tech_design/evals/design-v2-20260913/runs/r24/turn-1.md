建议把衔接分成两件事：**保存运营这次到底批准了什么，以及在门户真正写入时检查这次操作还能不能执行。** 批准后的暂停和模型再次运行，都不应改变批准内容；客户当前是否允许接收，则必须由门户数据库在写入时判断。

我会按下面这条链路设计。先讨论关键机制，暂不展开表结构。

1. **展示和批准指向同一份固定内容。** 助手准备好公告后，服务端保存完整正文、明确的客户 ID 清单和发布位置，并给这份内容一个标识；运营页面展示的就是这一份。点击批准时，服务端记录运营批准了该标识对应的内容，不能临时再读“最新草稿”或重新执行客户筛选。否则，页面展示后、点击前的修改就可能混进批准范围。需要修改正文、客户清单或位置时，产生新的待批准内容，原批准不能套用。

2. **批准落库后，由后台任务等待值班窗口。** 批准记录保存成功，页面才显示“已批准，等待发布”，这时还不能显示“发布成功”。后台可以扫描已批准、已到窗口且未完成的记录来执行；通知可以用来加快唤醒，但不能成为唯一线索，否则批准已保存、通知未发出时任务就会丢失。进程暂停或重启后，从这些持久记录继续，不要求运营重新批准有效的原内容。

3. **执行代码从批准记录取参数。** 后台任务使用一个稳定标识代表“这次批准对应的发布”，每次恢复和重试都沿用它。模型若再次调用发布工具，工具只能执行该批准记录里的内容；模型重新生成的正文、客户或位置不能覆盖它。参数不一致时，返回“与批准内容不一致，未执行”，交回修改和审批流程。正常的延迟发布不需要再次调用模型，因此也不必为等待窗口持续保留模型会话。

4. **门户在真正写入的事务里检查接收资格。** 门户根据批准中的客户 ID 找到当前接收开关，在同一事务内检查并写入公告。这里不能只有“先查再写”：应锁住相关客户记录直到事务结束，修改接收开关的操作也必须与这些锁互斥。关闭开关先提交，发布就会读到关闭并停止相应写入；发布先拿到锁并提交，则这次发布发生在关闭之前。这样才把“执行时仍允许接收”落到真实的并发顺序上。其他客户资料的变化不应笼统导致批准失效，也不应通过重新渲染正文改变已批准文本。

5. **门户同时保存这次发布的执行结果，供重试查明。** 门户把上述稳定标识作为唯一标识，在写公告的同一事务里保存成功结果。两次并发尝试只能有一次形成这次发布的记录。若门户已经提交，但调用方超时，后台仍用原标识查询或重试，门户返回已保存的结果，不再次写公告。如果事务没有提交，则没有成功记录，可以用相同标识重新尝试。运营以后再次批准相同正文，也可以是合法的新发布，应使用新的标识，不能只按正文是否相同去重。

批准记录和门户数据不一定需要放在同一个数据库。即使分开保存，门户也必须能拿到可信的批准内容，不能把模型声称“用户已批准”当作凭据。是否已经发布，以门户随公告一起提交的结果为准；后台自己的完成标记如果因崩溃没更新，恢复时据此补齐。

这里还有一个会直接改变事务范围和结果含义的决定，需要先和你确定：

**假设批准了 100 个客户，执行时其中 1 个关闭了接收，是整次暂停、一个都不发布，还是允许先向其余 99 个发布？**

我目前倾向于整次暂停，并明确显示哪个客户不满足条件，因为你强调批准的是“这批客户”，这样不会替运营决定少发给谁。但“批准这批客户”也可能表示允许向其中执行时仍合格的人发布，这两种理解都讲得通。

整次暂停时，需要在一个事务里检查全体客户并一起完成写入；部分发布时，则需要保存每个客户的结果，而且还要确定关闭的客户本次跳过，还是以后开启后补发。客户数量也会影响前一种方案的锁范围和事务成本：几十到几百人与数万客户不能未经验证就采用相同容量判断。先确定这里的业务选择，再收敛执行结果和恢复方式，避免提前把关键行为定死。
