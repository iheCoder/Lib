这次恢复应继续执行原批准：**向甲的“服务公告”发布版本 7；乙因当前关闭接收而跳过并记录原因；丙不在批准范围内，不执行。** 甲修改客服电话不影响这次批准，也不触发重新审批。模型生成的版本 8 和新增客户丙不能进入执行参数。

按你明确的边界，上一轮整批暂停的建议取消，采用逐客户检查、逐客户提交。设计可以收敛如下。

### 批准保存什么，恢复从哪里继续

运营批准时，保存其实际看到的完整正文、甲和乙的客户 ID，以及“服务公告”对应的准确发布位置。这份内容在批准后固定下来；版本号用于辨认，真正执行应读取已保存的版本 7 正文，不能凭“版本 7”再去取一份可能被覆盖的草稿。

这份记录代表“运营允许系统执行的这一次发布”，同时也是暂停恢复的依据。批准保存成功后，界面显示“已批准，等待发布”；到达值班窗口，后台读取这份记录，依次处理甲、乙。等待期间无需保持模型会话，恢复也无需重新审批。

模型带回的版本 8 和甲、乙、丙清单，应在工具入口被识别为与批准不符，不能直接调用门户写入。该调用可以返回“参数超出批准范围，未按这些参数执行”。与此同时，原来已批准的任务仍然有效，后台继续从原批准记录读取版本 7、甲乙和原位置。拒绝这次错误调用，不等于撤销原批准。

如果确实想发布版本 8、加入丙或改变位置，就另行展示变更后的完整内容并取得批准。暂停、重试和不影响授权内容的资料更新都不属于这种变更。

### 每个客户怎样真正发布

门户每次处理一个客户，开启一个数据库事务，完成以下步骤：

1. **先确认这是不是已经处理过的同一次操作。** 用“本次批准的标识 + 客户 ID”唯一识别一次客户发布。门户为它建立处理记录，并用唯一约束和事务锁串行处理重复请求；已有最终结果就直接返回。客户 ID 还必须属于该批准清单，不能只凭调用方传来的 ID 执行。
2. **读取并锁定这个客户当前的接收开关。** 锁持有到事务结束。正文和位置来自批准记录，开关来自门户当前数据；客户客服电话等无关字段不用于判定批准是否有效。
3. **根据开关完成本次结果。** 开启时，写入版本 7 公告，并保存“已发布”和对应公告标识；关闭时，不写公告，保存“已跳过：执行时客户关闭接收”。公告写入与发布结果必须在同一事务提交，跳过结果也在持有客户锁的事务里提交。

只有提交成功，门户才返回确定的“已发布”或“已跳过”。处理中断、数据库错误或调用超时不能伪装成业务跳过。

按这条链路，甲的事务写入版本 7；乙的事务留下跳过原因。两人都有最终结果后，任务可以显示“处理完成：已发布 1，已跳过 1”，而不是含糊地显示全部发布成功。乙以后重新开启接收，也不会让这次已经跳过的任务自动补发。

### 检查之后，乙恰好关闭怎么办

关键是让**检查开关和写公告之间，关闭操作不能插入并先提交**。因此，关闭开关的接口必须修改同一条受锁保护的客户记录；如果开关存放在独立表，就锁那条开关记录。只读一次开关、释放连接后再写公告是不够的。

并发只有两种有效顺序：

- **关闭操作先提交。** 发布事务拿到锁后读取到关闭状态，记录跳过，不写公告。
- **发布事务先锁住记录，读到开启。** 关闭请求等待，发布事务完成公告与结果的提交后，关闭操作才能继续。因此数据库顺序是先发布、后关闭，这次发布符合执行时允许接收的条件。关闭接口应在关闭事务提交后才向调用方报告成功。

所以，即使乙的关闭请求在“检查之后、写入之前”到达，也不会发生“关闭已经生效，发布却仍使用旧判断写入”的情况。这里以数据库提交顺序确定生效先后；关闭请求刚到达，不代表关闭已经生效。

锁只覆盖单个客户的一次短事务。等待值班窗口、模型运行和外部网络调用都不能放在持锁期间。

### 重试和中断怎样恢复

逐客户结果既用于展示，也用于恢复。它表示这次批准下某个客户已经发生的事实，不随最新资料重新计算。

例如甲已发布，但后台还没收到响应就断开：恢复后仍用原批准标识和甲的 ID 请求门户。门户发现已有“已发布”结果，返回原公告，不再创建一份；即使甲此时也关闭了接收，已有发布结果仍然保留。随后后台继续处理乙。

如果甲的事务在提交前崩溃，公告和结果一起回滚；下一次尝试重新检查当时的开关。若乙的“已跳过”已经提交，重试直接返回该原因，不因为后来开关变化改成发布。

这需要门户保存的逐客户结果与公告处于同一事务边界。后台批准记录若在另一个数据库，后台只负责调度和汇总；响应丢失时，通过原标识向门户查明结果，不能自行认定成功或创建新的发布标识。两个后台执行者意外同时领取同一任务，也由门户的唯一约束阻止重复副作用。

### 必要的信息与成本

核心只需保留两类业务信息：一份不可变的批准内容，以及门户中每个获批客户的执行结果。前者限定允许做什么，后者记录实际做了什么；客户当前接收开关继续由门户原有数据负责。

处理成本随获批客户数量增长，每个客户独立提交，因此中途可能看到甲已发布、乙尚未处理，这与你允许分别发布的边界一致。客户较多时可以分页读取名单、限制并发，不需要一次锁住整批客户；分页仍必须读取原批准清单，不能重新筛选对象。具体并发量需要结合数据库负载验证，但不会改变授权范围、开关检查和重试的规则。
