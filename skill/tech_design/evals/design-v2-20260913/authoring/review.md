## 必须修正项

### 1. 报告题需要定义“一份报告”约束的是业务产物还是底层计算次数

`events` 首轮写“同一次申请最终只生成一份报告、发一条站内通知”，同时允许消息重投和进程恢复。通知已有明确的服务端原子去重能力；报告生成器、文件落盘与进度记录之间的能力却没有规定。“一份报告”可能被合理理解为只暴露一个稳定下载产物，也可能被理解为生成过程只能运行一次。这两种解释对生成完成但本地记录未保存、两个消费者并发、旧执行者恢复等窗口提出不同要求。

当前规则主要覆盖申请身份、可靠受理和通知恢复，没有明确检验重复消息是否可能让同一申请出现两份报告。因此既可能误罚允许重复计算但唯一发布的正确设计，也可能放过“有申请号就能保证报告不重复”的空缺。

建议在题面明示当前真正要求，例如“同一申请对用户只有一个确定的报告文件和结果，故障恢复允许重新计算，不能暴露第二份业务报告”，并给 oracle 增加对应的并发或中断检查。如果原意确实禁止重复计算，则应说明可用的生成端去重、查询或提交能力，或者允许被测者指出这一保证所缺少的能力。不要只在隐藏 oracle 中替题面选择解释。条件更新结果指针、稳定产物键、可查询的生成端去重等不同正确路径均应可接受。

### 2. 首轮未展开与错误设计需要有明确分离的裁决方式

rubric 一方面允许“首轮可以讨论而非完整定稿”，另一方面把“未提供该项必要能力”与明确错误一起列入 FAIL。多个首轮 probe 又要求同时给出完整身份、持久恢复、发布原子性等机制。Skill 本身要求重要取舍确认后再推进依赖设计，所以合理聚焦一个关键选择、解释其影响并等待确认的首轮，可能合法地尚未展开其他机制。

当前“不能直接推论模型最终无能力”的提醒是正确的，但不足以防止汇总时将这种 FAIL 与错误方案合并为候选胜负。建议明确：尚未展开可以保留为覆盖缺口，但必须在 reason 或独立标签中标明“合理等待决定”“无故遗漏”或“明确错误”；不要据共同 FAIL 数比较正确性。无需强制改出复杂评分 schema，规定报告如何区分即可。第二轮固定提示没有回答首轮真实决策时，也应保留这一轨迹限制，不把尚未得到的用户确认当成已经发生。

## 题目约束与 oracle 的公平性

- `latest` 已给出单调版本、不可变构建输入、已发布版本不回退和积压约束。允许条件更新、发布串行化等等价路径，未强制取消计算。第二轮才增加快照不可取代语义，probe 对轮次的区分合理；资源权重不应被要求某个固定比例，说明有执行机会且不丢已受理任务即可。
- `agent_retry` 明示用户授权和平台原子去重、查询能力，足够支持稳定申请身份及未知结果恢复。A3 的“宿主”应按受信任的确定性执行边界理解，不能仅因实现把这一职责放在服务端工作流或工具适配层而扣分。A5 允许禁用写工具、吸收重复调用或确定性输出，没有绑定单一路径。
- `approval` 明确批准范围及门户具备事务内检查能力，P3 又要求实际并发语义，因此“只是放到事务”不能自动过关是合理的。第二轮才确认逐客户成功和无关资料变化不影响批准，不能用 P4/P5 反向要求首轮已作同样选择。并发关闭接收开关应按选定原子边界确定先后，不能暗含“关闭一旦开始就能追回已发布公告”的额外规则。
- `simple` 的默认值、局部更新、登录用户、显示反馈和写入顺序足够明确，可以直接给设计。不要把 S3 的“服务端确认结果”误解为成功响应必须回传偏好字段：成功确认后采用本次已提交值同样可以满足需求，题面没有要求特殊响应结构。少量验收点可接受，但不应成为 PASS 的必需章节。
- 整体 oracle 显式允许不同实现，未发现必须使用 outbox、CAS、特定数据库或特定 Agent 框架的单一解。建议评分时把 `allowed_paths` 明确视作例子而非穷举；其外满足同一业务约束的机制仍应按执行过程判断。

## 候选新增规则的反作用复核

候选已经对前置盘点中的主要反作用加入约束：不强制收到/受理/完成成为状态，不要求每个事件远程查询；先判断旧任务是否仍需交付；仅在模型参与时展开 Agent；有效批准延续；不用固定表格维护多轮结论。这些是文本层面的良好防护，是否有效仍需轨迹证据。

剩余风险不阻塞本次实验，但应在评分中观察：

1. “只有在现有条件下确实无法同时满足目标时”可能被过严理解为必须先证明不可能才可讨论取舍。遇到外部能力未知时，应允许说明条件依赖、查证能力或提出关键澄清，不要把未知当作已经可保证。候选其他关于事实与假设的规则提供了缓解，暂不能据文字判断会发生误导。
2. “成功、失败和重试等相关写入都应服从它”应约束会影响当前事实的写入，不应禁止保存旧执行者的历史诊断记录。若回答为所有日志和状态都引入全局锁，属于过度扩张，而非候选要求的必要实现。
3. Agent 的时间、成本、上下文与信任要求可能把范围扩大到每题完整预算、记忆和安全架构。文本已限制“实际需要”及不加框架，评分仍要检查它有没有以必需交付形式扩张。

## 可观察收益缺口与非阻塞限制

本套题能观察身份与可靠受理、旧结果发布和积压、工具未知结果与输出修复、审批恢复及简单题克制。不能由这五题推导全部拟改能力均有提升：

- 没有外部不可信材料伪装授权、过期记忆或来源冲突的输入，因此不能证明上下文信任处理改善。
- 没有漏事件、乱序事件与多事实来源之间的专门冲突过程。报告与通知结果恢复只覆盖事实来源的一部分，不能证明一般同步或对账设计能力。
- 没有缺少外部去重或查询能力的场景。不能证明候选会正确解释无法同时兑现的目标，而非惯性承诺或预设漏执行/重复执行二选一。
- 没有真正检验模型调用触发条件、无效输出持续修复、循环停止或成本耗尽的过程。创建工单修复题只覆盖其中一次有副作用的恢复。
- 第二轮新增业务边界可以观察局部修正，但没有较长讨论中推翻旧假设、用户笼统同意与明确授权的对照。不能证明完整的多轮结论维护能力。
- 题面已高度明确地提示关键失败点，所以首轮“主动发现”最多说明把已给条件串成机制，不能解释为在开放真实需求中自行找出未提示风险。第二轮是明确引导后的推演。
- 候选和题目均围绕同一组拟改方向。即使评分盲化且候选胜出，也主要支持这些定向案例上的收益；不能仅因评审独立便称为未见场景泛化证据。没有真人参与也不能证明普通开发者的实际理解率。

上述缺口不要求本轮补成庞大测试集。若保留当前案例，最终报告逐项写清已观察范围和未测能力即可；只有要宣称某项未覆盖能力提高时，才需增加直接证据。

## 修订采纳情况

root 告知已采纳后，本评审仅定点读取上述指定文件的相关修改，确认：

1. `events` 首轮已补充“一份报告指最终归属于申请、可下载的业务产物只有一份；允许因中断重复计算，不要求计算过程只执行一次”。第 1 项的题面歧义已解除。单一产物在重复消费或中断下是否真正得到保证，仍应按回答机制判断；当前专门 probe 对这一点的覆盖较弱，是应保留的测量范围限制。
2. rubric 已增加 `NOT_COVERED`，明确合理讨论阶段未展开不混算为明确错误；`FAIL` 收窄为明确错误或方案已定却缺失必需保障。第 2 项裁决歧义已解除。首轮与第二轮的发现仍需分开记录。
3. rubric 新增 `alternatives`：只在 `events/latest` 的真实分叉下观察机制、代价和选择依据；其余允许 NA，不按方案数量计分，明确占优方案解释排除其他路径的理由也可通过。此调整能补充真实方案取舍的可观察性，没有强制凑出多方案。它不能补足前述上下文信任、未知外部能力或长对话等未测范围。
