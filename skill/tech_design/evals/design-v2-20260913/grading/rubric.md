# 预设评分规则

被测对象是技术设计对话，不是已实施的业务系统。只据题目已确认规则及实际回答评价，允许不同正确实现。技术推演通过不代表实现、容量、真实工具副作用或普通开发者理解率已通过。不要通过词语、章节、篇幅、问题个数或方案数量计分。

每个案例的 rules/probes 提供依据。每个 probe 分别判断其适用轮次的表现：PASS=完整说明符合要求的机制与结果；PARTIAL=方向合理但关键执行或约束缺失；FAIL=明确错误或方案已定却缺失必需保障；NOT_COVERED=该轮未覆盖，尤其是合理讨论阶段暂未展开，不混算为明确错误。每项附逐字证据及完整原因。首轮应记主动发现、已有机制或未覆盖；第二轮新补的内容不能计入首轮。首轮因合理讨论而尚未覆盖，不能直接推论模型最终无能力，但如实记录当前缺口。

额外共同维度：

- clarity：对当前阶段的主要操作，能只凭解释复述参与方、数据变化、生效点及重要概念存在理由。自然语言支持机制，代码只辅助。没有真人评分，仅说明模型判据下解释充分与否。
- focus：只展开与当前机制相关内容；未要求却给完整测试计划、发布步骤、监控告警或排期为偏离。容量尚未实测、真实迁移影响等必要说明不扣分。一句相关验证提醒与整套验证交付分开，局部扩写 PARTIAL，明显另开交付 FAIL。
- economy：每个实际新增状态/组件/保护能连接到题中真实失败；允许必要持久化、原子条件或审批，禁止对低风险题强制上操作台账、调度平台、Agent 或审批。不要因某个正确方案比另一方案代码多就判过度设计。
- alternatives：在 events/latest 存在真实设计分叉时，解释候选机制如何满足约束、代价及当前选择依据；不按方案数量给分，不要求为了凑数引入中间件。其余案例允许 NA，除非回答自身引入真实分叉。一个明确占优的方案如果解释排除其他路径的原因，也可通过。
- decisions：保持事实、当前建议、假设和未决项的身份；新事实更新受影响的机制；不把笼统同意变成未讨论事项的审批；已有授权和充分前提下不重复追问。首轮可以讨论而非完整定稿，重要前提未知时允许明确依赖/合理澄清。simple 题已允许决定常规实现，不应为不存在的关键空白暂停。

每份轨迹输出：
{blind_id,case,probes:[{id,verdict,reason,evidence:[{turn,quote}]}],first_turn:{discovery:"active|mechanism_only|missing|wrong",reason,evidence:[{turn,quote}]},dimensions:{clarity:{verdict,reason,evidence},focus:{...},economy:{...},alternatives:{...},decisions:{...}},strengths:[{turn,quote,impact}],issues:[{turn,quote,impact}]}。

first_turn 判断案例主要风险是否被串成实际参与方变化和后果；只有“幂等/重新检查/队列”不算主动推演。可以按关键风险说明部分主动部分缺失，不把一项代替全部；总体标签只是索引，原因中保留范围。

不得读取条件映射、任何版本 Skill、其他评分或历史 eval。不得猜分组。所有引文必须是对应 turn 的连续原文，不得使用省略号拼接。没有引文的纯缺失判断可引用最近的声称并解释缺了什么。最终按规则/场景和各项维度报告，不使用总排名。
