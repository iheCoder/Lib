# 技术设计 Skill 新旧版与无 Skill 对照报告

Skill 已按讨论路线修改，并完成旧版、新版、无 Skill 的 30 条独立对话、54 份回答及两名模型评分员的匿名评估。**本轮没有证明新版稳定优于旧版或无 Skill，也没有观察到明确的业务机制错误或简单题复杂度回归。** 三组的主要机制都能解释清楚，差异集中在六处评分分歧，不能据此给三个条件排总名次。

## 本次改了什么

保留单文件 Skill 的原有主干：先一起推演机制，再建立模型，解释具体过程，确认重要取舍后收敛。新增内容集中在几类容易被一句术语带过的判断：

- 先明确必须保住的结果；已有能力足够时，不预设必须在漏执行和重复执行之间二选一。
- 分清一次业务申请、重复尝试和合法的新申请；说清“成功”已经承诺了什么，以及依据哪个事实确认结果。
- 检查旧任务、变化后的条件、并发成功与失败写入，真正产生结果时如何保持约束；结合业务判断能否合并、取消或丢弃任务。
- 多轮讨论持续区分事实、决定、假设和未决项，但不要求每轮输出台账。
- 只在模型参与业务时展开 Agent 边界：模型判断与执行代码的责任、未知副作用、输出修复、有效审批的沿用，以及实际需要的终止和成本条件。

新增规则同时限制其适用范围，不要求每个功能都有状态表、队列、审批或 Agent 框架。生产改动是 21 行新增和一处改写，结构校验通过。评估全过程使用冻结候选，没有看见回答后继续修改提示词。

源码与实验快照：[当前 Skill](../../SKILL.md)、[旧版快照](old.snapshot.md)、[候选快照](candidate.snapshot.md)。

## 如何理解这次对照

五题分别运行旧版、新版、不加载技术设计 Skill 三组，每组每题两次。四题各有两轮，简单设置题只有一轮。每条轨迹从新上下文开始，第二轮接着自身的第一轮回答。题目由没有读过 Skill 的独立上下文编写；另一评审先盘点风险，再看到候选与题目审查歧义。

两名评分员仅被允许读取匿名材料，不能读取分组和 Skill；它们先分别完成八个合成正反例校准，均匹配预设判断，再对全部匿名回答独立评分。校准说明它们能区分这些明显样例，不代表已经与真人判断一致。每个判断保留原文引文，脚本核对引文及文件哈希。

这里的“无 Skill”仍然是处在同一宿主全局指令下的 Codex，已有清楚表达、谨慎确认、最小改动等通用要求。它不是完全没有指导的裸模型。三组比较的是在这个实际环境中额外加载技术设计 Skill 的表现，不能推广为所有模型、所有环境里的能力差异。 生成与评分均继承当前宿主配置，没有另行指定模型或推理档位，具体运行模型标识和采样元数据未取得；两名评分员是分别开始的上下文，不是特意选取的不同模型。上下文隔离依靠新对话与读取约束，文件系统仍共享，且没有完整工具轨迹，不能宣称操作系统级隔离。

以下分别说明场景、预期和三组真实回答。首轮根据已给约束形成机制，与第二轮收到明确时序后补充处理，是两种证据；后者不反计为首轮主动发现。题面本身已经给了较明确的风险线索，所以“主动发现”也不能解释为自行找到了真实项目中未透露的风险。

## 报告已经生成，通知却超时，重启后如何恢复

用户生成月报，接口承诺“已受理”后重启也能继续。同一次点击的网络重试仍是原申请，主动再生成是新申请；后台消息可能重复。通知平台可以按业务编号查询、原子去重。第二轮让通知实际保存成功但响应超时，工作进程随后重启。

正确结果是：仍找到同一申请及唯一正式报告，通知先保留“结果待确认”，再查询或用原编号重试确认；不能因为通知超时重新生成已经确认的报告。报告最终只有一份业务产物，不要求底层计算从未重复。

**旧版的两次回答都做到了。** 例如 r01 让客户端在第一次请求前持有稳定标识 K，服务端以此找回进度编号 A；后台先持久保存文件，再确定 A 的正式报告并留下待通知依据，之后才调用通知服务。它解释了为什么“已经调用通知”意味着按该设计本地已确认报告，重启后只需补齐通知事实。r05 则先讨论申请与待发送消息同事务保存，同时允许数据库直接领取工作。它也把临时计算产物与正式下载产物分开。[r01 恢复过程](runs/r01/turn-2.md)、[r05 首轮](runs/r05/turn-1.md)

**新版的两次回答同样做到。** r06 倾向在没有现成队列要求时直接保存申请并由后台领取，并明确旧执行者提交成功、失败或续期都需要检查当前执行资格。r02 说明报告事实由保存的结果确认，通知事实由通知服务确认，页面不必每次同步调用通知平台，但不能把尚未查明的通知显示成确定成功或失败。[r06 首轮](runs/r06/turn-1.md)、[r02 恢复过程](runs/r02/turn-2.md)

**无 Skill 的两次回答也做到了。** r03 推荐申请记录负责恢复、消息加速；r04 更倾向申请与待发送消息同事务提交，但说明小吞吐量时直接扫描能减少机制。两者都保留稳定申请身份、唯一正式结果和独立通知恢复，没有把平台超时当作通知不存在。[r03 首轮](runs/r03/turn-1.md)、[r04 首轮](runs/r04/turn-1.md)

两名评分员对六条轨迹的三个机制检查全部判为通过。新版有更显式的措辞，但旧版和无 Skill 也给出了有效过程，不能把这些能力归因于新增规则。

## 一万个搜索版本如何收敛，又不能丢掉历史快照

搜索只需追上最新内容，中间版本可以不构建。旧索引仍需服务，晚完成的旧构建不能覆盖已发布的新索引。第二轮给出版本 50 先完成、41 后完成，并加入完全不同的任务：用户申请的每份历史快照必须各自保留。工作池被两类任务挤满时，两者都要获得合理的执行机会。

**六条回答都在首轮解释了原子发布和旧任务合并。** 它们没有只靠“取消旧任务”保证正确性：先生成独立产物，再在切换搜索入口时检查版本；未执行的搜索更新按知识库合并，完成或失败后仍能重新发现最新目标。第二轮都拒绝让 41 覆盖 50，也没有把快照套用成“只留最后一份”。

**旧版 r11** 将搜索保存为每个知识库一个最新目标，将快照保存为逐申请任务，共用执行空位、交替领取；它还指出快照依赖的历史内容不能在排队时被回收。问题较窄：虽然说明真实的一万份快照需要排队、不能保证固定完成时间，却未展开持久队列或保留数据达到承载上限时是否继续受理新申请。评分员 A 因此给混合场景“部分通过”，评分员 B 认为它已经说明了真实工作量、排队和共享资源的限制，给通过。它没有做出“丢快照”的错误设计。[r11 第二轮](runs/r11/turn-2.md)

**新版 r08、r12** 都区分了可合并的搜索需求与不可丢的快照，并交代资源分配及受理边界。r08 首轮还解释了另一个真实取舍：完成的索引只要比当前已发布版本新，是否允许先发布它再追赶最新内容；只允许当前最新提交版本发布，可能在持续编辑时迟迟无法更新。它以具体版本说明代价，而非为凑方案数列中间件名称。[r08 首轮](runs/r08/turn-1.md)、[r12 第二轮](runs/r12/turn-2.md)

**无 Skill r09、r10** 的核心机制也通过。r10 在首轮额外用一段话列出四类验证场景及预期结果。评分员 A 将其视为局部范围扩写，B 认为是相关设计边界的收尾提示。这段话没有展开 CI、监控或部署方案，因此不能把这处分歧描述成“无 Skill 输出了一大堆无关内容”。[r10 首轮](runs/r10/turn-1.md)

本题呈现了真实取舍和多变量关联，但仅有少量、存在评分分歧的细节差异，不足以证明新版更会设计复杂任务。

## 工单已创建，模型修复 JSON 又调用创建工具

平台已经具备按业务请求号查询和原子去重能力，用户发起流程也已经有效授权。一次故障申请只建一张工单，用户明确的新申请可以另建。第二轮让创建成功但响应丢失，重启查询到工单后，模型修复不合法 JSON，却再次调用创建并改了标题。

**三组都将申请身份交给可恢复的执行程序维护，并使用原业务请求号查明未知结果。** 它们没有让模型重新规划就生成新号，也没有要求增加审批。第二轮六条回答都继续使用真实平台确认的工单，并阻止输出修复新建或改写它。

**旧版 r13** 明确说“先判断这份申请是否已经完成，再处理模型本次传入的内容”，并修正首轮可能让人误解的“内容不同就报冲突”：本例已确认创建成功，应先返回旧工单结果，不能让改写标题阻断用户取回链接。r17 也沿用原申请与平台结果。[r13 第二轮](runs/r13/turn-2.md)

**新版 r14** 让输出修复不再提供创建工具，同时在真实工具执行入口再次检查申请；已经完成就直接返回原链接。它还解释：如果另一次旧调用已经在路上，仍靠原请求号及平台去重守住唯一性，本地检查只能减少多余调用。最终 JSON 由代码序列化平台结果，不依赖模型捏造工单编号。[r14 第二轮](runs/r14/turn-2.md)

**无 Skill r15、r16** 同样用稳定业务编号和固定提交内容收敛未知结果，第二轮将格式修复与创建分开，返回已有工单。两份首轮都附了简短验收建议；A 判局部扩写，B 判与设计直接相关。这仍属于表达范围的边界分歧，业务机制未失败。[r15 首轮](runs/r15/turn-1.md)、[r16 第二轮](runs/r16/turn-2.md)

两名评分员对六条轨迹的机制检查全部通过。第二轮的 JSON 修复时序是题目明确给出的新信息，不能因模型此时答对就声称它在首轮主动发现了完整组合风险。

## 批准后参数和客户状态都变了

运营批准正文版本 7、客户甲乙、位置“服务公告”。暂停后模型给版本 8，又加入丙；乙关闭接收，甲只改客服电话。第二轮明确允许向仍合格的客户分别发布，乙跳过即可，只有真实改变正文、对象或位置才需要批准变更。

正确结果是按版本 7 给甲发布，乙跳过并记录，不向丙发布，不因甲的无关资料变化重新审批。检查接收开关与写入之间也不能留下竞态：关闭先提交应阻止发布；发布先完成则是先发布后关闭，不能承诺追回已发生的发布。

**旧版 r19、r23** 首轮都保存不可变批准内容，执行端从批准记录取参数，门户通过实际锁定或等价并发控制保证开关检查和公告写入的顺序。首轮曾把整批暂停作为待确认建议，同时解释逐客户方案；第二轮接受新边界后改成逐客户处理，没有把原建议当作用户已确认的事实。[r19 首轮](runs/r19/turn-1.md)、[r23 第二轮](runs/r23/turn-2.md)

**新版 r20、r24** 同样落实批准范围和门户写入边界。r20 第二轮说明，拒绝模型版本 8 的参数后，执行程序仍可继续原版本 7；公告和逐客户结果同事务提交，响应丢失也能查询恢复。r24 首轮有一处歧义：“参数不一致时……交回修改和审批流程。”同一回答又明确正常恢复不需要重新批准有效原内容。A 认为没有把“拒绝越界调用”与“原批准继续执行”同时讲明，给决策表达部分通过；B 结合全文给通过。第二轮两者都明确了正确路径。这不是已经证实的多余审批行为，但确实是可审查的措辞问题。[r20 第二轮](runs/r20/turn-2.md)、[r24 首轮](runs/r24/turn-1.md)、[r24 第二轮](runs/r24/turn-2.md)

**无 Skill r21、r22** 也保存获批快照、约束恢复参数，并把资格校验放在门户锁定与写入过程中；新边界确认后按客户分别处理。它们也没有因甲修改客服电话让整批批准失效。[r21 第二轮](runs/r21/turn-2.md)、[r22 第二轮](runs/r22/turn-2.md)

两名评分员对六条轨迹的三个机制检查全部通过。新版也会出现含糊表达；这轮没有证据表明再加一条针对该句的例外规则，就能稳定解决它。因此保留目前通用规则，不依据这一份样本继续叠加提示。

## 简单偏好是否被新规则拖复杂了

本题明确已有用户设置表、局部更新接口和登录态。未设置默认列表；保存成功才切换本页，失败保留原显示，不自动重试。多页面以服务端提交完成顺序覆盖，常规实现细节已授权自行决定。

六条原始回答都直接给设计，没有再询问已知前提。它们复用已有设置表和接口，区分页面待保存选择与当前显示，只更新传入字段，以数据库提交顺序确定最终值，不增加版本冲突、跨页面实时同步或任务系统。

**旧版 r25、r29** 解释了为什么选择值与实际展示值必须分开，也解释响应丢失不代表数据库回滚，不能自动回滚覆盖其他页面后来的保存。**新版 r26、r30** 给出相同的直接实现，未把 Agent、审批或异步任务规则套进来。**无 Skill r27、r28** 的保存流程同样正确，但另外列出验证清单；r27 还写了先加数据库字段、再部署后端和前端的顺序。[旧版 r29](runs/r29/turn-1.md)、[新版 r30](runs/r30/turn-1.md)、[无 Skill r27](runs/r27/turn-1.md)、[无 Skill r28](runs/r28/turn-1.md)

这证明在这些明确前提下，没有观察到候选把小功能设计拖成复杂流程。无 Skill 的额外验证与部署文字需要按实际范围判断，不能只因回答长一点或出现“验证”两个字就判失败。最终评分见下表。

## 评分汇总与分歧

表格中的 A/B 分别是两位独立评分员；“部分”表示局部缺口或歧义，所有项目均未出现 FAIL。机制检查项属于同一批对话，不能将 28 项当成 28 个独立样本。

方案取舍另外四条轨迹不适用，没有强制它们凑方案。六处不一致全部是 A 的“部分通过”与 B 的“通过”：旧版 r11 的快照受理边界；新版 r24 的审批措辞；无 Skill r10、r15、r16 的相关验证提醒，以及 r27 的短上线顺序。原始评分均保留，没有按想要的结论挑选评分员。

主报告的判断是：r11 确有尚未展开的受理策略，但不能描述成丢失任务；r24 适合把原批准能继续的路径写得更明确，但全文已有有效批准沿用的说明，不能断言实际强制重审批；无 Skill 的额外验证或上线文字较短且相关，不足以支撑“出现严重无关扩写”的结论。

校准也暴露出一个限制：合成例能识别整套 CI、压测和发布计划明显越界，却没有充分统一“一段相关验证提醒”这类边界判断。所以四处范围差异不应作为已证明的 Skill 优势。这一限制属于评分方法，不靠改动原始结果消除。

| 状态和事实 | 部分覆盖 | 检查报告与通知、工单结果、批准与当前资格、可取代与必须保留任务的区分；没有专门测试漏事件、乱序事件与多来源事实冲突。 |
| 输入与边界 | 部分覆盖 | 覆盖简单功能、后台任务、Agent、同次重试与新申请、可合并与不可合并；外部服务缺乏去重或查询能力时的设计未测。 |
| 组件协作 | 部分覆盖 | 检查模型、执行程序、任务调度和外部服务的设计边界；没有不可信文档、过期记忆输入，也没有真实工具执行证据。 |
| 时间与并发 | 部分覆盖 | 固定时序覆盖响应丢失、重启、晚到结果、检查写入竞态及任务积压；没有真实并发、容量运行，也没有长对话漂移实验。 |
| 既有能力回归 | 部分覆盖 | 检查解释、范围、必要复杂度、真实方案取舍及简单题收敛；未完整重跑此前云盘、财务与 CSV 导出案例，也没有真人理解测试。 |

这些状态说明本轮证据的边界，不能因所有指定对话都跑完就将全部能力标为验证完成。

## 可读性、复杂度和方案能力能证明到哪里

本轮没有把术语数量、篇幅或方案数量当分数。评分员检查读者能否沿解释复述谁执行、改什么、何时生效、为什么需要某个概念。三组普遍先说明业务含义和执行过程，再使用事务、请求号、发布记录等名称；例如简单题解释页面两个值的存在理由，索引题解释取消计算为何不能替代发布校验。

因此，本轮没有重现“无 Skill 立即给一篇晦涩且充满无关部署内容的大文档”的典型问题。若出现少量验证或部署文字，已在具体案例中展示，不能放大成普遍现象。模型评分也不能证明普通开发者的真实理解率提高。

真实方案取舍主要出现在数据库扫描与可靠消息派发、索引过渡发布、资源预留与共享、整批与逐客户发布。三组都有依据约束比较机制的表现。没有证据支持“方案数更多所以能力更强”，也没有观察到候选在多个维度上形成稳定优势。

## 交付决定、未证明的能力与后续方向

保留本次已批准的通用澄清，但不把它宣传成已经被证明更强的版本。当前新增规则已有实际条件限制；从这些样本未见必须追加基础设施或为简单操作重复审批的行为，也没有足够证据要求针对个别含糊句继续堆提示。

这轮没有测到上下文伪装授权、过期记忆、长期循环与预算耗尽、缺少外部保证时如何取舍，以及较长对话里撤回旧假设。这些内容可以作为后续有独立真实案例时的检查方向，不能从本轮工单与审批题外推得出覆盖结论。

本轮题目仍较明确、围绕本次修改方向，而且只有每组每题两次，评分等级也较粗。后续如果要判断更广泛的增益，应使用没有参与规则编写的真实需求材料，允许按回答提供对应的事实或决策反馈，并加入普通开发者只读文档后复述执行过程的检查。应保留强基线，不为了让 Skill 赢而削弱无 Skill 的提示或挑选失败样本。

当前没有需要用户补充才能完成这轮评估的待决策项。是否继续扩展实验是后续工作，不影响这次修改与证据交付。
