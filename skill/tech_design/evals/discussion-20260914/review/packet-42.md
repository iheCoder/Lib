## 第 1 轮用户

请使用提供的 tech-design skill，基于需求文档和两个交互原型，与我进行这个需求的技术设计。

需求文档是多轮修订的产物，以下已确认口径覆盖其中仍残留的旧文字：
- 分类没有图标，也不需要返回分类下模板数量；模板有图标。
- 模板用于准备输入内容与默认资源；用户可以编辑正文并增删资源。发送以用户最终内容和资源为准。
- 发送时模板 ID 只用于尽力统计。模板已停用、删除、版本发生变化或统计失败，都不能影响已经准备好的正常对话发送；不要求模板专用幂等 ID，不追求无遗漏无重复的精确统计。
- 用户可配置个人常用窗口、次数和展示条数，按需求文档第 12 节；收藏不返回失效占位。
- 参数交互参考首页原型中正文内填写、选择和正文可编辑的实际表现。原型中多选、单选、下拉都在本期范围内，不包含“猜你要用”。
- 多个管理员可以操作同一租户，需要处理并发排序时旧页面覆盖新顺序的问题；具体实现尚未确定。

现有系统背景：后端主要是 Go，Anchor 提供 HTTP 接口并持有业务数据，使用 MySQL；Organization 提供部门、祖先部门与人员标签查询，现有资源可见范围可以按资源身份复用。已有对话链路为 Anchor 准备 Skill、召回知识库，然后调用 Maestro；模板不能赋予额外资源权限。模板相关旧代码和技术设计不作为本次标准。

## 第 1 轮助手

我理解，这次要做的是一套“维护模板 → 发现模板 → 准备输入 → 进入现有对话”的能力。模板保存提示词、参数和默认资源；用户编辑完成后，最终正文和资源就成为一次普通对话输入。你已确认的口径直接作为设计前提，原型里发送前重新校验模板状态、版本，以及收藏失效占位等旧行为不沿用。

我建议整体按下面这条流程组织：

1. **管理员维护模板。** 分类负责归类和顺序；组织模板保存内容、参数、资源绑定和可见范围。个人模板复用内容与参数能力，但归属本人，不进入组织分类和管理统计。
2. **Anchor 返回用户可以选择的模板。** 根据当前租户、模板状态以及 Organization 提供的部门、祖先部门和标签判断组织模板可见性；个人模板只查询本人。资源权限不参与模板列表过滤，详情里能够识别的资源失效原因单独提示。
3. **选择模板后，在正文内准备输入。** 首页原型实际是正文中嵌入填写或选择控件，周围正文仍然可编辑，所以不能做成独立参数表单后一次性拼接。前端需要保留这次取到的正文、参数定义和默认资源，支持文本、多行文本、下拉、单选、多选；已有草稿时，先确认替换。
4. **发送用户最终整理好的内容。** Anchor 使用最终资源列表准备 Skill、召回知识库，再进入 Maestro。用户删除的默认资源不能被补回来；发送不依赖模板当前是否存在、启用或更新，也不为验证参数重新读取最新模板。
5. **在对话真正受理后尽力记使用。** 模板 ID 作为附带的统计来源；统计失败不改变对话受理结果。最终保留的知识库如果不可用，由会话链路写入可理解的助手消息并结束本轮；系统故障与权限问题区分，不能把“已受理”展示或统计成“执行成功”。

这里有一个需要后续查证的现状：**现有对话链路在哪一步能够确认任务已经被接受，以及在哪一步能够写入助手错误消息。** 材料只给了 Anchor 到 Maestro 的大致链路，不能据此认定 HTTP 入口返回、某条记录落库或 Maestro 收到请求就满足这个条件。统计接入点要跟着这个事实走；目前没有理由为了统计增加模板专用幂等协议或可靠投递体系。

接下来真正影响方案的地方，我认为有三处。正文可以编辑，意味着要讨论用户删除参数控件、重复出现同名参数时，如何避免丢改动或留下无法发送的草稿；多管理员排序需要防止旧页面覆盖新顺序；收藏排行榜要求逐个收藏用户按**当前可见性**计数，不能直接对收藏表做一次计数就认为结果正确。这些会分别影响前端编辑模型、数据库写入边界和查询成本。

**这一轮我想先和你确定并发排序的处理方式。** 这个选择会直接决定后台接口和存储需要承担多少协调成本。

例如，甲、乙都打开了顺序为 A、B、C 的分类列表。甲先改成 C、A、B；乙还停留在旧页面，把 B 移到 A 前面。如果乙把自己的整个列表直接保存，甲的结果就会被覆盖。仅在写数据库时加锁也不能识别乙看到的是旧页面：锁只能让两次写依次发生。

我的推荐是：**每份可排序列表带一个顺序版本，旧版本提交失败，界面刷新最新顺序，让管理员重新调整。**

具体到一次拖动：

- 页面读取顺序时，一并拿到该列表的版本。
- 提交新顺序时带上这个版本。Anchor 在同一个 MySQL 事务里检查版本、保存顺序并推进版本；版本已经变化，就不写入本次顺序。
- 甲保存成功后，乙收到“顺序已被其他管理员修改”，界面展示甲保存后的顺序，乙可以在此基础上再移动。
- 分类排序的范围是当前租户的分类列表；模板排序的范围是某个分类下的模板列表。两个管理员分别调整不同分类里的模板，不需要互相冲突。
- 新增、删除、移入或移出会改变列表成员，也必须让对应顺序版本变化，否则旧页面仍可能漏掉新增项。只修改名称、正文则不必使排序失效。

这需要保存少量用于识别列表变化的版本信息，并让改变列表成员的操作遵守同一事务规则；它换来的结果很明确：不会静默丢掉另一位管理员已经保存的顺序。排序接口成功也表示新顺序已经提交数据库，而不是仅收到了请求。

另一个方向是只提交“把 B 放到 A 前面”，由服务端在最新顺序上执行。这能减少管理员重试，但服务端要决定怎样合并旧页面上的移动意图，最终顺序可能与管理员拖动时看到的结果不同；如果 A 同时被移走或删除，还要进一步约定处理方式。目前我更倾向前一种，因为它容易解释，也更容易验证。

你希望采用“发现顺序已变化，就刷新后重新调整”的方式，还是更看重连续拖动时少被打断，愿意接受服务端把移动操作应用到最新列表？

## 第 2 轮助手

排序就按刚才的推荐继续：按租户分类列表、分类内模板列表分别维护顺序版本，冲突时保留已提交结果，刷新后重新调整；列表成员变化也要参与版本更新。

接下来讨论**正文内参数怎样编辑，以及最终发送什么**。这里最需要避免的是：用户已经修改了正文，填写一个参数后，系统又用原始模板重新生成整段文字，把用户的修改覆盖掉。

我的建议是把“保存的模板”和“本次编辑的草稿”分开理解。

保存模板时，Anchor 保存提示词原文和参数定义。例如：

```text
请为 {{客户名称}} 整理方案，重点覆盖 {{关注内容}}。
最后给出适合 {{客户名称}} 的下一步建议。
```

这里有三个占位位置，但只有“客户名称”和“关注内容”两个参数。参数定义只需要解释当前交互必需的信息：参数名、控件类型、是否必填，以及选择类参数的选项。“客户名称”可以是文本，“关注内容”可以是多选。

**提示词与参数定义建议作为同一份模板内容一起保存。** Anchor 在保存时检查二者一致：正文中使用的参数都存在，定义中没有悬空参数，参数名不重复，选择类参数配置有效选项。正文和参数定义应同时成功或同时失败，避免用户拿到正文已更新、参数还没更新的组合。参数定义可以存为模板记录中的 JSON；目前没有按某个参数跨模板检索的需求，无须为每个参数单独建表。

用户选择模板后，前端把正文展开成普通文字和参数控件。这个结构只服务当前编辑过程，不把浏览器生成的 HTML 当成模板内容交给后端保存。

沿上面的例子，编辑过程这样运行：

- 用户填写一次“客户名称”，两处同名参数同步显示同一个值；同名参数不能各自变成不同客户。
- 用户把“整理方案”改成“整理售后回访方案”，之后再选择“关注内容”，只更新对应参数控件，保留已经改过的正文。
- 下拉和单选都保存一个选项值，只是交互形式不同；多选保存多个选项值，生成正文时按配置中的选项顺序用“、”连接。多行文本保留换行。
- 发送前，将当前编辑内容按出现顺序转成最终文本。普通文字取用户编辑后的内容，参数位置取当前填写值；不会重新套用原始提示词，也不会读取服务器上的最新模板再拼接。
- 最终资源列表与正文一起进入现有对话接口。前端不需要为了执行模板，额外要求后端根据模板 ID 还原参数或补齐默认资源。

这里要共同确定的是**参数控件被删掉时的行为**。这不是纯实现细节：它决定“正文可编辑”和“必填参数不能遗漏”如何同时体现。

我推荐保持以下规则：

1. 必填参数还在正文中但没有填值，提示对应项并阻止这次发送。
2. 同名必填参数出现多次，用户删掉其中一处，剩余位置仍存在且已填写，就可以发送。
3. 用户把某个必填参数的最后一处控件也删掉，仍提示该项缺失，并提供“补回此参数”的操作；只补回这个控件，保留其他正文修改，不要求重新选择整份模板。
4. 选填参数可以直接删除；保留但未填写时，生成正文为空值，不自动插入“未提供”等用户没有写过的文字。
5. 用户主动解除模板关联后，将已填写内容转为普通文本，未填写控件移除，后续按普通输入编辑和发送，也不再携带该模板的统计关联。

例如，用户误删了最后一个“客户名称”，我们不会要求他把已经写好的售后回访方案全部重填；他可以补回客户名称，也可以明确解除模板关联，自行组织普通正文。

**这些必填检查属于模板辅助编辑的规则，由前端根据本次草稿中的参数定义执行。** 后端仍负责正常对话输入校验和真实资源权限校验，但不把“必须符合某个模板参数结构”变成对话发送的新前置条件。这样，管理员更新或删除模板后，已经准备好的草稿仍然能按原来的编辑内容发送，也符合模板 ID 只用于尽力统计的口径。

这套处理本身不需要查询大量数据；前端成本随正文长度和参数出现次数增长。材料没有给出可靠的容量数据或已经确认的正文、参数数量上限，我不会直接把原型里的演示限制当成业务约束；如果后续发现超长正文或大量重复参数是实际场景，再据此确定必要限制。

本轮的关键建议是：**删除最后一处必填控件仍保留填写要求，但允许局部补回；主动解除关联则转为普通正文。** 你认为这个行为是否符合用户在正文里自由修改的预期？

## 第 3 轮助手

正文参数按上一轮建议继续。接下来把模板本身怎样保存、谁能看到，以及资源绑定怎样保留放到同一条读写流程里讨论。

**我建议组织模板与个人模板共用一张模板表，以明确的归属条件区分。** 两者都保存名称、描述、图标、正文、参数和默认资源；区别集中在谁能管理、谁能看到，以及是否属于业务分类。这样收藏和使用记录可以直接关联同一个稳定模板 ID，组织模板换分类也不会换身份。

这张表的重要业务信息可以分成三组：

| 信息 | 存在理由 |
| --- | --- |
| 租户、组织或个人类型、个人所有者 | 服务端确定数据归属；个人模板的读写必须同时限定租户和当前用户，管理员身份不能绕过所有者条件 |
| 分类、启停、分类内顺序 | 只服务组织模板；个人模板不进入组织分类，也不需要组织模板的启停流程 |
| 内容、参数定义、默认资源、删除标记、修改版本 | 保存当前模板；删除后普通查询不可见；修改版本用于避免多个编辑者相互覆盖，不代表建立历史版本库 |

分类单独保存名称、描述和顺序，不含图标、模板数量、启停或可见范围。租户内未删除分类名称必须唯一，固定入口名称由 Service 校验；唯一性也要有数据库约束兜底，不能只靠“先查重再插入”，否则两个管理员同时新增仍可能重名。软删除后如何表达仅有效记录唯一，需要结合实际 MySQL 版本确定索引写法。

模板列表主要按租户、类型、分类、顺序读取；“我的”按租户、所有者读取，索引围绕这两条路径设计。可见范围会影响最终筛选方式，暂时不把一个未经验证的复合索引宣布为完整方案。

**可见范围复用现有按资源身份管理范围的能力。** 组织模板作为一种资源保存“全员”或部门、标签范围，不再另建一套人员授权名单。用户属于子部门时，用其所在部门及祖先部门匹配配置；部门命中与标签命中按并集处理。

例如，模板范围配置为“销售部或重点客户标签”。用户在销售部下属的华东组，即使命中不了标签也可以看到；另一位用户不在销售部，但有该标签，同样可以看到。Skill、知识库是否可用不进入这个判断。

查询还有两个容易出错的地方：

- **必须先按可见性筛选，再确定分页结果。** 不能先取 20 条模板，再过滤成 3 条，就当作完整的一页。现有范围能力能否参与数据库过滤、是否支持批量判断，材料没有说明，需要查证后选择具体查询方式。
- Organization 查询失败不能当成“用户没有部门和标签”，返回看似正常的空列表；无法确认的范围应提示暂时无法加载。这个失败只影响继续浏览相关模板，不重新阻塞已经准备好的正常对话发送。

同一请求内可以复用用户的部门、祖先部门和标签结果，避免每个模板都重复查询。跨请求缓存会涉及权限变更多久生效，目前先不额外引入缓存和失效通知机制。

然后看默认资源。我建议**只保存资源身份，不把“当前可用”永久保存在模板里**。资源身份沿用现有链路能够识别的 Skill、知识库标识；不能先假定所有来源的资源仅凭一个数字 ID 就能唯一定位。

两类资源各最多 50 个，而且当前主要读写方式是随模板整体加载、整体保存，可以先与参数一样保存为 JSON 数组；没有反向检索需求时，不必先增加绑定关系表。保存时对各自的资源身份去重，再分别检查数量上限。资源名称和失效状态在详情、编辑时按当前访问者查询；服务无法确认时返回“状态暂无法确认”，不能把查不到一律解释成“已删除”。

**保存模板时，“新增绑定”和“保留原绑定”必须分开校验。**

假设原模板绑定知识库 K1、K2。管理员已经失去 K2 权限，这次只修改了正文：

1. Anchor 从数据库读取原绑定 K1、K2。
2. 保存请求仍保留 K1、K2；这两项不是新增绑定，不因管理员现在看不到 K2 就删除或拒绝保存。
3. 如果请求增加 K3，只对新增的 K3 检查当前管理员是否有权选择。
4. 如果管理员明确移除 K2，就保存移除后的结果。

这里的“原绑定”必须以服务端读取的记录为准，不能相信客户端把任意资源标成“原来就有”。界面也必须完整保留已绑定资源身份；不能用资源选择器当前能搜到的结果覆盖整个绑定集合。

多管理员编辑时，再用模板自身的修改版本保护这次保存。例如乙打开旧模板后，甲增加了 K3；乙随后保存旧集合，不能把 K3 静默删掉。Anchor 在事务中按读取版本更新，版本不匹配就保留乙的编辑稿并提示冲突。这个版本与之前确认的**列表顺序版本分开**：正文编辑不会无故使别人正在进行的排序失败，排序也不会覆盖正文。

“另存为我的”需要一个明确的服务端复制操作，因为它允许保留普通用户当前无权使用的源资源：

- 用户提交源组织模板身份和读取时版本；Anchor 检查源模板当前仍对该用户可见。
- Anchor 从源记录取得完整内容和绑定，包括已失效或用户无权使用的资源，创建独立的个人模板身份。
- 返回复制结果时附带能够识别的资源状态；无法使用的资源也不丢弃。
- 用户自行新增的资源仍按本人可见性校验，不能利用“复制”给任意隐藏资源建立绑定。
- 如果源模板在用户打开后发生了修改，建议保留用户正在编辑的内容，提示重新核对源模板，不悄悄换成另一份内容再保存。这是创建个人模板的保存冲突处理，不影响用户把已有草稿作为正常对话发送。

这一轮还有一个需要落实到数据库事务里的并发边界：删除空分类与新增、移入模板可能同时发生。删除时查到“空”还不够；删除分类与向该分类写入模板，必须通过同一分类记录协调，在事务中重新检查分类未删除和是否为空。它可以复用分类内排序操作所用的协调位置，避免最后出现“分类已删除，但里面刚放进一个模板”。

上述模型和写入方式是本轮的建议。接下来值得展开的是收藏和使用数据：收藏有效性要求读取时重新判断，使用统计则允许少量遗漏，两者不能套用同一种保障强度，尤其不能为了排行榜把组织查询成本传到对话发送上。

## 第 4 轮用户

你已经解释清楚的建议可以按推荐继续；尚未展开的设计还没有确认。请按你认为合适的顺序继续讨论。规模目前没有可靠实测数据，需要时请明确假设。


## 第 4 轮助手

前面解释过的模板模型和写入边界继续沿用。这一轮讨论使用记录、常用与收藏，先明确它们各自保证什么。

**使用统计保证“只尝试记录已受理的发送”，但不保证每次都记到，也不保证绝无重复；收藏关系则需要明确保存成功或失败。** 用户点击收藏后，如果写数据库失败，应告诉用户这次没有收藏成功，不能像使用统计一样静默丢弃。

我建议使用统计先保存最小的明细记录：租户、用户、模板 ID、对话受理时间。用户和租户取服务端身份，时间取真正受理时刻，不能使用后台稍后写入的时间，否则跨午夜积压会改变“覆盖两个自然日”的结果。不保存提示词、参数值和资源内容，也不为统计创建模板专用提交幂等 ID。

具体记录过程建议这样接入：

1. 对话链路先完成原有受理动作；这个动作的准确位置仍需查证。
2. 在确认受理后，把上述几个标量交给后台记录入口，不等待统计写入。
3. 如果已有后台入口能做到不阻塞投递，优先复用；否则使用进程内有容量上限的队列，由少量固定工作协程写 MySQL。队列满、进程退出、写入失败都允许漏记，不回滚对话，也不要求用户重发。
4. 数据库写入使用独立的短超时，不能继承一个已经取消的 HTTP 请求上下文。这里独立的是统计工作的执行期限，不是让它无限重试。
5. 统计处理可以检查模板是否属于该租户、个人模板是否属于该用户；无效来源直接丢弃统计。停用、软删除不必拒绝同租户的历史来源，统计检查始终不影响对话。

这样只增加有限的后台工作，不建立可靠投递或补偿系统。异步仍会消耗数据库资源，不能因此承诺“零影响”；写入并发和等待时间应受限制，避免统计积压不断扩张。具体并发值目前没有实测依据，暂不写死为性能承诺。

HTTP 重试可能造成重复记录，我们接受这个边界。如果现有对话链路已经能够识别同一次发送，就复用它的“新受理”结果；不为了统计改造对话幂等协议。断点续流和重新生成不接入这段新发送记录逻辑；用户仍关联模板时，每次新的有效发送都继续携带模板 ID。

**个人常用直接基于这些明细计算，不另维护一份需要失效更新的“常用名单”。**

查询时取本人的最新设置：默认 30 天、至少 3 次、最多 20 条，允许范围沿用需求第 12 节；还要满足至少两个自然日。按模板 ID 聚合次数和最近使用时间，筛掉当前无效模板，再按次数、最近使用时间及稳定 ID 排序，最后截取展示条数。先截取再筛有效性，会漏掉本来应该补进来的模板。

个人设置单独保存一行，以租户和用户唯一定位；只保存三个可配置值，软删除后回退默认值。修改设置立即影响后续查询，不重写使用记录。

时间口径我建议分开：近 N 天按受理时间向前滚动计算；“两个自然日”按统一业务时区划分。当前讨论暂按北京时间举例，这是设计假设；如果产品已有统一时区约定，应沿用现状，不为模板另增一个时区设置。

管理端近 7 天、30 天次数、去重人数和每日趋势也从明细读取，只包含当前租户的组织模板。已停用、软删除的组织模板可以通过保留记录识别历史来源；个人模板不进入管理统计。

因此使用明细至少有两条重要查询路径：按租户、用户、时间查个人记录；按租户、时间查组织统计。相应索引分别服务这两种范围查询，模板 ID、用户 ID 是否作为覆盖列，要根据最终 SQL 和数据验证决定。记录量随累计使用增长，不会因为最多展示 50 条就只扫描 50 条；也不能未经需求许可就在 90 天后删除历史记录。

接着是收藏。**收藏表只保存当前关系，不需要记录每次点击事件。** 用“租户、用户、模板 ID”唯一约束，附带本次收藏时间：

- 收藏接口表达“设为已收藏”，重复请求保留原收藏时间，不把重试当成重新收藏。
- 取消表达“设为未收藏”，删除本人这条关系；重复取消仍然成功。
- 取消后重新收藏，创建新的收藏时间。
- 新收藏前检查模板当前有效；取消自己的关系不要求模板仍然可见。

这样同一用户同一模板天然只有一条关系。超过 30 天前收藏后一直保留的关系，不进入最近 30 天排行；最近取消后重新收藏的关系可以进入，但仍只算一个人，符合需求口径。

收藏列表、数量使用同一套有效性条件：组织模板当前启用、未删除且用户可见，个人模板归本人且未删除。先得到有效集合，再计数和分页，不返回失效占位。停用、失去范围时可以保留底层关系；恢复后会重新出现。资源失效不参与这层过滤。

**收藏排行榜最重的部分是判断收藏用户当前是否仍能看到模板。** 正确计算顺序是：

1. 读取当前租户近 30 天内建立、当前仍保留的收藏关系，先排除个人模板、已停用和已删除的组织模板。
2. 对剩余关系，按收藏用户当前部门、祖先部门和标签判断模板可见性；全员模板不需要逐人匹配部门、标签。
3. 对有效关系按模板计人数，再排序取前 10。不能先取收藏最多的 10 个模板再校验范围，否则第 11 名可能本来应该补入。
4. 同分建议按模板稳定 ID 排序，不额外引入评分字段。

一次查询内，同一个收藏用户的组织信息只取一次；若 Organization 有批量查询能力，应批量获取。当前材料没有证明存在批量接口，这是一个明确的待查证条件。

用数量级说明成本：**假设**有 1 万名收藏用户、每人 10 条近期收藏，候选关系就是约 10 万条；即使最终只返回 10 个模板，也不能忽略这 10 万条关系的有效性。如果逐人调用 Organization，最坏需要接近 1 万次人员查询；这不是可直接承诺响应时间的实现。我们应先查清批量能力与实际数据规模，再判断直接查询是否够用，而不是现在就引入跨系统权限镜像或允许排行变旧。

若本次查询无法取得必要组织信息，建议明确返回“排行榜暂不可用”，不把未知用户按可见或不可见计入，也不返回一个看似完整的错误排名。这样会牺牲故障期间排行榜的可用性，但保住已经明确的有效性口径；正常对话不等待这个查询。

“当前有效”按本次查询读到的已提交收藏和当前组织信息判断，不承诺跨 MySQL、Organization 的全局瞬时快照。查询开始前已完成的取消收藏应被排除；查询进行中发生的取消或调部门，可能在下一次读取体现。为消除这个极短竞态而跨系统锁住收藏、组织变更和查询，代价明显超出本功能需要，我不建议引入。

我建议这次采用明细统计、当前收藏关系和读取时有效性计算。尚需结合现状查证的关键条件已经比较集中：对话真正受理的位置、可见范围的批量筛选方式、Organization 批量查人能力，以及 MySQL 和现有时间口径。这里没有可靠规模数据，当前只能说明正确计算路径与成本增长方式，不能宣称性能已经满足要求。
