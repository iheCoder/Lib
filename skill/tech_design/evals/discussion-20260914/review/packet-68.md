## 第 1 轮助手

我的核心设想是：**Anchor 管理模板、可见范围和个人关系；模板把内容与默认资源交给输入框后，发送继续走现有对话链路。** 这样既能复用现有能力，也能落实你已经确认的“模板变化和统计失败不能影响正常发送”。目前我只核对了需求和原型，现有接口、表结构及事务边界都还不是已查证事实。

从用户操作到最终结果，整体流程可以先这样理解：

1. **浏览模板。** Anchor 根据租户、模板启停状态、部门及祖先部门、人员标签筛选组织模板，再按入口查询个人模板、收藏或常用。分类返回全部未删除分类，不带图标和模板数量；资源权限不参与模板是否展示的判断。
2. **准备输入。** 用户选择模板，拿到正文、参数定义和默认资源。正文中的参数直接填写或选择，支持文本、多行文本、下拉、单选、多选，正文也可以编辑。替换已有内容前确认；资源失效能识别时就提示。
3. **发送最终内容。** 前端把用户最终正文、附件、Skill 和知识库列表交给现有发送接口，不由后端重新根据模板拼装。模板停用、删除或变更，都不能触发原型 `send()` 中那种阻断发送的检查。
4. **接受与执行。** 系统接受任务后，才有一次可统计的使用；这不代表执行成功。Anchor 按当前用户权限准备 Skill、召回知识库，再调用 Maestro。知识库权限或资源失效导致本轮以明确的助手消息结束并写入历史；系统故障另作提示。使用统计失败不回滚或改变对话结果。
5. **后续查询。** 收藏和常用都结合查询时的模板有效性过滤；个人常用设置改变查询窗口和门槛，历史记录不重写。管理统计只覆盖组织模板。

我认为真正决定方案的有三个地方：

- **可编辑正文和参数的关系。** 原型允许编辑正文，但删除必填参数控件后仍会阻止发送。我们需要把“仍在填写模板”和“用户已转为普通正文”的具体行为讲清楚，避免后端为了验证参数重新依赖最新模板。
- **管理员并发排序。** 需要阻止旧页面覆盖新顺序，同时不能让排序与普通内容编辑、其他分类的操作无谓地互相等待。
- **当前可见性参与统计查询的成本。** 本人的收藏可以用一次本人组织身份查询过滤；收藏排行榜却要求检查每个收藏用户当前是否仍可见，不能只聚合收藏表就宣称满足需求。Organization 是否有合适的批量查询能力，是后面需要查证的条件。

发送独立于模板这一点已经确定，不需要再讨论是否放宽。**本轮我建议先确定并发排序的处理方式**，因为它会直接决定后台接口、顺序数据和相关事务怎样组织。

例如，管理员甲、乙都看到同一分类里的 `A、B、C`。甲先保存为 `C、A、B`；乙仍在旧页面，把 B 上移，提交 `B、A、C`。如果后台直接覆盖整份顺序，甲的结果就丢了。

我推荐让页面读取顺序时，同时拿到一个“这份列表的排序版本”；保存时带上它。服务器在一个事务里核对版本并保存顺序，成功后递增版本。甲先保存成功，乙随后带来的旧版本就被拒绝，页面展示最新顺序，提示乙重新操作。**检查和写入必须在同一事务内完成**，不能先查版本、再无条件更新，否则两次请求仍可能同时通过检查。

保障和影响范围也要一起限定：

- 全租户的分类顺序是一份列表；每个分类内部的模板顺序各是一份列表。分别校验和协调，两个管理员调整不同分类里的模板不需要争抢同一把租户级锁。
- 普通名称、描述或提示词编辑不改变排序版本。它们的保存接口也不能顺手写回旧的排序位置，避免从编辑接口绕过排序保护。
- 新增、删除和跨分类移动会改变列表成员，需要参与相应列表的版本更新。跨分类移动涉及源、目标两个分类，按固定顺序协调并在同一事务内完成；删除空分类的检查也必须与往该分类添加或移入模板的操作协调，防止“检查时为空，删除时已非空”。

这一方案的代价是：**同一分类内即使两人调整不同模板，后提交的人也可能需要刷新重做。** 换来的是规则直观，不需要后台猜测管理员在新顺序下的意图。另一种方向是提交“把 B 放到 A 前面”，由后台基于最新顺序执行；它可以减少某些冲突，但还要定义目标被移动、删除及连续拖动交错时的结果，目前我更倾向前一种明确拒绝旧顺序的方式。

存储上，这个选择意味着需要顺序位置和按上述范围独立的排序版本；还不需要因此给所有模板内容套上统一的大版本机制。若每次提交完整顺序，校验和可能的更新成本会随该列表长度增长，不能把整个租户的模板都读写一遍。实际每分类模板量尚未提供，后面再据规模决定是否需要缩小写入范围。

你是否接受这个冲突体验：同一份列表被别人改变后，本次排序不自动合并，展示最新顺序并让管理员重新操作？

## 第 2 轮助手

排序按刚才已经展开的推荐继续：按列表分别保护顺序，旧版本提交冲突时刷新重做，普通内容编辑不改排序位置。规模暂不作吞吐和耗时承诺。

接下来先讨论**参数填写到实际发送的过程**。这一段决定前端需要保留什么、模板保存时校验什么，以及对话接口为什么不用重新读取模板。

以“请面向 {{受众}}，用 {{表达风格}} 撰写通知”为例，受众支持多选，表达风格是单选；其他模板也可以使用下拉、单行和多行文本。我的建议是：模板在 Anchor 中保存提示词原文及对应的参数定义，包括参数名、类型、是否必填和选择项；它们共同描述可重复使用的输入方式。用户填写的值和修改后的正文属于本次草稿，不写回模板。

保存模板时，Anchor 校验占位符与参数定义相互对应、参数名不重复、选择类型有有效选项等，避免管理员保存一个无法填写的模板。同一个参数在正文中出现多次，可以对应同一份定义和同一个值。这里保留文本和必要的参数定义即可，不需要把原型的浏览器 `innerHTML` 当成后台存储格式。

用户点击使用时，前端获得这次读取的正文、参数定义和默认资源，在输入框里显示可填写的位置。之后同时保留两类信息：用户正在编辑的正文，以及各参数的填写状态。用户在参数之间新增一段话、删除原有说明，发送时都要保留这些改动，不能再拿原模板做一遍替换，把正文恢复回去。多选结果可以沿用原型，用“、”连接为最终文字；单选和下拉都是一个选择值，只是交互不同。

**必填校验只约束仍处在模板填写状态的草稿。** 我推荐保留原型已经表现出来的行为：

- 必填参数为空时，发送前定位并提示补充；不能只看正文是否非空。
- 用户误删了必填参数控件，也不能假装该参数已经填写。界面应提示缺失，并提供恢复这个填写位置的操作，保留用户其他正文改动。原型要求重新点击模板才能恢复，这会重新引入覆盖草稿的问题，不建议直接照搬。
- 用户如果决定完全自由写，可以显式“转为普通正文”：把已经填写的值留下，清理未填写的控件提示，解除模板关联，后续按普通对话发送。这样用户不必为了满足原模板的参数而填入没有意义的内容。

普通正文不能根据某个词是否还存在来反推“必填已完成”，因为用户本来就可以自由编辑文字。相应地，发送接口也不根据模板 ID 加载最新参数定义来拦截；最终输入内容继续满足普通对话接口自身的校验规则。模板保存的合法性、前端填写体验和最终资源权限，是不同位置承担的责任。

这也解释了模板变更时的行为。用户上午打开模板，已经填写一半；管理员随后把“受众”改成“对象”，或停用、删除模板。前端仍保留这次草稿的原定义和值，用户可以填完并发送。即使能够发现新版，也只能提供不阻断发送的更新提示，由用户主动重新取用；发现变更不需要成为每次发送的前置调用，更不能自动替换正文。已经准备好的默认资源同样不自动随新版变动。

资源部分沿这条流程处理：

1. 填入时，把模板预置的 Skill、知识库作为初始选择，保留能识别的不可用提示。用户可以删除它们，也可以通过现有资源选择器增加资源。
2. 发送时，提交最终选择的完整资源列表。比如模板有知识库 K1、K2，用户删掉 K1、加上 K3，Anchor 只能执行 K2、K3，不能再从模板补回 K1。
3. Anchor 按当前用户身份走现有处理链。详情中“可用”的提示只反映查询时状态，不能替代执行时的权限检查；资源可能在用户填写期间被停用或撤权。
4. Skill 沿用当前不可执行时剔除的规则。最终保留的知识库如果权限不足、删除或停用，本轮不进入 Maestro 的模型调用，由会话服务写入明确的助手消息；RAG 超时等系统故障用不同文案说明。

因此，这里有一个需要在现有代码中查证的衔接点：**对话被接受之后，知识库处理失败是否已经能够写入助手消息并结束本轮。** 背景说明了 Anchor 先处理资源再调用 Maestro，但尚未证明错误分支已经具备这项能力。设计上应把它接入真实会话处理流程，不能用 HTTP 返回错误或者“已收到请求”代替需求要求的会话结果。

模板关联期间的每次有效发送仍可携带模板 ID；转为普通正文后解除关联。统计只消费“对话已经被接受”这个事实，不能反过来决定上述正文和资源能否发送。具体在哪里确认接受、怎样尽力记录使用，下一步再结合常用和管理统计需要保存的事实展开。

这一轮需要确定的是草稿交互：**删除必填控件时保留模板填写约束，提供局部恢复；用户通过“转为普通正文”明确放弃参数约束并解除关联。** 你是否接受这个处理方式？

## 第 3 轮助手

草稿交互按上一轮的建议继续。这一轮讨论**使用怎样入账，以及怎样支持常用、使用人数和趋势查询**。我的推荐是：在对话确认接受后尽力更新统计；统计按“某用户在某天使用某模板几次”保存，不先建设逐次事件流水和可靠投递链路。

先明确两个统计假设：本轮暂按 UTC+8 划分自然日，“最近 N 天”指包含今天在内的最近 N 个自然日。这样“至少使用过两个自然日”、每日趋势和窗口边界可以用同一个口径。需求还没有明确最近 N 天是否必须精确到滚动的 N×24 小时，这个差异会影响能否只保存每日数据，不能留到写文档时才决定。

一次实际发送可以这样运行：

1. 对话服务照常校验、接受本次发送，得到已有的业务接受结果。模板统计不参与这个事务，也不提供前置成功条件。
2. 只有到达“本次发送已被接受”的位置，才尝试交给统计处理一条信息：当前租户、当前用户、模板 ID 和接受时间。租户与用户取自服务端身份上下文，不能相信前端自行填写的身份。
3. 统计处理在后台更新当日次数。没有模板关联就不产生这项统计；统计完成与否不改变发送结果。

这里的第一步需要查证现有代码：接受一轮发送究竟由哪段持久化或派发流程确认。仅收到 HTTP 请求、开始解析参数，或建立连接，都不能作为计数依据。如果资源处理在已接受之后失败，这次仍计使用；如果普通对话本身尚未接受就拒绝了请求，则不计。

**异步也有成本，需要限制统计自己的负担。** 我建议优先复用现有的有界异步处理能力；若没有，可以使用一个容量有限的进程内队列和固定数量的处理协程。发送侧只做不等待的入队尝试，队列满时丢弃该条统计；统计写入有超时，并限制占用数据库连接的数量，不能为每次发送无上限地启动协程。

进程退出、数据库异常、队列满都可能漏记；HTTP 重试若在现有链路再次触发了接受事件，也可能重复计数。这符合你已确定的统计口径，不新增模板专用幂等 ID、持久化消息队列或补偿状态。若已有对话去重机制能够准确区分“新接受”与“返回上次接受结果”，采集点应复用它，但不为模板统计重建一套。

后台统计可以核对模板是否属于该租户，以及个人模板是否属于该用户。停用和软删除记录仍可参与这一身份核对，不能要求模板当前启用或版本相同；查不到记录、归属不符或查询失败，就丢弃这条统计，正常对话已经独立进行。异步处理还应使用接受时记录的时间，不能用真正写入数据库的时间，否则跨午夜积压会把使用记到错误日期。

存储上，建议一张使用日统计表承担这些查询，核心业务信息只有：

| 信息 | 存在理由 |
| --- | --- |
| 租户、用户、模板身份 | 确定是谁使用了哪个模板，并隔离租户与个人数据 |
| 使用日期 | 支持窗口过滤、至少两个自然日、按天趋势 |
| 当日使用次数 | 同一天重复发送需要累加，不能只记录“用过” |

对“租户、用户、日期、模板”建立唯一约束。第一次使用创建一行，之后使用通过数据库原子累加更新次数，避免两次同时发送都读到 1，最后只写成 2。计数允许投递层面少量重复和遗漏，不代表数据库写入本身可以存在可避免的覆盖错误。

这一个模型就能直接支持：

- **个人常用：** 读取本人窗口内数据，按模板求使用次数之和，并检查有记录的日期至少为两天。套用用户自己的次数门槛，再与当前可见模板相交，排序后取展示条数；不能先取前 20 条再过滤失效模板，否则可能漏掉后面符合条件的模板。排序建议按使用次数降序、最近使用日期降序、模板 ID 稳定排序。
- **管理使用次数与趋势：** 只取当前租户的组织模板，按窗口求次数之和，按日期分组得到趋势。
- **管理使用人数：** 在整个查询窗口内按用户去重；不能把每天的使用人数相加，同一个人在多天使用仍然只是一人。

模板移分类不改变模板 ID，统计自然连续。已停用、软删除的组织模板仍保留可识别的模板记录，因此管理使用统计可以保留它们的历史数据；这里不能复用首页“只取当前可用模板”的过滤。个人模板即使有使用数据，也不进入管理员的使用统计。收藏排行榜则有自己的当前有效性要求，不能直接套用这里的统计口径。

索引也由这些查询推导：唯一索引可以按 `(租户, 用户, 日期, 模板)` 排列，服务本人窗口查询及累加定位；另一个索引按 `(租户, 日期, 模板, 用户)` 排列，服务管理端的租户窗口查询。暂不为没有出现的查询逐个加索引；每多一个索引，统计写入也要维护它。

个人常用配置则单独保存每个租户用户的一份设置，包含窗口天数、最少次数、最多条数和软删除标记。未配置或软删除时回退 30 天、3 次、20 条；修改设置只改变后续查询条件，不改日统计数据。7～90 天、2～20 次、6～50 条由 Anchor 校验，至少两天保持固定。

每日聚合减少了存储行数，但**没有自动减少写入次数**：每次被采集到的使用仍会更新数据库。行数随“每天实际使用过的用户与模板组合数”增长；个人查询扫描本人最多 90 天，管理查询扫描租户最多 30 天。当前没有实测规模，我不据此承诺响应时间，也不先增加缓存或第二层汇总。如果后面证据表明写入或窗口扫描太重，再针对真正的成本调整。统计与对话共用 MySQL 时，后台限流只能约束统计负担，不能消除数据库底层资源竞争。

这一轮真正需要取舍的是时间精度：**按自然日统计，可以用这一张日统计表直接支撑现有展示；如果“最近 30 天”必须精确到当前时刻向前 720 小时，就需要保留更细的时间数据。** 我推荐前者。窗口按包含今天的最近 N 个自然日计算，是否符合你希望的产品口径？


## 第 4 轮用户

你已经解释清楚的建议可以按推荐继续；尚未展开的设计还没有确认。请按你认为合适的顺序继续讨论。规模目前没有可靠实测数据，需要时请明确假设。


## 第 4 轮助手

时间窗口和日统计按已经展开的推荐继续。接下来讨论**模板可见范围、收藏关系和收藏排行榜**。这三件事应共用可见性判断，但不能共用一种简单的计数方式。

首先，组织模板的可见范围建议复用现有“按资源身份配置可见范围”的能力，将模板作为一种资源关联部门和人员标签。Anchor 保有模板身份、租户、启停和删除状态；范围配置继续表达“组织全员”或“指定部门、标签”，不另外把每个模板展开成一份用户名单。部门人员变化后，名单容易过期，维护同步也会增加另一套状态。

一次本人浏览请求中，Anchor 使用当前用户的部门、祖先部门和人员标签计算可见性。例如模板指定“研发部”或“项目经理”标签，用户所在子部门的祖先包含研发部，就已经命中；不需要同时具备项目经理标签。Skill 和知识库权限始终不加入这个判断。

建议把这项判断集中复用在组织模板列表、详情、收藏创建、个人常用和另存为个人模板的源模板读取中，避免列表隐藏了模板，详情或复制接口却仍能绕过范围。个人模板则直接要求租户和创建者都匹配；管理员身份不扩大个人模板的读取权限。已经准备好的草稿发送，仍沿用前面确定的独立发送边界。

这里可以在一次请求内复用同一份用户组织信息；暂不引入跨请求权限缓存。现有范围能力的存储形式、Organization 查询是否自带缓存以及刷新时效还没有查证，不能把“可以复用范围能力”理解成已经证明它满足所有接口和时效要求。

**收藏只需要保存当前关系，不需要复制模板，也不需要为了排行榜保存所有收藏动作。** 我的建议是一张收藏关系表，保存租户、用户、模板 ID 和这次开始收藏的时间，并对租户、用户、模板建立唯一约束。

- 收藏时，Anchor 先确认该用户此刻可以读取模板，再创建关系。重复提交收藏请求视为已经收藏，不刷新收藏时间，否则一次 HTTP 重试就可能把老收藏变成近 30 天的新收藏。
- 取消收藏时删除关系；即使模板已经不可见，也允许本人取消这条关系，不要求先读出模板正文。重复取消返回同样的取消结果。
- 重新收藏时创建新关系，使用新的收藏时间；唯一约束保证同一用户不会为一个模板贡献两个人数。
- 停用或暂时不命中范围时保留关系，查询时过滤；恢复有效后重新出现。模板软删除后，关系即使暂时保留也不能出现在有效查询中，因此本期不必增加删除模板时批量清理收藏的同步步骤。

举个时间例子：用户 40 天前收藏，此后一直保留，这条关系不进入近 30 天收藏排行榜；如果昨天取消又重新收藏，则以昨天为当前收藏时间，进入窗口，但只算一人。收藏列表本身没有这个 30 天限制，40 天前的有效收藏仍然展示。

本人收藏查询先从关系中找到模板，再套用当前有效性：组织模板属于当前租户、启用、未删除且本人命中范围；个人模板未删除且属于本人。**有效总数和分页列表使用同一份判断结果**，不返回失效占位。不能先分页取十个原始收藏、再删掉其中八个失效项，就直接认为本页只有两个有效收藏。按最近收藏时间倒序，同时间用模板 ID 保持顺序稳定即可。

关系表需要一个按 `(租户, 用户, 收藏时间, 模板)` 排列的查询索引，服务本人列表；排行需要按 `(租户, 收藏时间, 模板, 用户)` 扫描窗口内关系。唯一约束负责去重，查询索引负责找数据，两者的职责不同。

**收藏排行榜更重的原因，是“当前仍可见”针对每一个收藏用户，而不是查看报表的管理员。** 查询流程建议是：

1. 从当前租户近 30 天的收藏关系中，筛出当前启用、未删除的组织模板及其收藏用户。
2. 对这些用户去重，获取他们当前的组织身份，再按各模板范围判断每条收藏关系是否有效。同一用户收藏了十个模板，其组织信息在本次请求中复用。
3. 按模板统计有效去重用户数，最后排序取 Top 10；同分按模板 ID 保持稳定。没有有效数据时才返回空榜。

不能先按未经可见性过滤的人数取 Top 10，再检查这十个模板：前十个可能因为用户离职、调部门或移除标签而大量失效，原来第十一名反而应该入榜。也不能用近 30 天使用次数，或模板累计收藏人数代替当前要求。

这一段有两个具体的外部条件要查证：Organization 是否支持合适的批量身份查询，以及能否明确区分“用户已不属于该租户”“标签为空”和“查询失败”。组织全员范围也必须以用户仍属于组织为前提，不能把已经离开的人员长期算进去。现有资源范围能力如果已经处理这些判断，应直接复用，避免另写一套解释。

容量上，若假设某租户窗口内有 2 万条候选收藏关系、涉及 3000 名不同用户，数据库要处理的候选量是 2 万条，外部身份读取应围绕 3000 个去重用户组织，而不是做 2 万次重复查询。这只是说明成本来源，并不是现网规模或性能结论。没有批量能力时，可以通过有限并发取得正确结果，但是否能在页面可接受时间内完成尚未证明；不能先承诺实时毫秒返回，也不能未经讨论改成每天刷新一次榜单。

我的推荐是先以**本次查询取得的当前组织信息完成过滤**为基线。它没有跨系统同一毫秒快照的含义：组织信息与收藏关系来自不同系统，只能明确本次读取采用的权威结果；现有接口的真实缓存和刷新行为需要验证。如果之后证明规模或接口能力无法支持这个方案，再具体讨论数据获取方式或时效代价。

错误处理也应保持事实清楚：判断指定范围所需的组织信息拿不到时，不能当作用户无权限或人数为零。对于缺少必要身份信息的排行榜请求，我建议明确返回“暂时无法计算，请稍后重试”，不给出一个看似完整、实际漏算的 Top 10；本人模板查询同样区分查询故障与确实不可见。无需组织范围判断的“我的”入口可以独立工作。

这一轮我推荐的处理方式是：收藏关系实时增删，查询时统一过滤有效性；排行榜完整计算有效候选后取前十，依赖数据不完整时明确失败。**你是否接受排行榜在无法查清当前可见性时显示暂不可用，而不展示不完整的排名？**
