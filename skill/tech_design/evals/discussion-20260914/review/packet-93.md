## 第 1 轮助手

我会按提供的 tech-design skill 逐步展开讨论，以你这次确认的口径为准。这个需求的核心，是让模板帮助用户准备一次对话，并让管理员持续维护这些模板；准备好的正文和资源进入现有对话链路后，执行依据就是用户的最终输入。

我理解的整体流程如下：

1. **管理员准备模板。** Anchor 保存分类、组织模板、参数定义、可见范围及资源绑定。组织模板新建默认停用，启用后才向命中范围的用户提供。个人模板复用正文、参数和资源绑定能力，查询和修改始终限制为本人。
2. **用户浏览和选择。** 分类导航返回全部未删除分类，不带图标和模板数量。组织模板结合当前租户、启停状态，以及 Organization 提供的部门、祖先部门和标签判断可见性；绑定资源的权限不参与模板是否展示的判断。
3. **模板填入编辑区。** 获取模板内容和默认资源，输入框已有内容时先确认替换。按首页原型，在正文内直接填写文本、使用下拉、单选和多选，同时允许编辑正文及增删资源。参数定义服务于这段准备过程。
4. **用户发送最终内容。** Anchor 使用最终正文、附件、Skill 和知识库列表进入现有链路。不会重新合并用户已移除的资源，也不会因为模板变更、停用或删除而拦截已准备好的发送。Skill 沿用现有不可执行时静默剔除的行为；最终保留的知识库发生权限或资源失效问题时，以写入对话历史的助手消息结束本轮，不调用模型，系统故障另行区分。
5. **提交接受后尽力记使用。** 使用次数表达“提交被接受”，不代表模型已执行成功。统计失败不影响发送，不增加模板专用幂等协议。之后，常用按个人设置和当前模板有效性计算，收藏也只返回当前有效项。

目前真正影响实现的重点，我认为有三个：正文可编辑时参数如何保留和校验；后台多人编辑时怎样保护已经保存的变化；常用和收藏排行怎样结合当前可见范围计算，避免对大量用户逐个调用 Organization。材料没有提供现有对话“提交被接受”的确切落点、组织查询的批量能力和数据规模，这些先作为待查证条件。

这轮先展开**后台排序并发**。这里已经有明确的真实问题，而且会影响后续的数据模型。

假设甲、乙都看到模板顺序 `A、B、C`。甲先把 C 移到最前面，保存成 `C、A、B`；乙仍在旧页面上把 B 移到最前面。如果乙直接提交整个旧列表，甲的调整就会被覆盖。只把两次写入放进数据库事务仍不够：事务能避免写到一半，但还需要识别乙操作所依据的顺序已经过时。

我建议采用**按排序列表检查版本，冲突时拒绝本次调整并刷新**：

- 租户的分类列表有自己的排序版本；每个分类下的模板列表有自己的排序版本。两个管理员调整不同分类内的模板时，互不产生排序冲突。
- 页面读取顺序时同时取得版本。拖动或点击上下箭头后，携带该版本提交调整。Anchor 在一个短事务内检查版本、更新顺序并推进版本；全部提交成功才向前端返回“已保存”。
- 两人基于同一版本提交时，先成功的一次生效。后到的一次不写入旧顺序，界面提示列表已被其他管理员调整，展示最新顺序，让当前管理员基于新列表重新操作。
- 新增、删除模板及跨分类移动也会改变列表成员，因此要同步推进受影响列表的排序版本。单纯编辑模板正文不改变排序版本，避免无关修改打断排序。分类列表的新增、删除同理。

这里需要新增的版本只表达“这份列表的成员或顺序是否发生变化”，不需要让管理员从打开页面到保存一直占有锁。代价是并发冲突时，后一位管理员需要重做一次调整；每次自动保存尚未返回时，页面还应暂缓该列表的下一次排序提交，避免自己的连续操作相互冲突。

另一种做法是让服务器把乙的“移动 B”自动应用到甲保存后的最新列表。但甲已经改变了位置关系，自动合并后的结果可能不再符合乙当时看到的操作意图，还需要处理参照项被移动或删除的规则。当前后台维护场景下，我更倾向于前面的冲突提示方式，行为容易解释，新增协调也较少。

发生并发排序冲突时，保留先保存的结果，让后一位管理员看到最新列表后重新调整，这个处理是否符合你的预期？

## 第 2 轮助手

排序采用前面讨论的方式：按列表检查版本，发生冲突时保留已保存结果，刷新后重新调整。下面先展开“模板内容如何变成用户草稿”，同时讨论它需要怎样的数据模型。这里确定下来，后续模板管理、个人模板和发送接口才能沿用同一套规则。

我建议 **Anchor 保存模板的原始提示词、参数定义和默认资源；前端负责把这些内容组成可编辑草稿，发送时提交最终正文和最终资源列表**。这个过程不需要模型参与。

例如模板原文是：

> 请为 {{对象}} 撰写关于 {{事项}} 的通知，采用 {{表达风格}}，通过 {{通知方式}} 发布。

前端取得详情后，把普通文字呈现为可编辑正文，把占位符呈现为正文中的输入或选择控件。文本参数支持单行、多行；下拉和单选保存一个选项，多选保存选项数组，发送前按确定的顺序连接成正文中的文字。多个位置引用同一个参数时，共享同一份填写值，避免一处修改后其他位置仍是旧值。

这里有两份内容，各自承担不同职责：

- **服务器上的模板定义**：原文、参数名称、类型、必填规则、选项和默认资源，供后续用户重新取用。
- **本次草稿**：用户已经修改的正文、参数填写值、最终选择的资源，以及可解除的模板来源关联。管理员后续修改模板，不回写这份草稿。

前端需要保留正文和参数控件之间的对应关系，才能支持正文编辑与多选交互；可以使用现有编辑器的文本节点和参数节点能力，是否已有合适组件仍待查证。最终发送的是从当前编辑内容得到的纯文本，不把浏览器的 HTML 作为会话执行内容，也不让 Anchor 根据最新模板重新替换占位符，否则用户修改的正文会丢失。

参数约束分两个位置处理。**保存模板时**，Anchor 校验原文占位符与参数定义是否一致、参数是否重名、枚举类型是否配置了有效选项，避免发布无法填写的模板。**使用模板时**，前端按取用时拿到的定义检查必填项，单选只能有一个值、多选只能使用提供的选项。普通对话发送接口继续承担现有正文和资源的校验，不根据统计用的模板 ID 回查参数或版本。

有一个值得明确的交互边界：首页原型允许编辑正文，但它的 `validateInline()` 会把“必填参数控件被删除”也视为未完成。我建议保留这层含义：仍在模板填写状态时，删除必填块会提示缺少哪个参数，保留已经编辑的正文，不自动重新套用模板；用户可以通过已有的解除关联操作转为普通文本，按自己的内容继续发送。参数填写约束只帮助完成这份草稿，不能成为服务端对普通对话增加的模板门槛。

默认资源也在取用时复制到草稿。例如模板绑定 Skill S1、S2 和知识库 K1，用户删除 S2、K1，另加 K2，最终发送就是 S1 和 K2。详情返回的“当前可用”只是提示；即使用户看到详情时有权限，发送前权限仍可能变化，实际执行必须继续使用当前用户身份和现有资源权限校验。

数据存储上，我倾向于**组织模板和个人模板使用同一张模板主表，通过来源和归属区分**，原因是两者共享提示词、参数、图标、资源绑定，收藏和使用统计也都需要一个稳定模板身份。移动分类、修改正文都保留这个身份；“另存为我的”产生新的身份，后续互不影响。

这张表中几组数据的职责是：

| 数据 | 解决的问题 |
| --- | --- |
| 模板 ID、租户、组织/个人来源、个人所有者 | 确定稳定身份和访问边界；个人所有者由登录身份确定 |
| 分类、顺序、组织模板启停状态 | 管理组织模板的归类、展示和上架；个人模板不配置组织分类与可见范围 |
| 名称、描述、图标、提示词、参数定义 | 完整描述一份可供取用的内容 |
| 默认 Skill、默认知识库 | 保存资源身份，供取用、编辑和复制时使用 |
| 软删除标记 | 停止提供模板，同时保留历史引用的识别基础 |

参数与资源列表主要随一份模板整体读取和保存，目前没有按某个参数或绑定资源反查所有模板的需求，因此建议先作为模板中的 JSON 内容保存，避免为这些数组增加多张明细表。资源身份沿用现有资源接口的结构；上限分别是 50 个 Skill 和 50 个知识库。这里是依据访问方式作出的选择，尚无性能实测结论。组织模板可见范围如何接入现有范围能力，下一轮单独展开，先不另造一套权限明细表。

“同一张表”也意味着查询必须始终显式限定归属：管理端只查询当前租户的组织模板，个人模板的详情、编辑、删除都要求当前用户是所有者，不能让管理员权限越过这个限制。

资源保存还要区分三种情况：原有绑定即使失效也可以保留；新增绑定必须校验当前编辑者可见；“另存为我的”允许完整继承源模板的绑定。复制时由 Anchor 读取用户当前可见的源模板并复制绑定，不能让客户端把任意无权访问的资源标记成“继承”来跳过新增校验。资源不可用状态在返回时查询并附加，不能因一次查询失败就删除绑定，也不能把查询失败标成“无权限”。

这轮新增的建议是共享模板主表、以 JSON 保存参数和资源数组，以及前端按取用时定义完成正文内填写。对于“仍在模板填写状态时，必填参数被删除就提示补齐；解除关联后可按普通文本发送”这个具体边界，你希望沿用原型的处理吗？

## 第 3 轮助手

正文内填写、共享模板主表以及参数和资源的保存方式，按上一轮已经展开的建议继续。这轮讨论可见范围与收藏，把“本人能看到什么”和“管理员的收藏排行怎么算”放在一起推演，它们需要复用同一条有效性规则。

**组织模板接入现有资源可见范围能力，以模板自身的资源身份保存范围。** 具体身份结构和存储接口仍待查证，先不新建一套模板专属权限系统。分类不登记可见范围；个人模板直接由租户和所有者限制访问。

一次组织模板查询可以这样运行：

1. Anchor 从登录态确定租户和用户，取得用户所属部门、这些部门的祖先部门，以及人员标签。同一请求内复用这份身份信息，避免每个模板都调用一次 Organization。
2. 查询当前租户未删除、已启用的组织模板。全员模板直接命中；指定范围模板，只要配置的部门与“本人部门及祖先部门”有交集，或者配置的标签与本人标签有交集，就命中。
3. 按对应入口排序和分页。详情、收藏新增、“另存为我的”等通过模板 ID 访问内容的入口，也执行同样判断，不能只依赖首页曾经展示过这个模板。

例如模板面向“研发部”，用户属于“研发部／平台组／后端组”，其祖先部门包含研发部，因此命中。用户同时属于多个部门时，应合并各部门的祖先集合，不能只取一个主部门。用户不在研发部但命中了模板配置的标签，也可以看到模板。

**先判断可见性，再确定分页结果和数量。** 如果先从数据库取 20 条，再在前端剔除不可见模板，会出现本来有下一批可见模板却返回空页、数量与列表不一致的问题。若现有范围能力能提供查询条件，就在数据库内完成过滤；若它返回资源身份集合，则由 Anchor 将该集合与模板条件一起用于查询。它具体支持哪种方式需要查证，但列表和数量必须共用同一套过滤条件。

模板的全员／指定范围切换还涉及保存一致性。例如从全员改成指定研发部，不能先清空旧范围，短暂把模板解释成全员，再补上部门。我的建议是将模板修改和范围修改放在同一个 MySQL 事务内提交；这以现有范围记录能够参与 Anchor 的本地事务为前提。若查证发现范围由其他服务独立持久化，就需要回来讨论其提交契约，不能先假定两个独立写入具备原子性。指定范围为空始终应视为非法配置，不能回退成全员。

收藏本身可以保持简单：**一张收藏关系表，一名用户与一份模板最多有一条当前收藏关系。** 它只需要表达租户、用户、模板和本次收藏时间，不复制模板内容。

- 收藏接口表达“设为已收藏”，已经收藏时保持原关系和时间不变。这样 HTTP 重试不会把一个月前的收藏刷新成今天。
- 取消收藏删除该关系，重复取消也返回成功。它不删除个人模板。
- 取消后重新收藏，重新记录收藏时间，因此可以重新进入最近 30 天窗口；唯一关系仍保证同一用户最多计一人。
- 模板暂时停用或用户暂时失去可见范围时，底层关系保留。查询时不返回该项，也不计入数量；以后恢复有效就重新出现。

新增收藏需要模板当前可见；取消收藏只操作本人关系，不必要求模板仍可见，避免失效关系无法取消。若用户收藏与管理员停用恰好交错，可能留下底层收藏关系，但后续查询仍按当前状态过滤，不会通过收藏重新开放模板内容。

这张关系表的索引来自三个实际读写路径：

| 索引方向 | 用途 |
| --- | --- |
| 租户、用户、模板，唯一 | 防止重复关系，定位收藏和取消操作 |
| 租户、用户、收藏时间、模板 | 按最近收藏时间读取本人的收藏列表 |
| 租户、收藏时间、模板、用户 | 管理端扫描最近 30 天的收藏候选关系 |

这些索引都需要随收藏写入维护；暂不增加独立的收藏计数表，因为模板启停、范围变化和用户组织变化都会使预先保存的人数过时。

**收藏排行榜必须使用收藏者的身份判断，不能使用管理员自己的身份。** 比如某模板原先允许研发部和销售部使用，后来只允许研发部，那么销售部用户的现存收藏关系可以保留，但应退出这份模板的当前排行人数。

因此排行查询先取本租户最近 30 天仍存在的收藏关系，关联已启用、未删除的组织模板，再针对收藏用户判断当前范围命中情况，最后按模板累计去重人数并选前 10。同分时用模板 ID 固定顺序即可。不能先按未过滤人数取前 10 再检查权限，否则第 11 名以后可能有真正应当上榜的模板。

这部分最重的成本是组织信息读取。应按候选关系中的不同用户集中取得部门和标签，一名用户在本次排行查询中只解析一次，再复用于其收藏的各个模板。**是否已有批量查询能力尚未确认**；如果没有，需要讨论 Organization 是否补充批量接口，不能把它当成已存在的能力。

目前可以判断的是：成本随近 30 天候选收藏关系数和去重用户数增长，Top 10 不代表只需检查 10 条数据。还没有规模和延迟实测，不能据此承诺一次请求能处理多少人，也先不增加定时快照或跨请求缓存。若实际规模使这条读取路径无法满足响应要求，再讨论批量化、查询优化或允许怎样的刷新延迟；不能在实现里悄悄把“当前仍可见”改成历史累计人数。

组织服务故障时，我建议依赖当前范围判断的组织模板浏览、收藏数量或排行榜明确返回“暂时无法获取”，不能返回未经校验的内容，也不能把未知人数显示为零。个人模板可独立读取，已经准备好的对话继续走原来的发送链路。这里的“当前”指本次查询取得的模板状态与组织信息，不额外引入跨服务全局快照协议；查询期间又发生的组织变动由后续刷新体现。

对于组织信息暂时不可用的情况，让受影响的浏览或统计区域显示暂不可用、恢复后重新查询，而不返回可能过时的可见性结果，这个处理边界是否可以接受？


## 第 4 轮用户

你已经解释清楚的建议可以按推荐继续；尚未展开的设计还没有确认。请按你认为合适的顺序继续讨论。规模目前没有可靠实测数据，需要时请明确假设。


## 第 4 轮助手

可见范围、收藏关系及组织查询失败时的处理，按上一轮已经展开的建议继续。下面讨论使用记录、个人常用和管理统计，先把一次发送怎样变成统计记录说清楚，再推导存储和查询。

**统计挂在现有对话链路确认接受一轮新发送的位置，之后以不阻塞发送的方式尽力记录。** 这个确认点应当是现有服务已经接收本轮用户消息、可以继续处理该轮请求的业务落点；如果现有链路以用户消息持久化成功作为该落点，就在其后接入。具体函数和提交时序尚未查证，不能把 HTTP 请求刚到达、流式连接建立或模型最终答完当作同一件事，也不为统计新增对话生命周期。

一次实际执行可以这样展开：

1. 用户发出最终正文和资源，附带可选模板 ID。租户、用户身份取自服务端登录上下文。
2. 对话入口完成原有的接受流程。本轮在接受前被拒绝，不计使用；已经接受后才因知识库权限、资源失效或系统故障结束本轮，仍可以记一次使用。
3. 在接受点之后，尝试投递一份很小的使用记录，随后继续原有处理；投递和落库结果都不决定是否调用后续服务、是否返回发送成功。
4. 后台写入记录。模板所属租户和个人所有者可以在这里核对，防止把记录挂到其他租户或其他人的个人模板；不以模板当前启停、删除、版本或组织范围变化否定已经准备好的正常发送。

因此，统计用的模板查询、数据库写入和 Organization 查询都不应出现在发送的前置校验中。模板 ID 不存在或异步核对失败，可以放弃这条统计，不能反过来撤销已经接受的消息。

实现上优先复用已有的非阻塞后台任务能力，是否已有需要查证。若没有，建议在 Anchor 内使用有界的内存队列和固定数量的消费协程：投递时队列满就放弃本条记录；消费者使用独立的短超时写入 MySQL，避免沿用已经结束的 HTTP 请求上下文。队列容量和并发数要依据实际负载配置，当前不凭空定数。

这样做会有明确的损失边界：进程退出可能丢失队列里的记录，投递失败或数据库故障可能漏记；请求重试若被原有对话链路当作两次新发送接受，也可能重复记录。这些都符合已确认的尽力统计口径。当前不需要为了消除这些偏差增加事务消息表、持久化重放或模板专用幂等 ID，也不应在每次发送时启动不受限制的后台协程。

前端发送后继续保留模板来源关联，用户主动解除后才停止在后续新发送中携带模板 ID。断线续流和重新生成沿用原有处理入口，不经过“新发送被接受”的统计接入点；如果现有对话入口已经识别出某次 HTTP 重试并返回原结果，则自然沿用该结果，不再补记。这里复用原链路对请求的识别，不让统计自己决定重做业务操作。

持久化先采用**一张使用明细表，一条记录表达一次观察到的已接受发送**。它保存记录 ID、租户、用户、模板 ID 和服务端的接受时间。暂不保存提示词、参数答案、资源列表，也不保存模板完整快照，这些都不是常用和本期统计的计算依据。异步写入即使晚了几秒，也用接受时间归入日期，避免跨午夜时被记到另一天。

选择明细表，是因为用户可以把常用窗口从 7 天改到 90 天，还需要按模板计算使用人数和自然日分布；只保存一个累计次数无法重新计算。先直接从明细聚合，可以少维护一套每日汇总与明细之间的一致性。索引对应两条主要路径：

| 索引方向 | 主要查询 |
| --- | --- |
| 租户、用户、接受时间、模板 | 当前用户在所选时间窗口内使用了哪些模板 |
| 租户、接受时间、模板、用户 | 管理端近 7／30 天的使用次数、人数及趋势 |

组织模板软删除后，模板身份和名称仍保留，管理使用统计可以继续识别历史记录。使用统计与收藏排行的筛选规则不同：历史使用不能因为模板现在停用、删除，或者使用者后来换部门就消失；收藏排行则需要判断当前模板和当前收藏者是否仍有效。管理端使用统计始终只取本租户的组织模板，个人模板不参与。

个人常用设置单独保存，每个租户、每名用户一条，包含窗口天数、最少次数、展示条数和软删除标记。没有有效设置时使用 30 天、3 次、20 条；保存时由 Anchor 校验需求中的允许范围。至少覆盖两个自然日固定写在查询规则里，不新增一个可修改字段。恢复设置可以更新原记录并清除删除标记，无需同时保留多条有效配置。

一次常用查询的顺序是：

1. 读取本人最新设置，算出窗口起点。
2. 按本人和窗口扫描使用明细，按模板统计次数、不同自然日数量及最近使用时间。
3. 留下次数达到门槛、至少覆盖两个自然日的模板，再按当前有效性过滤组织模板和本人个人模板。
4. 建议按使用次数倒序、最近使用时间倒序、模板 ID 固定顺序排列，最后取设置的展示条数。

这里必须在过滤当前不可见模板之后再取前 N 条，否则可能被失效模板占用名额。修改个人设置后，下一次查询直接使用新范围计算，不需要改写历史记录，也不需要触发后台重算任务。统计刚进入队列时，常用可能暂时还未增加，写入后后续查询会反映出来；不会为了界面立刻加一而阻塞本次发送。

时间口径有一个尚未明确的地方。我的建议是常用窗口、管理趋势和收藏排行统一使用产品已有业务时区；材料未提供该约定，暂按 **Asia/Shanghai，并以包含今天在内的最近 N 个自然日** 讨论。例如 7 天窗口从六天前的零点开始，到本次查询时刻结束。数据库保存统一时间戳，服务端把业务日边界换算成查询时间范围。这样“两天内使用”和图表上的日期可以直接对照，也无需新增个人时区设置。

性能上，单用户常用的成本取决于该用户窗口内的使用记录数，管理统计取决于租户近 30 天的记录数；内存队列的积压取决于发送速度和数据库消费速度。现在没有可靠规模数据，因此明细聚合是当前的简单起点，不能据此承诺延迟或吞吐。使用记录需要至少支持完整的 90 天查询；是否长期归档和何时引入汇总，应结合实际增长另行决定，不在本期先建立一套归档系统。

这轮提出了非阻塞尽力落库、明细聚合和常用设置的具体做法。时间窗口按上述业务时区中的“最近 N 个自然日”计算，是否符合你希望用户看到的口径？
