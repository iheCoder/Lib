## 第 1 轮助手

我会按提供的 tech-design skill 和你逐步推演。先把整体链路讲清楚，本轮重点讨论尚未确定的并发排序；其他重要机制再沿着这些选择展开。

我的理解是：**模板负责帮助用户准备一份可编辑的对话草稿；Anchor 管理模板数据，现有对话链路负责执行用户最终提交的内容和资源。** 你给出的最新口径直接作为设计前提。

从用户操作到最终结果，我建议整体这样衔接：

1. **浏览与取用。** Anchor 返回分类和当前用户可见的模板。分类没有图标和模板数量；组织模板按租户、启停状态、部门及标签范围过滤，个人模板限定本人。资源使用权限不参与模板列表过滤。
2. **准备草稿。** 用户选择模板后，将正文、参数定义和默认资源填入编辑区；已有正文时先确认替换。首页原型实际支持正文内填写、下拉、单选、多选以及修改周围正文，这部分应保留。参数填写完成后形成最终文本，用户可以继续增删资源。
3. **提交对话。** 前端提交最终正文、附件和完整资源列表，模板 ID 作为可选统计信息。服务端不按模板重新拼装正文或补回资源，也不以模板状态、版本或统计结果决定是否接受正常发送。原型 `send()` 中检查模板失效、版本变化并阻断发送的旧逻辑不能照搬。
4. **执行与反馈。** Anchor 按现有链路准备 Skill、召回知识库，再调用 Maestro。Skill 不可执行时沿用静默剔除；最终保留的知识库发生权限或有效性错误时，写入明确的助手消息并结束本轮，不调用大模型。系统故障另作提示。这里要保留“提交已接受”和“任务执行成功”的区别。
5. **记录与查询。** 在对话确实被接受之后尽力记录使用，再服务于个人常用和管理统计；记录失败不传回对话主流程。收藏查询和收藏排行另外按需求要求核算当前有效关系，不能因为使用统计允许偏差，就一并放宽收藏口径。

上述服务分工来自你提供的背景；现有代码中究竟在哪里确认“提交被接受”、Organization 能否批量查询人员范围、资源接口能否区分删除与无权限，目前材料不能证明，后续会明确列为接口对接条件。

真正影响方案的地方，我认为主要有三处：正文可编辑时参数约束如何保留；多人修改时如何保护顺序而不扩大竞争范围；收藏排行如何判断每位收藏者当前仍然可见，避免大量逐人调用。这些需要具体推演，不能只靠字段和接口列表说明。

**先讨论排序：我建议旧页面发生冲突时拒绝本次排序，展示最新顺序，让管理员重新操作。** 当前需求是防止覆盖别人的修改，并未要求自动合并两个管理员的排序意图。自动合并需要解释双方都移动同一模板等场景，我倾向先不引入这层复杂性。

例如，甲、乙都看到某分类顺序是 `A、B、C`。甲把 C 移到最前并保存，乙随后根据旧页面把 B 移到最前。此时直接接收乙提交的整份顺序，就可能把甲的调整覆盖掉。只给每条记录加锁也解决不了：锁能让写入依次发生，却不能识别乙提交的是旧视图。

建议让每个排序列表有自己的版本，随列表一起返回：

- 当前租户的“分类列表”有一个排序版本。
- 每个分类的“模板列表”各有一个排序版本，停用但未删除的模板也属于这个列表。

甲和乙读到版本 8。甲提交调整时带上 8；Anchor 在 MySQL 的同一个事务内检查版本、更新顺序，并把版本改成 9。乙再带着 8 提交，服务端发现不一致，整次排序不写入；前端提示顺序已变化并加载最新结果，不自动重试旧顺序。版本检查与写入必须处于同一事务保护下，避免检查通过后被另一请求插入修改。

这个版本表示的是“列表成员与顺序发生了变化”，因此还需要守住几个边界：

- 新建、删除或移入移出模板时，也要在同一事务内更新受影响分类的排序版本，否则旧页面可能漏掉新增成员。
- 模板从分类 X 移到 Y 时同时影响两个列表；两处锁按固定顺序取得，减少交叉移动时的死锁风险。
- 仅编辑名称、正文、资源绑定，不改变排序版本；排序更新也只写顺序字段，不能把旧页面里的正文等内容一起保存。
- 不同分类内的模板排序使用各自的版本和锁，不共用一个租户级模板排序锁。分类导航自身的排序才在租户分类列表内协调。

它的代价是：同一列表里即使两人调整不同模板，后提交者也可能需要重做；好处是冲突结果明确，不会悄悄改变另一人的顺序。同一页面连续拖动也需要按次保存，前一次成功后拿新版本再提交，避免自己产生版本冲突。

存储上可以先考虑整数顺序，同一次调整只更新位置实际变化的记录。把末尾一项拖到开头，仍可能改动整个分类的记录，成本随该分类模板数增长；目前没有规模数据，不能据此承诺具体耗时。是否需要减少大范围顺序更新，应在确认实际数量级后判断。

你是否接受这种处理方式：同一列表发生并发修改时，保留先成功保存的结果，后提交者看到最新顺序后重新调整？

## 第 2 轮助手

排序沿用刚才的推荐：按实际列表维护排序版本，旧页面冲突时拒绝覆盖，不同分类分别协调。后面的内容属于新展开的设计建议。

接下来先把**模板怎么存，以及模板怎样变成用户可编辑的草稿**连起来讨论。这一步决定个人模板、收藏和统计怎样引用同一个模板，也决定参数填写是否会牵制正常对话。

**我建议组织模板和个人模板共用一张模板主体表，以类型和归属区分。** 两类模板都有名称、描述、图标、正文、参数和资源绑定，也都需要收藏、使用统计和稳定身份。共用主体后，模板移动分类、修改内容，都不需要改变收藏和统计引用。

两类记录的业务边界仍然明确：

| 模板类型 | 归属与访问条件 | 特有信息 |
| --- | --- | --- |
| 组织模板 | 当前租户；用户端另外检查启用状态和可见范围 | 所属分类、分类内顺序、启停状态、可见范围 |
| 个人模板 | 当前租户且所有者就是当前用户 | 所有者；没有业务分类和组织可见范围 |

这些限制需要落在 Anchor 的服务端查询和修改条件里。比如管理员查询组织模板，查询条件必须限定组织类型，不能因为具有管理员身份就查询到同表中的个人内容；个人模板的查看、编辑、删除则同时限定租户、类型和本人身份。“全部”入口才按业务要求组合可见组织模板与本人个人模板。

另一种做法是把两类模板分成两张表。它能让各自字段更整齐，但收藏、常用以及“全部”入口需要处理两套模板引用和查询分支。当前两类模板的正文与使用方式基本一致，我倾向共用主体，并用明确的服务方法约束访问。这个取舍的代价是：同表中会有只适用于某一类型的字段，开发时必须始终带对归属条件；仅仅放在同一张表里不会自动获得权限隔离。

正文和参数，我建议这样保存：

- 正文保存带占位符的纯文本，例如“请分析 {{业务}}，重点关注 {{分析维度}}”。
- 参数定义作为该模板的一份 JSON 保存，包含参数名、类型、是否必填和选项。五种类型是单行文本、多行文本、下拉、单选、多选。
- 不保存页面生成的 HTML。参数定义与正文一起读取、一起保存，当前也没有按某个参数选项搜索模板的需求，没有必要把每个参数拆成独立数据表。

管理员保存模板时，Anchor 检查占位符与参数定义一致、参数名不重复、选择类型有合法选项。一个参数可以在正文中出现多次，但只定义一次，对应同一份填写值。这里校验的是模板能否正确编辑和填写；并不要求管理员创建模板时提供参数实际值。

沿着一次操作看，用户使用上面的模板时，处理过程是：

1. **取一份当前内容。** 通过模板详情取得用户此时有权查看的正文、参数定义和默认资源，放入当前草稿。用户如果已有正文，先完成替换确认。
2. **在正文里编辑。** 前端把占位符显示为填写或选择控件，周围文字继续可编辑。比如把“请分析”改成“请结合附件分析”，再填写业务、选择多个分析维度。正文修改和参数值都保留在这份草稿中；相同参数的多处出现同步显示。
3. **从当前编辑内容生成发送文本。** 将参数控件替换为实际值，多选值可按选项顺序用“、”连接。生成文本时必须遍历当前编辑结果，不能拿原始模板正文重新替换一遍，否则会丢掉用户改写的“请结合附件分析”。
4. **提交普通对话。** 发送最终文本、附件和最终资源列表，模板 ID 随请求供尽力统计使用。参数定义、页面 HTML、模板当前版本都不成为对话提交的必需信息。

前端具体使用哪个编辑器，材料没有给出现状；实现时应先复用现有组件承载正文与参数控件，不在这里预设新编辑器框架或通用文档协议。

**必填校验分别放在模板配置和草稿填写这两个环节，不在发送服务端重新读取模板来校验。** 用户尚在使用参数控件时，前端检查必填值与枚举值，缺少时定位提示。原型还会把被删除的必填控件视为未完成；我建议保留这个约束，同时提供恢复缺失控件的操作，保留周围已经编辑的正文，避免只能重新填入整份模板。

用户通过“解除模板关联”转成普通文字后，已填内容保留，再按普通输入规则处理。这也说明参数必填属于填写辅助约束，不能作为资源授权或服务端执行安全边界。真正的资源权限仍由现有执行链按用户身份检查。

这里再推演一个容易写错的交错过程：用户打开模板并修改了正文，随后管理员停用模板、删除它或修改参数选项。用户手中这份草稿继续保留原来的参数定义和填写值，发送使用最终文本及资源；服务端不会取新模板覆盖它，也不会让统计查询失败反过来阻断发送。后续重新打开模板时，才按当时的模板状态与内容处理。

存储查询也由这些操作推导：组织模板列表需要服务于“租户、分类、顺序”的读取，个人列表需要服务于“租户、所有者”的读取；模板 ID 用于详情、收藏及统计引用。具体联合索引还要结合下一轮的可见范围查询一起确定，避免在查询写法未确定前堆索引。参数 JSON 不参与列表过滤，列表只取卡片需要的字段，正文与参数在详情或编辑时加载。

这一轮希望先确定主体建模方向：**组织模板和个人模板共用模板主体，服务端按类型及归属严格隔离访问；正文与参数作为一份配置保存，使用时形成独立可编辑草稿。** 你是否接受这个方向？下一步我会据此展开可见范围和资源绑定，特别是如何保留失效绑定、如何区分“保留旧绑定”与“新增资源”。

## 第 3 轮助手

模板主体共用、正文与参数一起保存、使用时形成独立草稿，沿用上一轮建议。接下来讨论可见范围和资源绑定：前者决定能否取得模板，后者决定默认带入哪些资源，执行权限仍由资源自身确认。

**可见范围优先复用现有按资源身份管理范围的能力。** 模板以自己的资源类型和模板 ID 接入，不另建一套模板专用的部门、标签权限系统。分类继续只有归类与排序职责。

以一个用户浏览组织模板为例：

1. Anchor 从登录身份取得租户与用户，不能接受前端自行指定查询他人的身份。
2. 从 Organization 取得该用户所属部门、这些部门的全部祖先部门，以及人员标签。用户可能属于多个部门，应合并这些集合。
3. 模板先满足当前租户、未删除、已启用，再判断范围：全员模板直接命中；指定范围的部门与上述部门集合有交集，或者标签有交集，就命中。
4. 将命中条件用于列表筛选，再排序、分页。详情和新增收藏也执行同一套可见性判断，避免通过旧卡片或猜测 ID 绕过列表限制。

例如，模板选择“研发部”或者“新人”标签，研发部下三级子部门的成员和其他部门带“新人”标签的成员都可见。这个过程查询的是当前用户的部门及祖先，不需要把研发部所有下级人员展开后逐一写入模板。

我建议一次列表请求尽量共用一次人员范围查询，避免每张卡片都调用 Organization。范围过滤还必须与分页衔接：不能取出第一页后随手删掉不可见项，就把残缺页面和错误的后续分页返回给用户。

现有范围能力能否直接支持数据库过滤或批量筛选，材料没有给出；这是需要对接的具体能力条件。如果目前只有逐资源检查接口，需要补足列表查询能力，不能把逐条网络调用当作已解决的实现。范围查询失败时也不能默认放行，或者伪装成“用户没有权限”；已经准备好的对话草稿仍按前面确认的规则发送。

范围判断使用本次从 Organization 取得的人员事实，MySQL 中的模板状态则按本次查询读取。组织关系可能在两次读取之间改变，现有材料不能证明跨服务原子快照；本方案也不引入跨服务锁。这里的检查是一次读取时的可见性判断，不承诺组织变更与模板查询在同一瞬间完成。

**资源绑定保存资源身份，不保存一份会被当作执行依据的权限结论。** 我建议模板主体中分别保存 Skill 引用数组和知识库引用数组，每类最多 50 个，资源身份使用各资源服务已有的身份表达，避免把不同来源的资源错误地当成同一个 ID。

这两个数组可以先用 JSON 保存：当前读写都是随模板整组加载、整组修改，没有按“绑定了某个 Skill”反向检索全部模板的需求，暂不需要新增资源关联表。服务端检查重复与数量上限；即使资源已经失效，只要仍保留在绑定中，也计入 50 个限制。

详情或编辑页面需要状态时，再按查看者身份查询各资源服务。可识别时显示无权限、已停用或已删除；接口超时只能显示状态暂时无法确认，不能据此写成已删除，更不能把引用清掉。卡片列表不必为每个模板解析最多 100 个资源的状态，否则模板数会直接放大外部调用量。执行时始终重新走现有资源权限链。

编辑保存的关键是区分“已经存在的引用”和“这次新增的引用”。例如数据库原来绑定 Skill A、B，其中 B 已无权限；管理员把正文改了，并把绑定调整为 B、C：

- B 是数据库中已有的绑定，允许保留，不因当前无权限而拒绝保存。
- A 没有出现在最终列表里，是管理员主动移除。
- C 是本次新增，必须检查当前编辑者有权看到它，不能只相信前端选择器已经过滤。

这个差异要与服务端读取的原绑定比较，不能相信前端传来的“这是旧绑定”标记。新增资源校验失败时，整次保存失败，页面保留编辑内容；不会先改正文、再留下部分绑定修改。

**为保证这个比较基于正确的原记录，我建议给模板配置增加独立的编辑版本。** 它解决的是正文、参数、范围和绑定被旧编辑页覆盖的问题，与已确认的排序版本分开。

保存流程可以这样安排：先读取模板和编辑版本，计算新增资源并在事务外完成外部可见性检查；然后进入短事务，核对编辑版本仍然一致，保存配置与绑定并增加版本。若其他管理员已经修改，整次保存返回冲突，不根据新记录悄悄重新解释旧请求。纯排序不改变配置编辑版本，保存正文也不写回旧页面的排序值；移动分类、启停等确实改变编辑页配置的操作则需要更新编辑版本。

外部资源检查后，权限仍可能马上被撤销。这里不需要为“检查”和“绑定落库”建立跨服务事务：绑定本来就允许随后失效，也不会授予权限；保存只证明校验当时满足新增条件，执行权限由真正执行时的检查保证。这样不用在数据库事务里等待资源服务，也不会让资源服务故障长时间占住模板行锁。

可见范围与模板配置能否在同一个事务内保存，取决于现有范围配置是否与模板同属 Anchor 的 MySQL。目前材料没有说明。我推荐以同库事务保存为接入方式；如果范围配置实际由远端服务持有，这部分需要重新讨论生效时机与失败恢复，不能直接宣称整体保存已经具备原子性。

“另存为我的”还有一个专门的继承边界：原组织模板已有的全部资源，包括当前无权限和失效项，都先进入个人模板编辑内容。保存时携带源模板身份和读取时的配置版本，由服务端确认源模板仍可读取，并据其绑定判定哪些属于合法继承；用户额外加入的资源仍走新增校验。不能把一个普通新建请求里的任意资源都解释为继承资源。

如果编辑期间源模板发生变化，建议保留用户编辑内容并提示重新确认来源，不默默换成新绑定。复制成功后，个人模板拥有自己的 ID 和配置，与源模板独立；后续源模板变化不再影响它。这里的冲突处理只影响创建个人模板这次配置操作，不影响用户已经准备好的正常对话发送。

这一轮新增的主要取舍是：**多人编辑模板时，也拒绝旧配置整份覆盖新配置，保留草稿让管理员重新处理；服务端不自动合并两人的正文与资源绑定。** 你是否接受这个处理方式？下一轮再展开收藏、常用和管理统计，把数据记录、查询与规模成本一起推演。


## 第 4 轮用户

你已经解释清楚的建议可以按推荐继续；尚未展开的设计还没有确认。请按你认为合适的顺序继续讨论。规模目前没有可靠实测数据，需要时请明确假设。


## 第 4 轮助手

模板配置并发编辑按上一轮建议处理。接下来把收藏、常用和管理统计放到实际读写流程里讨论。

这里有两种不同的保障要求：使用统计允许少量重复、漏记，必须与对话提交解耦；收藏列表和排行榜则需要按当前收藏关系、模板有效性和人员可见性计算。不能为了让两者实现统一，给发送增加可靠消息协议，或者把收藏排行也改成近似结果。

**使用记录，我建议先按“用户 × 模板 × 自然日”累计，不保存每次提交的独立统计明细。** 当前要回答的是次数、使用人数、趋势和跨日使用，没有逐次统计审计的要求。这种粒度足以支持这些查询，记录量随每天实际使用过的用户与模板组合增长，而不随每次重复发送增长。

这里需要明确一个设计建议：统计日沿用原型的北京时间，近 N 天表示包含今天在内的 N 个自然日。例如近 7 天从六天前零点开始，到当前时刻结束。这样常用窗口、至少两个自然日和管理趋势能够使用同一份日记录；它与滚动的最近 N×24 小时并不完全相同，本轮还需要你判断。

一次使用记录的写入过程建议是：

1. 现有对话链路确认提交已经被接受，才取得租户、实际用户、模板 ID 和接受时间。不能在 HTTP 请求刚进入时计数，也不等待 Maestro 最终成功。
2. 提交路径尝试交给一个有并发上限的后台写入任务。没有空闲额度就跳过，不等待、不反压发送；不为本需求增加可靠消息队列或补偿状态表。
3. 后台按模板 ID 确认其租户和类型，个人模板还需属于该用户。模板停用、软删除或配置版本变化都不作为拒绝正常使用归因的条件；伪造、跨租户或无法识别的模板 ID 直接不记，不影响已经接受的对话。
4. 按接受时间所属日期，对该用户、模板、日期的记录原子加一，同时把最近使用时间更新为两者中的较晚值。午夜前接受、午夜后才写入的提交仍计入前一天；后台任务乱序不会把最近使用时间改旧。

后台任务使用独立的短超时，不随着 HTTP 响应结束立即取消，也不能无限占用连接。并发与连接占用都应有上限，具体值需要结合现有数据库连接预算设置，当前没有数据支持填写一个固定数字。服务退出、数据库超时或执行结果未知时允许漏记，也不无限重试；否则这项辅助能力仍可能通过资源争抢拖慢对话。

这里不新增模板专用幂等 ID。同一次普通对话请求的重试是否已经被现有链路识别，需要接入时核实；统计钩子应放在“接受新提交”的位置，断点续流和重新生成不主动触发它。数据库计数采用原子累加解决正常并发覆盖问题，但不承诺消除所有重复提交。

对应的数据职责可以收敛为三类：

| 数据 | 保存什么 | 为什么需要 |
| --- | --- | --- |
| 每日使用记录 | 租户、用户、模板、统计日、次数、最近使用时间 | 同时支持个人常用、次数、去重人数和趋势 |
| 收藏关系 | 租户、用户、模板、当前这次收藏的时间 | 表达仍然收藏，以及是否落在近 30 天窗口内 |
| 个人常用设置 | 租户、用户、窗口天数、次数门槛、展示条数、删除标记 | 查询时应用个人规则；不存在或已删除时回退默认值 |

日记录以“租户、用户、模板、日期”唯一，防止同一天被拆成多行；次数用数据库自增更新，避免两次发送都读到 3，最后只写成 4。收藏以“租户、用户、模板”唯一。个人设置每人一份有效配置，更新或恢复该记录即可，不需要保留多份历史设置。

**常用查询先按个人规则聚合，再过滤当前可见模板，最后取展示条数。** 默认 30 天、至少 3 次、最多 20 条；允许范围分别是 7～90 天、2～20 次、6～50 条，至少两个自然日固定不变。按模板求和得到次数，日记录数得到使用天数，最大使用时间用于排序；推荐依次按次数、最近使用时间倒序，最后用模板 ID 保证稳定次序。

例如某人一天发送五次，只形成一个使用日，仍不能进入常用；分两天分别发送两次和一次，则达到默认门槛。个人规则改变后重新查询这些记录，不重写历史。过滤当前不可见模板必须发生在最终取前 N 条之前，否则失效模板会占掉展示名额。

管理使用统计只选组织模板：次数汇总每日次数，使用人数对整个查询窗口的用户 ID 去重，趋势按日汇总。不能把每天的使用人数相加当作整个窗口的使用人数。已删除模板的历史记录仍保留，通过软删除后的模板身份识别，不能因为普通模板列表过滤了删除记录，就把历史统计一起丢掉；这些记录也不会重新变成用户可用入口。

个人常用主要按“租户、用户、日期范围”读取，管理统计主要按“租户、日期范围”读取，因此除日记录唯一约束外，需要围绕这两条路径配置日期范围索引。代价是每次计数写入要维护相应索引；当前不再加逐次明细或额外汇总表。若以后实际活跃用户与模板组合使扫描成本过高，再根据查询数据调整，不能先假设某个租户规模已经满足性能要求。

**收藏接口建议表达“设为收藏”或“取消收藏”，不要做一次调用就反转状态的 toggle。** 重试“设为收藏”时，已有关系保持不变，也不刷新收藏时间；取消则删除这条关系，重复取消仍成功。取消后重新收藏，建立新的收藏时间；唯一约束保证同一人同一模板始终最多一条关系。

模板暂时停用或用户失去范围时，底层关系可以保留。列表和数量使用同一套当前有效性过滤，不返回占位；恢复可见后重新出现。用户主动取消收藏无需先取得模板详情，避免模板失效后无法清理自己的关系。新增收藏仍需检查当前模板可见。

排行榜的查询过程则要多做一步：

1. 找出当前租户最近 30 个自然日内建立、目前仍存在的收藏关系，关联当前启用且未删除的组织模板。
2. 针对这些关系里的收藏者，取得当前租户成员身份、部门及祖先部门、人员标签，逐个判断其是否仍命中被收藏模板的范围。
3. 只累计有效关系中的去重用户，再排序取前 10；同分时可按模板 ID 稳定排序。

不能先按原始收藏数取 10 个模板，再核验这些人的权限：原来排第 11 的模板可能才是真正有效的前 10。最近 30 天之前收藏且一直未取消的人，也不能仅因关系仍在就计入这个排行。

这部分最重的成本不是取 10 条结果，而是检查候选收藏关系。设候选关系有 F 条、涉及 U 个不同用户，数据库至少要处理相应候选数据，人员查询应按用户去重、分批，避免一条收藏调用一次 Organization。收藏者相同的多条关系复用人员事实，模板范围同样批量读取；最终 Top 10 之前的候选不能随意截断。收藏表需要服务于个人按时间查看，以及租户近 30 天候选读取这两条索引路径。

材料没有证明 Organization 已支持这些批量查询，所以需要落实批量人员范围能力及请求大小限制。没有可靠规模数据时，不能承诺排行榜的具体耗时，也没有依据先放宽“当前仍可见”的口径。查询失败应明确显示排行暂不可用，不返回部分核验结果冒充完整排行；个人常用和管理使用统计可以独立查询。

这一轮最值得先确定的是时间粒度：**采用北京时间自然日窗口，并只保存按用户、模板、日期累计的使用记录，是否符合你的预期？** 这个选择会直接决定使用记录的数据粒度；如果需要精确滚动到当前秒的 N 天窗口，就要换成更细的记录方式。
