排序按刚才已经展开的推荐继续：按列表分别保护顺序，旧版本提交冲突时刷新重做，普通内容编辑不改排序位置。规模暂不作吞吐和耗时承诺。

接下来先讨论**参数填写到实际发送的过程**。这一段决定前端需要保留什么、模板保存时校验什么，以及对话接口为什么不用重新读取模板。

以“请面向 {{受众}}，用 {{表达风格}} 撰写通知”为例，受众支持多选，表达风格是单选；其他模板也可以使用下拉、单行和多行文本。我的建议是：模板在 Anchor 中保存提示词原文及对应的参数定义，包括参数名、类型、是否必填和选择项；它们共同描述可重复使用的输入方式。用户填写的值和修改后的正文属于本次草稿，不写回模板。

保存模板时，Anchor 校验占位符与参数定义相互对应、参数名不重复、选择类型有有效选项等，避免管理员保存一个无法填写的模板。同一个参数在正文中出现多次，可以对应同一份定义和同一个值。这里保留文本和必要的参数定义即可，不需要把原型的浏览器 `innerHTML` 当成后台存储格式。

用户点击使用时，前端获得这次读取的正文、参数定义和默认资源，在输入框里显示可填写的位置。之后同时保留两类信息：用户正在编辑的正文，以及各参数的填写状态。用户在参数之间新增一段话、删除原有说明，发送时都要保留这些改动，不能再拿原模板做一遍替换，把正文恢复回去。多选结果可以沿用原型，用“、”连接为最终文字；单选和下拉都是一个选择值，只是交互不同。

**必填校验只约束仍处在模板填写状态的草稿。** 我推荐保留原型已经表现出来的行为：

- 必填参数为空时，发送前定位并提示补充；不能只看正文是否非空。
- 用户误删了必填参数控件，也不能假装该参数已经填写。界面应提示缺失，并提供恢复这个填写位置的操作，保留用户其他正文改动。原型要求重新点击模板才能恢复，这会重新引入覆盖草稿的问题，不建议直接照搬。
- 用户如果决定完全自由写，可以显式“转为普通正文”：把已经填写的值留下，清理未填写的控件提示，解除模板关联，后续按普通对话发送。这样用户不必为了满足原模板的参数而填入没有意义的内容。

普通正文不能根据某个词是否还存在来反推“必填已完成”，因为用户本来就可以自由编辑文字。相应地，发送接口也不根据模板 ID 加载最新参数定义来拦截；最终输入内容继续满足普通对话接口自身的校验规则。模板保存的合法性、前端填写体验和最终资源权限，是不同位置承担的责任。

这也解释了模板变更时的行为。用户上午打开模板，已经填写一半；管理员随后把“受众”改成“对象”，或停用、删除模板。前端仍保留这次草稿的原定义和值，用户可以填完并发送。即使能够发现新版，也只能提供不阻断发送的更新提示，由用户主动重新取用；发现变更不需要成为每次发送的前置调用，更不能自动替换正文。已经准备好的默认资源同样不自动随新版变动。

资源部分沿这条流程处理：

1. 填入时，把模板预置的 Skill、知识库作为初始选择，保留能识别的不可用提示。用户可以删除它们，也可以通过现有资源选择器增加资源。
2. 发送时，提交最终选择的完整资源列表。比如模板有知识库 K1、K2，用户删掉 K1、加上 K3，Anchor 只能执行 K2、K3，不能再从模板补回 K1。
3. Anchor 按当前用户身份走现有处理链。详情中“可用”的提示只反映查询时状态，不能替代执行时的权限检查；资源可能在用户填写期间被停用或撤权。
4. Skill 沿用当前不可执行时剔除的规则。最终保留的知识库如果权限不足、删除或停用，本轮不进入 Maestro 的模型调用，由会话服务写入明确的助手消息；RAG 超时等系统故障用不同文案说明。

因此，这里有一个需要在现有代码中查证的衔接点：**对话被接受之后，知识库处理失败是否已经能够写入助手消息并结束本轮。** 背景说明了 Anchor 先处理资源再调用 Maestro，但尚未证明错误分支已经具备这项能力。设计上应把它接入真实会话处理流程，不能用 HTTP 返回错误或者“已收到请求”代替需求要求的会话结果。

模板关联期间的每次有效发送仍可携带模板 ID；转为普通正文后解除关联。统计只消费“对话已经被接受”这个事实，不能反过来决定上述正文和资源能否发送。具体在哪里确认接受、怎样尽力记录使用，下一步再结合常用和管理统计需要保存的事实展开。

这一轮需要确定的是草稿交互：**删除必填控件时保留模板填写约束，提供局部恢复；用户通过“转为普通正文”明确放弃参数约束并解除关联。** 你是否接受这个处理方式？
