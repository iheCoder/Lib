草稿交互按上一轮的建议继续。这一轮讨论**使用怎样入账，以及怎样支持常用、使用人数和趋势查询**。我的推荐是：在对话确认接受后尽力更新统计；统计按“某用户在某天使用某模板几次”保存，不先建设逐次事件流水和可靠投递链路。

先明确两个统计假设：本轮暂按 UTC+8 划分自然日，“最近 N 天”指包含今天在内的最近 N 个自然日。这样“至少使用过两个自然日”、每日趋势和窗口边界可以用同一个口径。需求还没有明确最近 N 天是否必须精确到滚动的 N×24 小时，这个差异会影响能否只保存每日数据，不能留到写文档时才决定。

一次实际发送可以这样运行：

1. 对话服务照常校验、接受本次发送，得到已有的业务接受结果。模板统计不参与这个事务，也不提供前置成功条件。
2. 只有到达“本次发送已被接受”的位置，才尝试交给统计处理一条信息：当前租户、当前用户、模板 ID 和接受时间。租户与用户取自服务端身份上下文，不能相信前端自行填写的身份。
3. 统计处理在后台更新当日次数。没有模板关联就不产生这项统计；统计完成与否不改变发送结果。

这里的第一步需要查证现有代码：接受一轮发送究竟由哪段持久化或派发流程确认。仅收到 HTTP 请求、开始解析参数，或建立连接，都不能作为计数依据。如果资源处理在已接受之后失败，这次仍计使用；如果普通对话本身尚未接受就拒绝了请求，则不计。

**异步也有成本，需要限制统计自己的负担。** 我建议优先复用现有的有界异步处理能力；若没有，可以使用一个容量有限的进程内队列和固定数量的处理协程。发送侧只做不等待的入队尝试，队列满时丢弃该条统计；统计写入有超时，并限制占用数据库连接的数量，不能为每次发送无上限地启动协程。

进程退出、数据库异常、队列满都可能漏记；HTTP 重试若在现有链路再次触发了接受事件，也可能重复计数。这符合你已确定的统计口径，不新增模板专用幂等 ID、持久化消息队列或补偿状态。若已有对话去重机制能够准确区分“新接受”与“返回上次接受结果”，采集点应复用它，但不为模板统计重建一套。

后台统计可以核对模板是否属于该租户，以及个人模板是否属于该用户。停用和软删除记录仍可参与这一身份核对，不能要求模板当前启用或版本相同；查不到记录、归属不符或查询失败，就丢弃这条统计，正常对话已经独立进行。异步处理还应使用接受时记录的时间，不能用真正写入数据库的时间，否则跨午夜积压会把使用记到错误日期。

存储上，建议一张使用日统计表承担这些查询，核心业务信息只有：

| 信息 | 存在理由 |
| --- | --- |
| 租户、用户、模板身份 | 确定是谁使用了哪个模板，并隔离租户与个人数据 |
| 使用日期 | 支持窗口过滤、至少两个自然日、按天趋势 |
| 当日使用次数 | 同一天重复发送需要累加，不能只记录“用过” |

对“租户、用户、日期、模板”建立唯一约束。第一次使用创建一行，之后使用通过数据库原子累加更新次数，避免两次同时发送都读到 1，最后只写成 2。计数允许投递层面少量重复和遗漏，不代表数据库写入本身可以存在可避免的覆盖错误。

这一个模型就能直接支持：

- **个人常用：** 读取本人窗口内数据，按模板求使用次数之和，并检查有记录的日期至少为两天。套用用户自己的次数门槛，再与当前可见模板相交，排序后取展示条数；不能先取前 20 条再过滤失效模板，否则可能漏掉后面符合条件的模板。排序建议按使用次数降序、最近使用日期降序、模板 ID 稳定排序。
- **管理使用次数与趋势：** 只取当前租户的组织模板，按窗口求次数之和，按日期分组得到趋势。
- **管理使用人数：** 在整个查询窗口内按用户去重；不能把每天的使用人数相加，同一个人在多天使用仍然只是一人。

模板移分类不改变模板 ID，统计自然连续。已停用、软删除的组织模板仍保留可识别的模板记录，因此管理使用统计可以保留它们的历史数据；这里不能复用首页“只取当前可用模板”的过滤。个人模板即使有使用数据，也不进入管理员的使用统计。收藏排行榜则有自己的当前有效性要求，不能直接套用这里的统计口径。

索引也由这些查询推导：唯一索引可以按 `(租户, 用户, 日期, 模板)` 排列，服务本人窗口查询及累加定位；另一个索引按 `(租户, 日期, 模板, 用户)` 排列，服务管理端的租户窗口查询。暂不为没有出现的查询逐个加索引；每多一个索引，统计写入也要维护它。

个人常用配置则单独保存每个租户用户的一份设置，包含窗口天数、最少次数、最多条数和软删除标记。未配置或软删除时回退 30 天、3 次、20 条；修改设置只改变后续查询条件，不改日统计数据。7～90 天、2～20 次、6～50 条由 Anchor 校验，至少两天保持固定。

每日聚合减少了存储行数，但**没有自动减少写入次数**：每次被采集到的使用仍会更新数据库。行数随“每天实际使用过的用户与模板组合数”增长；个人查询扫描本人最多 90 天，管理查询扫描租户最多 30 天。当前没有实测规模，我不据此承诺响应时间，也不先增加缓存或第二层汇总。如果后面证据表明写入或窗口扫描太重，再针对真正的成本调整。统计与对话共用 MySQL 时，后台限流只能约束统计负担，不能消除数据库底层资源竞争。

这一轮真正需要取舍的是时间精度：**按自然日统计，可以用这一张日统计表直接支撑现有展示；如果“最近 30 天”必须精确到当前时刻向前 720 小时，就需要保留更细的时间数据。** 我推荐前者。窗口按包含今天的最近 N 个自然日计算，是否符合你希望的产品口径？
