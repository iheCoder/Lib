排序就按刚才的推荐继续：按租户分类列表、分类内模板列表分别维护顺序版本，冲突时保留已提交结果，刷新后重新调整；列表成员变化也要参与版本更新。

接下来讨论**正文内参数怎样编辑，以及最终发送什么**。这里最需要避免的是：用户已经修改了正文，填写一个参数后，系统又用原始模板重新生成整段文字，把用户的修改覆盖掉。

我的建议是把“保存的模板”和“本次编辑的草稿”分开理解。

保存模板时，Anchor 保存提示词原文和参数定义。例如：

```text
请为 {{客户名称}} 整理方案，重点覆盖 {{关注内容}}。
最后给出适合 {{客户名称}} 的下一步建议。
```

这里有三个占位位置，但只有“客户名称”和“关注内容”两个参数。参数定义只需要解释当前交互必需的信息：参数名、控件类型、是否必填，以及选择类参数的选项。“客户名称”可以是文本，“关注内容”可以是多选。

**提示词与参数定义建议作为同一份模板内容一起保存。** Anchor 在保存时检查二者一致：正文中使用的参数都存在，定义中没有悬空参数，参数名不重复，选择类参数配置有效选项。正文和参数定义应同时成功或同时失败，避免用户拿到正文已更新、参数还没更新的组合。参数定义可以存为模板记录中的 JSON；目前没有按某个参数跨模板检索的需求，无须为每个参数单独建表。

用户选择模板后，前端把正文展开成普通文字和参数控件。这个结构只服务当前编辑过程，不把浏览器生成的 HTML 当成模板内容交给后端保存。

沿上面的例子，编辑过程这样运行：

- 用户填写一次“客户名称”，两处同名参数同步显示同一个值；同名参数不能各自变成不同客户。
- 用户把“整理方案”改成“整理售后回访方案”，之后再选择“关注内容”，只更新对应参数控件，保留已经改过的正文。
- 下拉和单选都保存一个选项值，只是交互形式不同；多选保存多个选项值，生成正文时按配置中的选项顺序用“、”连接。多行文本保留换行。
- 发送前，将当前编辑内容按出现顺序转成最终文本。普通文字取用户编辑后的内容，参数位置取当前填写值；不会重新套用原始提示词，也不会读取服务器上的最新模板再拼接。
- 最终资源列表与正文一起进入现有对话接口。前端不需要为了执行模板，额外要求后端根据模板 ID 还原参数或补齐默认资源。

这里要共同确定的是**参数控件被删掉时的行为**。这不是纯实现细节：它决定“正文可编辑”和“必填参数不能遗漏”如何同时体现。

我推荐保持以下规则：

1. 必填参数还在正文中但没有填值，提示对应项并阻止这次发送。
2. 同名必填参数出现多次，用户删掉其中一处，剩余位置仍存在且已填写，就可以发送。
3. 用户把某个必填参数的最后一处控件也删掉，仍提示该项缺失，并提供“补回此参数”的操作；只补回这个控件，保留其他正文修改，不要求重新选择整份模板。
4. 选填参数可以直接删除；保留但未填写时，生成正文为空值，不自动插入“未提供”等用户没有写过的文字。
5. 用户主动解除模板关联后，将已填写内容转为普通文本，未填写控件移除，后续按普通输入编辑和发送，也不再携带该模板的统计关联。

例如，用户误删了最后一个“客户名称”，我们不会要求他把已经写好的售后回访方案全部重填；他可以补回客户名称，也可以明确解除模板关联，自行组织普通正文。

**这些必填检查属于模板辅助编辑的规则，由前端根据本次草稿中的参数定义执行。** 后端仍负责正常对话输入校验和真实资源权限校验，但不把“必须符合某个模板参数结构”变成对话发送的新前置条件。这样，管理员更新或删除模板后，已经准备好的草稿仍然能按原来的编辑内容发送，也符合模板 ID 只用于尽力统计的口径。

这套处理本身不需要查询大量数据；前端成本随正文长度和参数出现次数增长。材料没有给出可靠的容量数据或已经确认的正文、参数数量上限，我不会直接把原型里的演示限制当成业务约束；如果后续发现超长正文或大量重复参数是实际场景，再据此确定必要限制。

本轮的关键建议是：**删除最后一处必填控件仍保留填写要求，但允许局部补回；主动解除关联则转为普通正文。** 你认为这个行为是否符合用户在正文里自由修改的预期？
