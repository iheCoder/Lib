# 离线设计对话实验的方法审计

审计范围：仅阅读 `control/protocol.md`、`control/input-manifest.json`、`input/request.md`、`input/requirements.md`，并抽查两个原型的有关源码片段。未阅读 skill、运行回答、历史会话或记忆。本记录供实验解释使用，不进入被测输入，也不评价 skill。

结论：协议可用于观察“在这些已澄清材料下，模型能否继续展开设计及其代价”；不能将命中三个主题本身解释为无提示的自主发现。原型源码已经暴露部分实现示例，必须在结果归因时扣除。

## 重要限制

1. **主题与部分答案已经给出。** `request.md` 明确点出个人常用配置、正文内参数与多种选择控件、多个管理员的旧排序覆盖问题，还指定发送以最终内容和资源为准、统计尽力且不阻塞发送。需求第 12 节给出窗口、门槛、自然日、当前可见性等规则。复述这些内容是理解或遵守输入，不是主动发现；“统计不能拖累对话”同样是既定约束。

2. **完整原型源码构成实现提示。** `home.html:207-211` 已包含有效性筛选、事件窗口、自然日计算、频次排序和截取；`home.html:281-310` 已包含参数类型、占位符、正文可编辑与序列化；`admin.html:440-442` 已包含全分类 ID 列表、逐项版本校验及全量改写顺序。协议声明原型不代表生产设计，能避免把示例当成强制方案，但不能消除模型接触这些示例带来的提示效应。不能把相同机制的再现认定为独立设计发现。这里只确认存在这些源码，不证明浏览器实际交互全部正确。

3. **归因应对具体论证作区分。** 建议在观察说明中标明“输入明示”“原型已有示例”“模型进一步推导”，并附材料位置或回答轮次。可计为进一步推导的是：为何操作顺序影响结果、可配置窗口对数据保留和查询的要求、参数自由编辑与最终文本之间的语义选择、排序方案如何影响非排序编辑/删除/移动，以及相应成本和取舍。主题由输入点名后，模型自行深入属于主动展开，不能改称自主发现主题。

4. **已有冲突使实验同时测到口径优先级处理。** 需求正文仍保留模板专用幂等 ID、版本变化后重确认等旧文字；原型 `home.html:373` 仍有模板失效或版本变化阻止发送的逻辑。应以 `request.md` 的覆盖声明解释这些差异。正确执行覆盖规则可记为遵循约束；不应把遵循旧原型算作正确实现，也不应要求模型反复质疑已经明确覆盖的业务前提。

5. **判据需要按候选方案适用性解释。** 不预设必须使用全量重排、分类锁、版本字段、日汇总表、异步队列或富文本 AST。排序需要说明实际写入及竞争范围；方案避开了广泛共享锁，可以论证相关影响受限，不必虚构同类锁等待。常用若是有界 Top N，不必强制另造分页接口，但须解释过滤、排序和截取的语义。字符串替换可以是实现组成部分；只要编辑、存储、回显、选择、自由编辑和最终发送语义讲清，不能因没有复杂表示而扣分。已有“真实选择与限制”“适度”条款支持这种解释。

6. **比较结论限于本题与观察窗口。** 每版两个上下文、最多四轮，支持报告出现了哪些论证和遗漏，不支持稳健胜率、因果净收益或跨需求泛化结论。默认续轮策略相同有利于可比，但模型提出的问题和获得的局部确认不同，不能说每轮经历完全相同。根据本题遗漏制定补丁再用本题复跑属于同题改进验证，不能视作独立留出集。尚未讨论的议题按协议记为窗口未覆盖，不推断永远不会处理。

## 可以保持不变的规则

- 保留冻结输入、清单与哈希记录；不为此次评判临时删改原型，避免改变已经开始的比较条件。
- 保留新上下文、相同轮数上限和续轮回复策略；未知业务事实保持未知，不补入未提出的故障提示。
- 保留先解释方案与代价再获取局部反馈，不将局部确认扩张为全部确认。
- 保留逐项定性、匿名版本评分与原始轮次回答；以论证语义及证据来源判断，不用关键词、单一实现或总分替代。
- 保留现有关于晚期澄清输入、无生产源码、无性能实测、无无-skill 对照组的限制声明。本审计仅补充解释边界，不修改协议或实验输入。
