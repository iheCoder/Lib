# 匿名语义评估指引

你将收到四段最多四轮的真实设计对话，包名不表示版本或好坏。不要读取 skill、候选差异、运行目录、映射文件、作者观察或历史会话。只读取 review/packet-*.md、input/request.md、input/requirements.md；原型只在核对输入已有内容时按需查看。

按对话整体分别判断，不要求每轮都覆盖所有主题，也不要求在四轮内完成设计。不用总分和关键词命中统计代替判断。若一项未展开，写“此窗口未覆盖”，不推断后续永不讨论。

每份包给出以下定性观察，并引用轮次和一小段原话：
1. 常用是否串起受理/记录、存储选择、可配置窗口/门槛/自然日、有效性/可见性、排序截取，以及成本增长。
2. 参数模板是否讨论保存与草稿表示、填写/选择、正文自由编辑、控件删除/重复引用与最终发送的语义和取舍。
3. 排序分别观察：旧视图冲突与方案选择；实际写入范围及增长；对普通编辑、删除、成员变更/跨分类移动的竞争与等待。仅不改变排序版本不能证明不会等待；不同合理实现可以用不同方式限缩影响，不强制全量重排、分类锁或某种算法。
4. 是否在说明重要方案与代价后留出反馈，是否把局部确认扩张为整体定稿，是否有明显无依据的行为或承诺。

区分输入明示、原型已有示例和模型进一步推导。输入已明确常用规则、正文内控件、多人排序冲突和统计不阻塞对话，因此主题出现和规则复述不算无提示发现。重点看进一步论证的执行过程、相互影响和代价。

如某包只口头承诺“不相互等待”，却没有说明怎样限制实际竞争，不判为充分。不得把短篇幅本身当优点，也不得因没有长篇 DDL 就扣分。这里是设计讨论，不能证明 SQL 正确性或现场性能。

输出 review/assessment.md，先给一个小表比较各包，再给证据与限制。不猜版本，不建议修改 skill，不读取已完成的其他审计意见。
