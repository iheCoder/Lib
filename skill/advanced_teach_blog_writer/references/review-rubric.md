# 审稿规则

这份 reference 是反平庸审稿器。它的任务不是把句子润色得更漂亮，而是判断文章是否已经具备高级中文技术博客的结构力量、技术可信度和阅读质感。

## 审稿顺序

先审结构，再审技术证据，最后审语言。不要在结构失败的文章上做局部润色；那只会让一篇散文档变成更流畅的散文档。

## 必过门槛

中心论点：读完前两段，必须能用一句话说出文章真正想证明什么、解释什么或改变什么判断。如果只能说“本文介绍了 X 的原理和实践”，说明论点失败。

读者路径：每一节都应该回答上一节自然产生的问题。如果章节可以任意换序，说明文章只是材料堆叠。

金字塔结构：文章必须有一个顶部主论点，并由 3 到 5 个高层分论点支撑。二级标题如果超过 7 个，必须证明它们是必要的抽象层；超过 10 个时默认判定为结构失败，除非用户明确要求手册或 FAQ。

因果连续性：文章必须能从现象走到机制，再从机制走到工程后果。只有“做了什么”和“有哪些模块”，没有“为什么会这样变化”，说明因果链失败。

机制必要性：每个底层机制都要解释一个高层现象。讲了很多源码、协议或架构名词，却无法说明它们服务哪个问题，必须删掉或重连。

工程闭环：文章至少要出现约束、失败模式、验证方式、观测指标、回滚策略、成本权衡或边界条件中的若干项。完全没有工程闭环的文章，只是知识讲解。

证据诚实：版本行为、性能数据、源码细节、线上案例和生态现状必须可验证。无法验证时，语气要降级，明确写成假设、经验判断或示例。

段落质感：文章应该是连续论证，而不是 checklist、PPT 大纲、面试答案、百科条目、短视频稿、SEO 软文或 API 文档。

问题消化：用户给出的一系列问题必须被吸收到文章主线里。除非用户明确要求 FAQ，连续的“问题 + 回答”、面试追问章节、常见问题章节都判定为失败。

## 打回信号

出现以下情况时，必须返工：

- 开头是“X 是什么”“本文将从以下几个方面介绍”，但没有真实问题或判断。
- 大量段落可以互换位置，说明没有递进关系。
- 标题密集到像目录，正文只是给标题补解释。
- 二级标题超过 10 个，或者标题读起来像一套题库。
- 出现“面试官可能会怎么追问”“常见问题”“Q&A”一类兜底章节，用来堆放未消化的问题。
- 连续使用“首先、其次、然后、最后”推动文章，但这些顺序不是系统机制本身。
- 用十几个 bullet 代替正文论证。
- 机制解释像百科摘录，不能解释当前工程场景。
- 方案描述只有优点，没有代价、边界和失败模式。
- 代码块里放普通解释、总结口号或非代码材料。
- 结尾只说“综上所述”，没有形成可迁移原则。

## 返工方法

如果中心论点失败，重写开头：先给判断，再给读者为什么必须关心这个问题。

如果读者路径失败，重排章节：把每个标题改写成一个读者问题，再按问题的自然发生顺序排列。

如果文章像问答录，先删除全部问题标题，再把问题背后的共同矛盾归并成 3 到 5 个分论点。答案必须进入段落，不允许集中堆在文末。

如果因果链失败，补上“状态变化”：说明某个输入、请求、数据、锁、队列、缓存、连接、事务或调度状态如何一步步改变。

如果技术机制游离，删除不服务论点的知识点。技术博客不是讲全，而是讲透一条关键路径。

如果工程闭环不足，补充观测、验证、回滚、灰度、容量、成本、团队协作或长期治理中的真实环节。

如果语言像清单，把并列 bullet 改写成段落，让每段包含原因、转折或结果。

## 交付前自问

交付前用下面五个问题做最终检查：

1. 这篇文章最重要的一句话是什么？
2. 读者为什么会愿意读下一节？
3. 哪个机制解释了最关键的现象？
4. 哪个工程边界阻止结论被滥用？
5. 如果删掉所有列表，文章还是否成立？
6. 如果删掉所有问号标题和“面试追问”章节，文章是否更像一篇博客？
